# 龙宫天空渲染总设计

> 状态：**现行实现**（基于 `e548e19`「使用缓存对天空盒进行优化」）
> 覆盖范围：`beloong:loong_palace` 维度的自定义天空渲染、天气视觉禁用、维度特效注册、
> 相关资源与维度类型契约
> 本文取代此前所有分散的龙宫天空相关设计/计划/对照文档（见文末「已废弃文档」），
> **是龙宫天空渲染的唯一权威文档**；与其他文档冲突时以本文件为准。
>
> **性能现状**：天空占渲染线程约 **1.94%**（优化前 2.955%）。
> 该渲染路径属合理开销范围，**不存在待修复的性能问题**；几何缓存已于 2026-09-11 落地。

## 一、设计目标

龙宫（`beloong:loong_palace`）是「化龍」整合包的独立主场维度，需要一个与主世界观感**完全不同**的天空：

1. **多层动态天空盒** —— 采用 Dramatic Skys 的九层图集方案（星星 / 月掩 / 遮罩 / 昼 / 夜 / 太阳 / 太阳光晕），
   通过昼夜 alpha 淡入淡出与逐层旋转形成动态天象。
2. **日月本体** —— 独立的太阳与月亮贴图，月亮按相位取图集子区域。
3. **龙宫恒为晴天外观** —— 客户端直接屏蔽云、雨雪与雨声，天空不因 `isRaining()` / `isThundering()` 改变。
4. **保留原版雾** —— 地形雾、天空雾、水中雾均按原版处理，**不做禁雾**。
5. **兼容 Iris** —— 不使用自研着色器管线，全部走标准实体渲染管线。

## 二、总体架构

### 2.1 挂载方式：`DimensionSpecialEffects`，不使用 mixin

对应参考模组 NeoForgeSkyboxes 用 Mixin 注入 `LevelRenderer.renderSky`，本模组改用**原版提供的扩展点**：

`dimension_type/loong_palace.json` 声明 `"effects": "beloong:loong_palace"`，
客户端 `BeLoongCoreClient` 用 `RegisterDimensionSpecialEffectsEvent` 以同名 `ResourceLocation` 注册实例。

**契约（两处必须一致）：**

| 位置 | 值 |
|---|---|
| `data/beloong/dimension_type/loong_palace.json` → `effects` | `"beloong:loong_palace"` |
| `BeLoongCoreClient.registerDimensionEffects()` | `ResourceLocation.fromNamespaceAndPath(MODID, "loong_palace")` |

**已验证：`beloong.mixins.json` 中不存在任何** `LevelRenderer` / `DimensionSpecialEffects` /
`FogRenderer` / `WeatherRenderer` **注入** —— 天空渲染完全无 mixin。

### 2.2 类与职责

| 类 | 行数 | 职责 |
|---|---|---|
| `client/sky/LoongPalaceSkyEffects` | 85 | 挂载点。`DimensionSpecialEffects.OverworldEffects` 子类；天空门控、调用两个渲染器、屏蔽云与天气 |
| `client/sky/DramaticSkyRenderer` | 255 | 九层天空盒。图层表、alpha 状态机、fade 计算、逐层旋转与混合 |
| `client/sky/CubeAtlasSkyRenderer` | 142 | 六面图集天空盒的几何与提交（含静态缓冲缓存） |
| `client/sky/SkyDecorationsRenderer` | 149 | 太阳与月亮本体（含静态缓冲缓存） |
| `client/sky/SkyRotation` | 98 | 旋转配置与 `PoseStack` 施加 |
| `client/sky/SkyBlendMode` | 60 | 混合模式（ALPHA / ADD / SCREEN） |
| `client/sky/SkyLayerConfig` | 17 | 图层配置 record |
| `client/sky/SkyAlphaSource` | 11 | alpha 来源枚举（NIGHT / DAY / SUNSET / SUNRISE） |
| `client/LoongPalaceSkyTickHandler` | 47 | 客户端 tick：状态重置与 alpha 趋近 |

## 三、渲染管线

### 3.1 调用链

```
LevelRenderer.renderSky(frustumMatrix, projectionMatrix, partialTick, camera, isFoggy, skyFogSetup)
  └─ level.effects().renderSky(...)                       ← DimensionSpecialEffects 扩展点
       └─ LoongPalaceSkyEffects.renderSky(...)
            ├─ shouldRenderSky(camera)                    ← 门控
            │    false → 两个渲染器都不调用
            ├─ DramaticSkyRenderer.render(level, modelViewMatrix, projectionMatrix)     ← 九层天空盒
            └─ SkyDecorationsRenderer.render(level, modelViewMatrix, projectionMatrix)   ← 太阳 + 月亮
       return true                                        ← 跳过原版天空
```

`renderSky` **恒定返回 `true`**（无论是否被门控），从而始终跳过原版天空绘制。

### 3.2 天气与云的屏蔽

`LoongPalaceSkyEffects` 覆写三个方法并**恒定返回 `true`**（原版语义：`true` = 已接管，跳过原版）：

| 方法 | 效果 |
|---|---|
| `renderClouds(...)` | 不绘制云 |
| `renderSnowAndRain(...)` | 不绘制雨雪 |
| `tickRain(...)` | 不播放雨声 / 不生成雨粒子 |

因此天空**不随天气变化**，龙宫恒为晴天外观。

### 3.3 相机门控：`shouldRenderSky(camera)`

以下情况**不绘制**自定义天空（但仍然 `return true`，因此也不会退回原版天空）：

- `camera.getFluidInCamera()` 为 `WATER` / `LAVA` / `POWDER_SNOW`
- 相机实体是 `LivingEntity` 且带有 `BLINDNESS` 或 `DARKNESS` 效果

## 五、Alpha 模型与过渡

### 5.1 单一显示 alpha（不做双因子相乘）

每个图层维护一个**显示中的 alpha**（`DISPLAY_ALPHAS[i]`），目标值由时间函数给出，显示值**逐渐趋近**目标：

```java
DISPLAY_ALPHAS[i] = moveTowards(DISPLAY_ALPHAS[i], alphaFor(source, dayTime), duration);
```

> **这是刻意的设计决策。** 早期曾尝试 `fadeAlpha × conditionAlpha` 的双因子模型，结果出现
> 「新图层慢慢淡入、旧图层立刻消失」的硬切：当旧图层的 `fadeAlpha` 跳变为 0 时，
> `alpha = 0 × conditionAlpha = 0` 会把它瞬间清零。现行实现取消该做法，只用单一显示 alpha 趋近目标。

### 5.2 状态机

| 字段 | 作用 |
|---|---|
| `DISPLAY_ALPHAS[]` | 每层当前显示 alpha（`float[9]`） |
| `initialized` | 是否已初始化；`false` 时直接把显示值设为目标值（不做过渡） |
| `lastDayTime` | 上一 tick 的时间，用于跳变检测 |
| `unexpectedTransitionActive` | 长过渡进行中标志 |

- `tick(level)` 每客户端 tick 调用一次（仅当位于龙宫），更新 `DISPLAY_ALPHAS`。
- `duration`：正常过渡 `20` tick；检测到意外时间跳变时 `200` tick。
- 跳变判定 `isUnexpectedTimeJump(dayTime)`：用**循环时间差**加阈值 `TIME_JUMP_THRESHOLD_TICKS = 50`，
  避免把客户端时间同步与正常跨天误判为跳变（判据须 `delta > 50 && delta < 24000 - 50`）。
- `reset()` 在**进入**龙宫时调用（由 `LoongPalaceSkyTickHandler` 判定 `isLoong && !wasInLoongPalace`），
  清空四个字段，避免上一世界/维度残留。

### 5.3 fade 区间（**支持跨天回绕**）

`fadeAlpha(dayTime, startFadeIn, endFadeIn, startFadeOut, endFadeOut)` 参考 NeoForgeSkyboxes 的
`Utils.calculateFadeAlphaValue` 循环区间算法：

- `inInterval(time, start, end)`：`start <= end` 时用普通区间；否则视为**环绕区间**（`time >= start || time <= end`）
- `cyclicDistance(start, end) = (end - start + 24000) % 24000`
- 命中「淡入」区间返回 `cyclicDistance(startFadeIn, time) / duration`；命中「淡出」返回其补值

**区间常量（`DramaticSkyRenderer`，单位 tick，0..23999）：**

| alpha 来源 | 淡入 | 淡出 |
|---|---|---|
| NIGHT | 13333 → 13666 | 22333 → 22666 |
| DAY | 23666 → 333（**环绕**）| 11666 → 12333 |
| SUNSET | 11666 → 12333 | 13333 → 13666 |
| SUNRISE | 22333 → 22666 | 23666 → 333（**环绕**）|

> DAY 与 SUNRISE 的淡入区间跨过 0 点（`start > end`），由 `inInterval` 的环绕分支正确处理。

## 六、旋转

### 6.1 `SkyRotation` 的 13 个参数

`rotationSpeed{X,Y,Z}` / `timeShift{X,Y,Z}` / `skyboxRotation` / `axis{X,Y,Z}` / `static{X,Y,Z}`。

### 6.2 五个预设（**实际取值**）

| 预设 | 参数 | 用于 |
|---|---|---|
| `STAR_ROTATION` | speed `(0,0,1)`，其余全 0，`skyboxRotation=false` | 第 0、1 层 |
| `DAY_ROTATION` | speed `(0,1,0)`，`skyboxRotation=true` | 第 2、3、4 层 |
| `SUN_ROTATION` | **与 `DAY_ROTATION` 完全相同** | 第 5、6 层 |
| `FLARE_ROTATION` | **与 `STAR_ROTATION` 完全相同** | 第 7、8 层 |
| `DECORATION_ROTATION` | **与 `STAR_ROTATION` 完全相同** | 太阳/月亮本体 |

> ⚠ **五个预设实际只有两组不同取值**（`{STAR, FLARE, DECORATION}` 与 `{DAY, SUN}`）。
> 保留五个名字是出于可读性与后续分化考虑，属**已知冗余**，见第十二节。

### 6.3 `apply(poseStack, level)` 的施加顺序

共 **12 次** `mulPose`，顺序为：

1. 轴旋转：`XP(axisX)` → `YP(axisY)` → `ZP(axisZ)`
2. 时间旋转：`XP(timeX)` → `YP(timeY)` → `ZP(timeZ)`
3. 轴旋转**逆序**：`ZN(axisZ)` → `YN(axisY)` → `XN(axisX)`
4. 静态旋转：`XP(staticX)` → `YP(staticY)` → `ZP(staticZ)`

第 1、3 步构成「绕任意轴旋转」的夹逼（把时间旋转放到该轴坐标系内施加）。

### 6.4 时间旋转计算

```java
if (speed == 0.0F) return 0.0F;
long timeOfDay = level.getDayTime() + timeShift;
double fraction = timeOfDay / (24000.0 / speed);
double skyAngle = Mth.frac(fraction);
return skyboxRotation
    ? (float) (360.0 * skyAngle)                      // 匀速自转
    : 360.0F * level.dimensionType().timeOfDay((long) (24000 * skyAngle));   // 跟随原版昼夜曲线
```

## 七、混合模式

`SkyBlendMode` 三个值的 `apply(alpha)` 语义（每个都**显式设置加法混合方程**，
避免其他模组残留的 blend equation 影响天空）：

| 模式 | `blendFuncSeparate(src, dst, srcA, dstA)` | `setShaderColor` | 说明 |
|---|---|---|---|
| `ALPHA` | `SRC_ALPHA, ONE_MINUS_SRC_ALPHA, ONE, ONE_MINUS_SRC_ALPHA` | `(1,1,1,alpha)` | 标准 alpha 混合；alpha 放在 A 通道 |
| `ADD` | `SRC_ALPHA, ONE, ONE, ONE` | `(1,1,1,alpha)` | 加法混合 |
| `SCREEN` | `ONE, ONE_MINUS_SRC_COLOR, ONE, ONE_MINUS_SRC_ALPHA` | **`(alpha,alpha,alpha,1)`** | screen：`result = src + dst − src·dst` |

> **SCREEN 的 alpha 必须缩放到 RGB**（而非 A 通道），否则该层不会随 alpha 淡出——这是早期实际踩到的坑，
> 已由源码注释记录。ALPHA 与 SCREEN 覆盖了当前全部 9 层。
>
> ⚠ `ADD` **当前未被任何图层使用**，属已知冗余，见第十二节。

## 八、几何缓存（几何提交方式）

**2026-09-11 引入。** 这是本模组与参考模组在该子系统上唯一的架构性差异。

### 8.1 缓存结构

| 对象 | 数量 | 说明 |
|---|---|---|
| `CubeAtlasSkyRenderer.skyBuffer` | **1** | 九层天空盒**共用**。顶点只依赖静态 `FACES` 表与字面量 UV，与贴图/旋转/混合/维度/时间全部无关 |
| `SkyDecorationsRenderer.sunBuffer` | 1 | 太阳 4 顶点，UV 恒定 |
| `SkyDecorationsRenderer.MOON_BUFFERS` | 8 | 月亮按相位（`moon_phases.png` 为 4×2 图集）各一个 |

- 全部为 `VertexBuffer.Usage.STATIC`（`GL_STATIC_DRAW`），**懒建于首次渲染**。
- 显存增量合计 **约 1.4 KB**（天空盒 552 B + 太阳 92 B + 月亮 8×92 B），另加 10 个 buffer 对象与 10 个 VAO 句柄。
- 提交序列照原版 `LevelRenderer` 绘制 `skyBuffer` / `starBuffer` 的三段式：
  `bind()` → `drawWithShader(modelView, projection, RenderSystem.getShader())` → `unbind()`

### 8.2 两条实现纪律（不可违反）

> **纪律 A：构建缓存时必须使用不带矩阵的 `addVertex(x, y, z)` 重载，存局部坐标。**
> 若沿用 `addVertex(matrix4f, …)` 把已变换的顶点写入缓冲，旋转会被**冻结在首次上传时的角度**，
> 表现为「天空不转」。这是本方案唯一的失败模式。

> **纪律 B：矩阵只在绘制时经 `drawWithShader(poseStack.last().pose(), projectionMatrix, …)` 传入。**
> 用 `RenderSystem.getShader()` 而非自行取 shader，以保证与旧路径（`BufferUploader._drawWithShader` 内部同样
> 取 `RenderSystem.getShader()`）逐位一致。

### 8.3 为什么零视觉变化（可证明）

旧路径把顶点在构建期用 `P = poseStack.last().pose()` 烘入，而 shader 收到的是**全局**
`RenderSystem.getModelViewMatrix()`；缓存路径把 `P` 作为 uniform 传入。

**全 jar 扫描 6316 个 `.java` 条目：`setModelViewMatrix` 调用点为 0** ⇒
`RenderSystem.modelViewMatrix` 恒为初始的 `new Matrix4f()`（单位阵）⇒ 两者结果严格相等（`P × v`）。

原版 `LevelRenderer` 绘制 `skyBuffer` 时同样显式传 `posestack.last().pose()`（见 `neoforge-*‑sources.jar`）。

### 8.4 生命周期：**无失效面**

缓存内容不依赖贴图对象、资源包、维度、世界时间、alpha 状态，因此：

| 事件 | 处理 |
|---|---|
| 首次渲染 | 懒建（渲染线程）|
| 资源重载 `F3+T` | **不重建**（原版 `LevelRenderer` 对 `skyBuffer`/`starBuffer` 同样不重建）|
| 进入 / 离开龙宫 | **不重建**——`DramaticSkyRenderer.reset()` 只清 alpha 与时间状态 |
| 维度切换 | **不重建** |
| 客户端退出 | **不做显式清理**，由 GL 上下文销毁回收（依原版先例：`LevelRenderer.close()` 只关后处理链）|
| 缓冲 `isInvalid()` | `ensure*` 内检查并重建（防御性，正常不触发）|

> **禁止**在 `DramaticSkyRenderer.reset()` 中加入丢弃缓冲的钩子——那会把唯一的重建/泄漏入口引进来，收益为零。

### 8.5 线程约束

`new VertexBuffer(Usage)`、`VertexBuffer.upload(MeshData)`、`RenderSystem.glDeleteBuffers(int)`
均带 `RenderSystem.assertOnRenderThread()` 硬断言 ⇒ 创建 / 上传 / 关闭**必须在渲染线程**。
`VertexBuffer.upload` 内部会自行关闭传入的 `MeshData`，**不需也不应额外 close**。

### 9.4 图集来源与规格

**来源**：OptiFine 资源包 **Dramatic Skys**。初期参考实现为 `FlashyReese/nuit`（`1.20.x/stable` 分支），
旋转 / 混合 / 日月装饰部分参考 NeoForgeSkyboxes。

核心天空图集为 **3072×2048** 的 3×2 六面图集，布局：

```
┌──────────┬──────────┬──────────┐
│ Bottom   │ Top      │ South    │   v ∈ [0, 0.5]
├──────────┼──────────┼──────────┤
│ West     │ North    │ East     │   v ∈ [0.5, 1]
└──────────┴──────────┴──────────┘
  u∈[0,1/3]  u∈[1/3,2/3]  u∈[2/3,1]
```

**各面 UV 子区域（权威表，来自 Dramatic Skys 的 Celestial `objects/*.json`）：**

| 面 | u 区间 | v 区间 |
|---|---|---|
| Bottom | `[0, 1/3]` | `[0, 0.5]` |
| Top | `[1/3, 2/3]` | `[0, 0.5]` |
| South | `[2/3, 1]` | `[0, 0.5]` |
| West | `[0, 1/3]` | `[0.5, 1]` |
| North | `[1/3, 2/3]` | `[0.5, 1]` |
| East | `[2/3, 1]` | `[0.5, 1]` |

> ✅ **已逐面核对**：`CubeAtlasSkyRenderer.FACES` 的 24 顶点 UV 与上表**完全一致**。
> 注意 `FACES` 的**数组顺序**是 `West, South, East, North, Top, Bottom`（按代码注释），
> 与图集的行列布局不同——顺序无关正确性，UV 才是决定因素。

### 9.5 贴图清单与显存

Minecraft 的 `NativeImage` 解码后一律为 **RGBA8**（4 字节/像素），
故实际显存**与 PNG 压缩体积无关**，只取决于像素尺寸。
下表按「宽 × 高 × 4 字节、不含 mipmap」计算（`SimpleTexture` 默认不生成 mipmap）：

| 资源 | 像素 | PNG 类型 | PNG 体积 | **显存** | 用途 |
|---|---|---|---|---|---|
| `textures/skybox/day.png` | 3072×2048 | RGB | 3458 KB | **24.00 MB** | 图层 3 |
| `textures/skybox/night.png` | 3072×2048 | RGB | 1333 KB | **24.00 MB** | 图层 4 |
| `textures/skybox/stars.png` | 3072×2048 | RGB | 289 KB | **24.00 MB** | 图层 0 |
| `textures/skybox/mask.png` | 3072×2048 | **Palette** | 344 KB | **24.00 MB** | 图层 2 |
| `textures/skybox/mask_moon.png` | 3072×2048 | RGBA | **31 KB** | **24.00 MB** | 图层 1 |
| `textures/skybox/sun.png` | 3072×2048 | RGB | 2010 KB | **24.00 MB** | 图层 5、6 |
| `textures/skybox/sunflare.png` | 1536×1024 | RGB | 21 KB | 6.00 MB | 图层 7、8 |
| `textures/environment/moon_phases.png` | **4000×2000** | **16-bit** RGB | 4316 KB | **30.52 MB** | 月亮本体（4×2 相位）|
| `textures/environment/sun.png` | 256×256 | RGBA | 22 KB | 0.25 MB | 太阳本体 |
| | | | **≈ 13.5 MB** | **≈ 180.8 MB** | |

> ⚠ **这是本子系统最大的一项资源开销，且此前从未被评估。**
> 几点值得注意：
> - **PNG 体积与显存完全脱钩**：`mask.png` 344 KB → 24 MB；`mask_moon.png` **31 KB → 24 MB**，
>   后者几乎是全透明图，24 MB 基本是浪费。
> - `moon_phases.png` 是 **16-bit** 色深，对月亮贴图没有意义；且 4000×2000 远超实际需要
>   （原版 `moon_phases.png` 仅 128×64）。
> - 6 张 3072×2048 的图集各自独立上传（不参与方块图集拼接），无法被 MC 的图集机制共享。
> - 若启用 mipmap，总量将再放大约 1/3（约 241 MB）。
>
> 该问题已列入第十二节的待处理项，并被列为配套代码审查的**第一优先批次**。

## 十、性能实测（2026-09-11）

采样：客户端 profiler，Render thread 独占，采样间隔 4 ms。

| 指标 | 优化前（`profile-…20.15.51`，373.44 s）| 优化后（`profile-…20.53.27`，530.42 s）|
|---|---|---|
| `LoongPalaceSkyEffects.renderSky` | 11.04 s = **2.955%** | 10.30 s = **1.942%** |
| `CubeAtlasSkyRenderer.render` | 6.83 s = 1.828% | 6.82 s = 1.286% |
| `SkyDecorationsRenderer.render` | 2.74 s = 0.734% | 1.79 s = 0.337% |

**会话时长与操作不同，绝对秒数不可直接相减。** 用不受时长影响的判据：

- **结构性差分（决定性）**：旧路径的 `BufferUploader.drawWithShader` / `BufferUploader.upload`（2× `glBufferData`）
  / `bindImmediateBuffer` / `Tesselator.begin` 在两个渲染类的子树下**已完全消失**，改为直连自有缓存缓冲。
- **内部构成比**：被消除部分原占 `CubeAtlasSkyRenderer` 的 45.9%、`SkyDecorationsRenderer` 的 33.0%、
  合计占天空自身开销的 **36.6%**；现为 0。
- **推算**：`2.955% × (1 − 0.366) = 1.874%`，实测 **1.942%**，差 0.07 个百分点。
- **缓冲只建一次**：`ensureSunBuffer` 全程仅 4 ms（仅一次 `isInvalid` 检查的采样），无每帧 `new` 迹象。
- **反向判据**：`VertexBuffer.drawWithShader` 在天空下仍存在且量级可观（5.44 + 0.62 + 0.53 s），绘制未被跳过。

**仍未测**：跨会话可比的 FPS 提升幅度（需固定操作与时长重测，见第十四节）。

## 十一、设计决策记录

| # | 决策 | 依据 |
|---|---|---|
| 1 | 用 `DimensionSpecialEffects` 挂载，**不使用 mixin** | 原版扩展点足够；避免 mixin 维护成本 |
| 2 | **不依赖原版 `LevelRenderer.starBuffer`**，星空由 `stars.png` 图层处理 | Dramatic Skys 的高分辨率星野观感要求；原版是程序生成点云，观感不同 |
| 3 | 天空盒用**固定 24 顶点 UV 表**而非「基础 quad + 每面旋转」 | 避免图集切分后旋转/翻转产生的接缝 |
| 4 | **单一显示 alpha + `moveTowards`**，不用 `fadeAlpha × conditionAlpha` 双因子 | 双因子会在旧图层 `fadeAlpha` 归零时瞬间清零，产生硬切 |
| 5 | 混合用 `blendFuncSeparate`，每个模式显式设 `GL_FUNC_ADD` | 防止其他模组残留的 blend equation 影响天空 |
| 6 | SCREEN 模式把 alpha 缩放到 **RGB** 而非 A | 否则 screen 层不随 alpha 淡出（实测踩坑）|
| 7 | **保留原版雾**，不做禁雾 | 地形/天空/水中雾按原版处理，观感更自然 |
| 8 | 天气与云在**客户端**直接屏蔽（三方法返回 `true`）| 龙宫定位为恒晴。⚠ **此策略曾发生反转**——早期设计文档明确写「不再禁用原版天气 / 不添加任何天气抑制代码」，现行实现相反，详见 §13 |
| 9 | **几何缓存为静态 `VertexBuffer`**（2026-09-11）| 消除每帧重建 `MeshData` 与 2× `glBufferData`；与原版 `LevelRenderer` 同法 |
| 10 | 几何缓存**不做 shutdown 清理**、**不加重置钩子** | 依原版先例；缓存无失效面，清理反而引入泄漏风险 |
| 11 | **天灾维度不使用自定义天空**（`effects: minecraft:overworld`）| 与其「第二个主世界」定位一致 |
| 12 | **`has_skylight: true` 保留**，不移除天空光照 | 方块需正常受自然天空光；龙宫为开放维度（`has_ceiling: false`）。这是自第一阶段起就被明确记录的决策 |

  服务端 profile 不含任何渲染栈帧，无法用于本子系统。
