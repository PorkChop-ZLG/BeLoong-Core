## 一、设计目标

### 1.1 叙事定位：整合包主城与序章舞台

龙宫是「化龍」整合包的**主城**：一张固定的地图存档，悬浮于九天之上，统御龙星上的龙族。
整合包的序章完全发生在龙宫，玩家的第一次出生点就在龙宫中央平台。

| 序章流程（整合包侧） | 依赖龙宫提供的什么 |
|---|---|
| 出生在龙宫中央大平台 | **固定出生维度与坐标**（LockDown `login_spawn_target`） |
| 由 NPC「末」引导进入前殿 | **固定地图**（地图模板，非程序生成） |
| 见九条主龙的雕像 | 建筑与 NPC，由整合包负责 |
| 前往化龙池、跳入池水选择龙种 | **化龙池水机制**（本模组，§10.1） |
| 学会飞行、飞到前殿二楼 | **天空与虚空地形**（无地面，必须飞行） |
| 学习饮食 / 技能 / 加点 / 成长 / 诅咒 | 主城作为安全教学场 |
| 引出主线「寻找应龙」 | 主城作为任务总线 |

> 依据：`docs/【化龙】整合包任务流程设计思路.md`（序章）与 `run/config/lockdown.toml`
> 的 `pinned_dimensions` / `login_spawn_target`。**本模组不实现** NPC、剧情、商店、小游戏。

### 1.2 三条设计约束

本文后续所有机制都由下面三条约束推导而来。任何与它们冲突的既有设计都应视为需要修正。

**约束 1 —— 绝对安全区：龙宫全境不允许发生任何非预期的世界改变。**

主城承载整合包的固定地图与 NPC，一旦被破坏或被怪物干扰，整个序章就废了。这条约束在三层落实：

| 层 | 手段 | 位置 |
|---|---|---|
| 维度层 | 维度类型硬禁自然刷怪 + 生物群系 spawners 全空 | §2.1、§2.2 |
| 玩家层 | 12 道环境保护门（方块破坏/放置/交互/工具/耕地/作物/地物/传送门/爆炸…） | §8 |
| 区块认领层 | 龙宫维度**禁止** FTB Chunks 认领，防止玩家用认领绕过保护 | §8.2 |

**约束 2 —— 进出通道收口：所有跨维度传送必须走 `teleport` 包，共用同一份冷却。**

龙宫是主城，进出必须可预期。三种入口（门 / 技能 / 坠虚空兜底）与一种出口（回主世界）
全部由 `teleport` 包解析落点，并共用同一份 NBT 冷却（60 tick）。唯一例外是坠虚空兜底
（它是抢救机制，见 §5.3 与决策 6）。

**约束 3 —— 观感必须与主世界不同：龙宫不是"另一个主世界"，而是"九天之上的宫阙"。**

主世界已有天灾维度作为"第二个主世界"（见《天灾维度总设计》）。龙宫必须在第一眼就被认出不同：

- **纯虚空地形**（无地表、无地物、无矿）——本模组不在龙宫生成任何东西，地形与建筑全部来自整合包预建地图（§2.2）；
- **九层自定义天空**，永昼晴天，屏蔽云与雨雪（§9）；
- 所有落点都**没有地面可站**，玩家必须靠飞行——这与序章「学习飞行」的教学目标一致。

### 1.3 职责边界

| 归属 | 内容 |
|---|---|
| **本模组（BeLoong-Core）** | 维度定义与维度类型、进出通道（门/技能/兜底）、传送 API 与冷却、环境保护、化龙池水、传送石碑、天空与氛围渲染、地图模板迁移机制 |
| **整合包** | 龙宫的建筑与地形（地图模板内容）、NPC 与对话、任务线与剧情、商店与小游戏、九龙雕像、化龙池的**水体摆放**（区域数据由本模组提供，池子本身是建筑） |
| **依赖模组** | Dragon Survival（龙状态判定、化龙祭坛 GUI、飞行等级）、Waystones（传送石碑的方块与数据）、FTB Chunks（绕过权限判定）、LockDown（模板维度固定与出生点） |

> 这是**整合包与模板内容的一致性**问题，不是本模组的缺陷。

## 二、维度定义与契约

### 2.1 `data/beloong/dimension_type/loong_palace.json`

当前文件内容（逐字段）：

| 字段 | 值 | 含义与设计意图 |
|---|---|---|
| `ultrawarm` | `false` | 非下界类维度：水不会蒸发 |
| `natural` | `true` | 有昼夜与时间推进。**这是统一冷却用 `getGameTime()` 作时间基准成立的前提**（见 §7.2） |
| `coordinate_scale` | `1.0` | 与主世界 1:1，不做下界式 1:8 压缩 |
| `has_skylight` | `true` | 有天空光 |
| `has_ceiling` | `false` | 无天花板，天空可见 |
| `ambient_light` | `0.0` | 无环境光。**虚空区域因此全黑**，观感靠天空系统而非光照 |
| `monster_spawn_light_level` | `0` | **约束 1 的维度层落实**：怪物生成的光照上限为 0 ⇒ 只有"总亮度恰好为 0"的位置才可能刷怪（见下方语义说明） |
| `monster_spawn_block_light_limit` | `0` | 方块光超过 0 即拒绝（`0 < 15` 所以这条判定生效） |
| `piglin_safe` | `false` | 猪灵照常僵尸化 |
| `bed_works` | `true` | 床可用（主城需要） |
| `respawn_anchor_works` | `false` | 重生锚不可用 |
| `has_raids` | `true` | 允许袭击 |
| `logical_height` / `min_y` / `height` | `384` / `-64` / `384` | 与主世界同量程：可建筑区间 `y ∈ [-64, 319]` |
| `infiniburn` | `#minecraft:infiniburn_overworld` | 沿用主世界不可燃标签 |
| `effects` | `beloong:loong_palace` | **天空系统的挂载点**：指向客户端注册的 `LoongPalaceSkyEffects`（§9） |

> **云与雨雪的屏蔽方式（容易读反，务必注意）**：`DimensionSpecialEffects` 的
> `renderClouds` / `renderSnowAndRain` / `tickRain` 三个方法的返回值语义是
> **`true` = 已处理（跳过默认渲染）**。`LoongPalaceSkyEffects` 三者都 `return true`
> ⇒ **云、雨雪、雨声全部不画**，龙宫永远呈现晴天。这与"返回 true 表示画了云"正好相反。

> ⚠️ **`ambient_light: 0.0` 与 `min_y: -64` 的组合含义**：虚空列在 `y < 64` 处是**全黑的空气**。
> 玩家一旦掉下去，视觉上完全看不到落点——这正是 §5.3 坠虚空兜底传送存在的理由。

#### 两个刷怪字段的真实语义（已核对原版源码）

出处：`Monster#isDarkEnoughToSpawn`（`neoforge-21.1.236-sources.jar`）。原版判定是**三段**：

```java
if (level.getBrightness(LightLayer.SKY, pos) > random.nextInt(32)) return false;   // ① 天光
int i = dimensiontype.monsterSpawnBlockLightLimit();
if (i < 15 && level.getBrightness(LightLayer.BLOCK, pos) > i) return false;        // ② 方块光
int j = level.isThundering() ? level.getMaxLocalRawBrightness(pos, 10)
                             : level.getMaxLocalRawBrightness(pos);
return j <= dimensiontype.monsterSpawnLightTest().sample(random);                  // ③ 总亮度
```

龙宫的取值落在第 ③ 段：`monsterSpawnLightTest` 是 `IntProvider` 常量 `0` ⇒ 条件变为
**`总亮度 ≤ 0`，即只有当总亮度恰好为 0 时才允许刷怪**。

这不是"光照阈值调低"，而是**把允许区间压到单点 0**。又因为 `ambient_light: 0.0`，
龙宫的虚空列总亮度恒为 0——所以真正兜底的是**群系 spawners 全空**（§2.2）：

| 层 | 手段 | 效果 |
|---|---|---|
| 维度类型 | 总亮度必须为 0 | 任何有光照的位置都不刷怪 |
| 群系 spawners | 八类全部 `[]` | **龙宫没有任何可生成的生物条目**——这是"不刷怪"的决定性一层 |

> 这说明约束 1 的第一层实际是"维度类型 + 群系"两层，**缺一不可**：只改维度类型
> （比如把光照放宽）会立刻开始刷怪，因为维度类型并不限制"生成什么"。


### 2.2 `data/beloong/dimension/loong_palace.json`

```json
{
  "type": "beloong:loong_palace",
  "generator": {
    "type": "minecraft:flat",
    "settings": {
      "layers": [], "biome": "beloong:loong_palace",
      "lakes": false, "features": false, "structure_overrides": []
    }
  }
}
```

- 生成器是**原版超平坦，且 layers 为空** ⇒ 不放置任何地层方块；`lakes` / `features` /
  `structure_overrides` 全关 ⇒ 不生成湖泊、地物、结构。
- **直接后果**：龙宫的落点**不可能**靠高度图求得（除整合包预建地图自带的方块外全是虚空），
  因此所有「进入龙宫」的落点都必须显式给 Y —— 这就是 `fallbackY` 存在的原因（§7.1）。

> ⚠️ **本群系不生成任何地物**：`features` 为**空数组**。龙宫的地形与建筑**全部**来自整合包
> 用 LockDown 加载的预建地图存档（§1.3、§9.3），本模组只定义维度、群系与环境。
> 该数组曾挂着原版 `minecraft:void_start_platform`，已作为纯数据包修改移除（§15 变更记录）。

## 三、进出总图

**这是龙宫最容易看漏的部分**——入口有三条、出口一条，判定分散在四个类里。

### 3.1 总表

| # | 方向 | 触发 | 判定（按顺序） | 落点 | 冷却 | 失败行为 |
|---|---|---|---|---|---|---|
| A | 任意 → 龙宫 | **走进龙宫门** | ① 是玩家 ② 是龙 ③ 当前维度 ∈ {主世界, 龙宫} ④ 不在冷却中 | `At(配置 targetX, ?, targetZ)` fallback `fallbackY` | 检查+写（60t） | actionbar 提示，不传送 |
| B | 龙宫 → 主世界 | **走进龙宫门** | 同 A 的 ①②③④ | `Spawn(主世界)` → **出生点周围扩散** | 检查+写（60t） | actionbar 提示 |
| C | 主世界 ⇄ 龙宫 | **龙之生存技能** `beloong:tp_loong_palace` | ① 目标是玩家 ② 不在冷却中 ③ 当前维度 ∈ {主世界, 龙宫} | 同 A / 同 B | 检查+写（60t） | 冷却中→actionbar；维度缺失→系统消息 |
| D | 龙宫 → 主世界 | **Y < 0 兜底**（每 `checkIntervalTicks` 查一次） | ① 是存活的服务端玩家 ② 当前维度是龙宫 ③ `Y < 0` | `Spawn(主世界)` → 同上 | **特例：既不检查也不写** | 无（静默抢救） |
| E | 任意 → 龙宫 | **首次进入存档** | LockDown 的 `login_spawn_target` 配置 | 硬编码 `beloong:loong_palace;0.5;64.0;0.5;180.0;0.0` | 无（整合包侧） | 无 |
| F | 龙宫 → 主世界 | **死亡后无个人重生点** | 原版重生逻辑 | 原版规则（**不经过本模组 API**） | 无 | 无 |

> **E 与 F 是整合包/原版路径，不在本模组的传送收口范围内**，列出仅为让"进出"这件事完整。
> E 的坐标来自 `run/config/lockdown.toml`，**不是**本模组的 `targetX/targetZ/fallbackY`（默认 `0.5 / 0.5 / 65.0`）。
> **两套 Y 值不同是刻意行为，不需要统一**：本模组用 `y = 65` 作为**落点高度**，
> 目的是**防止玩家卡在地下**；LockDown 的 `64.0` 服务于另一条路径。理由见决策 9。

### 3.2 方向判定

```java
// LoongPalacePortalBlock#getPortalDestination（门）
boolean fromLoongPalace = TeleportTarget.LOONG_PALACE_LEVEL.equals(level.dimension());
// 龙宫 → 主世界 Spawn；否则 → 龙宫 At

// TpLoongPalaceEffect#apply（技能）
if (Level.OVERWORLD.equals(currentDim))        → 龙宫 At
else if (LOONG_PALACE_LEVEL.equals(currentDim)) → 主世界 Spawn
else                                            → 直接返回（不放行）
```

**两处判据不同且都成立**：门用"是不是龙宫"二分（允许集合只有主世界与龙宫两个维度），
技能用"是不是主世界 / 是不是龙宫"三分（第三分支拒绝）。
技能的第三分支由数据包的 `usage_blocked` 先挡，代码里再兜一层（**不放行**）。

### 3.3 允许集合只有两个维度

```java
// LoongPalacePortalBlock#isAllowedDimension —— 唯一的"允许集合"判据
static boolean isAllowedDimension(ResourceKey<Level> dimension) {
    return Level.OVERWORLD.equals(dimension) || TeleportTarget.LOONG_PALACE_LEVEL.equals(dimension);
}
```

激活器（§4.2）与门方块（§4.3）**共用**这一个方法，构成两层维度闸。
**下界/末地/天灾里的水都点不亮龙宫门**；即使用指令把门方块放进其他维度，进门也会被拒绝。

## 四、入口 A/B：龙宫门（荧石框架 + 框内注水）

### 4.1 形状与方块清单

| 项 | 值 | 来源 |
|---|---|---|
| 框架判定 | **方块 tag** `#beloong:loong_palace_portal_frame`，默认只含 `minecraft:glowstone` | `registry/ModBlockTags.java`、`data/beloong/tags/block/loong_palace_portal_frame.json` |
| 框内"空"的判定 | **空气 ∨ 水 ∨ 本门方块** | `LoongPalacePortalShape#isEmpty` |
| 尺寸 | 宽 2–21、高 3–21（沿用原版下界门约定） | `LoongPalacePortalShape` 常量 |
| 展开方向 | X 轴门朝 `WEST` 展开、Z 轴朝 `SOUTH`（与天境一致） | `LoongPalacePortalShape` 构造器 |
| 门方块 | `beloong:loong_palace_portal`，属性 `axis`（水平轴） | `LoongPalacePortalBlock`、`registry/ModBlocks.java:114` |
| 物品 | `beloong:loong_palace_portal`（BlockItem），进创造模式页签 | `item/ModItems.java:149`、`item/ModCreativeModeTabs.java:55` |

**`updateShape` 的自我销毁判据**（照抄天境）——只有三者**同时**成立才熄灭：

```java
!crossAxisHorizontal && !facingState.is(this) && !new LoongPalacePortalShape(...).isComplete()
```

前两个条件是短路：门方块之间的水平传递、与同轴邻块的更新，都不做昂贵的形状重算。

### 4.2 激活流程

**走方块事件，不走 tick 轮询。**

| 步骤 | 实现 |
|---|---|
| 事件 | `BlockEvent.NeighborNotifyEvent`（水的进入必然伴随邻居更新，**方块驱动、零开销**） |
| 第一层维度闸 | `isAllowedDimension(level.dimension())`（§3.3） |
| 水的判定 | `level.getFluidState(pos).is(FluidTags.WATER)` —— **任意水，含流动水**；只认水源方块会漏掉大部分情形 |
| 找形状 | `LoongPalacePortalShape.findEmpty(level, pos, Direction.Axis.X)`，内含"换另一水平轴再试" |
| 点亮 | `shape.createPortalBlocks()`：把框内每格替换为门方块，flags = `2 \| 16`（发包、**不触发邻居更新**，避免更新风暴） |
| 音效 | `LOONG_PALACE_PORTAL_TRIGGER`，音量 **0.25** |
| 日志 | `LOGGER.debug("loong palace portal lit at {} in {}")` |

> **刻意不取消该邻居事件**（天境会 `setCanceled(true)`）：取消会吞掉这次方块更新，
> 而原版水与荧石的后续结算依赖邻居更新。

### 4.3 三条失败门与玩家提示

失败判定分散在**两处**，理由是节流位置：

| 位置 | 作用 | 为什么在这里 |
|---|---|---|
| `entityInside`（每 tick） | **预检**：给玩家一个说法，但**不阻断登记** | 这里有节流；放在 `getPortalDestination` 会每 tick 反复触发 |
| `getPortalDestination`（PortalProcessor 回调） | **真正的闸**：判定后返回 `null` 即不传送 | 是唯一能阻止传送的位置 |

| 失败 | 触发条件 | 消息键 | 日志级别 |
|---|---|---|---|
| `NON_DRAGON` | `DragonStateProvider.isDragon(player)` 为假 | `message.beloong.loong_palace_portal.not_a_dragon` | DEBUG（设计内拒绝） |
| `WRONG_DIMENSION` | 当前维度不在允许集合 | `message.beloong.loong_palace_portal.wrong_dimension` | DEBUG（设计内拒绝） |

1. **actionbar，不进聊天框**（`displayClientMessage(msg, true)`）——门是"持续接触"的方块，
   不节流会把聊天框刷满；actionbar 会被新消息直接替换；

## 六、出口：龙宫 → 主世界

三条出口路径（门 / 技能 / 坠虚空）**全部**落到 `TeleportTarget.Spawn(主世界)`，语义是
**世界出生点 + 周围扩散**。

### 6.1 `Spawn` 目标的语义

```java
record Spawn(ServerLevel level) {
    BlockPos pos()    { return level.getSharedSpawnPos(); }   // 每次实时读取，不缓存
    double centerX()  { return pos().getX() + 0.5D; }         // XZ 取出生点中心
    double fixedY()   { return pos().getY(); }                // Y 直取出生点自身
}
```

- **XZ** 取出生点中心（`+0.5` 对齐）；
- **Y 刻意不查高度图**——出生点是维度自身的数据，与"那一列现在有什么方块"无关（需求口径）。

### 6.2 扩散实现（`SpawnSpreadResolver`）

仅服务端主线程，复刻原版 `ServerPlayer#adjustSpawnLocation` 的主体：

```
半径 = gamerule spawnRadius（默认 10）→ 被世界边界距离夹一次（贴边时仍给 1 格）
候选数 = (半径*2+1)²  → 共素数步长（count>16 时取 17）→ 随机起点 → 逐个候选判定
判定 = PlayerRespawnLogic 的安全落点逻辑（区块非阻塞探测 + 虚空列排除 + 水面列排除 + 向下找完整碰撞面）
复核 = level.noCollision(player, 碰撞箱)
全部失败 → 返回出生点原样坐标
```

**与原版的四处刻意差异**：

| # | 差异 | 原因 |
|---|---|---|
| 1 | 区块用 `ServerChunkCache#getChunkNow`，**不在内存就跳过该候选** | **主线程绝不阻塞**（本项目 2026-09-12 死锁事故后立下的硬约束） |
| 2 | **忽略游戏模式**（原版冒险模式下整段跳过扩散） | 用户指定 |
| 3 | **忽略天空光判断**（原版要求 `hasSkyLight()`） | 调用方只在主世界用 |
| 4 | 失败**不做"上顶/下踩"**，原样返回出生点坐标 | 用户指定 |

`spawnRadius` 默认 10 ⇒ 候选 441 个。**非玩家实体不扩散**（`DimensionTeleport` 里判 `instanceof ServerPlayer`），
直接落在出生点坐标。

> ⚠️ **为什么不直接用原版**：`PlayerRespawnLogic#getOverworldRespawnPos` 内部用阻塞的
> `level.getChunk`。本项目有明确禁令（见 §7.3），必须自实现。

## 七、传送 API 契约（`teleport` 包）

### 7.1 三种 Target 语义

| 类型 | XZ | Y | 兜底 |
|---|---|---|---|
| `At(level, x, z, fallbackY)` | 原样使用 | **走高度图**（`CoordinateLanding`） | `fallbackY == null` ⇒ 拿不到就不传送；非 null ⇒ 用兜底 |
| `Spawn(level)` | 出生点中心 `+0.5` | **出生点自身的 Y，不查高度图** | 永不失败 |
| `TeleportTarget.toLoongPalace(loongPalace)` | 读配置 `targetX`/`targetZ` | 走高度图 | 读配置 `fallbackY` |

`toLoongPalace` 是包内**唯一读配置**的目标；**龙宫维度 ID 不在配置里**（编译期常量）。

### 7.2 冷却：60 tick 硬编码

```java
public static final String KEY = "beloong_portal_cooldown";   // NBT 键，不得更改
public static final int TICKS = 60;                            // 无配置项
```

| 项 | 说明 |
|---|---|
| 存储 | 玩家持久化 NBT ⇒ **跨维度、跨重登有效** |
| 时间基准 | `player.level().getGameTime()`。跨维度后 `player.level()` 已切到目标维度 |
| 为什么硬编码 | 冷却属结构性内容，不进配置。原 `teleportCooldownTicks` / `cooldownTicks` 配置项已删除 |
| 共用范围 | 天灾门、龙宫门、龙宫技能**共用同一份**；坠虚空兜底是唯一特例（§5.3） |
| 附加动作 | 门方块还需 `refreshVanillaToOutlastNbt`（见下） |

**`refreshVanillaToOutlastNbt` 为什么必需**：原版 `Entity#handlePortal` 在**询问落点之前**就设置了
传送冷却，而 `setAsInsidePortal` 在冷却期内只刷新冷却、不登记 `insidePortalThisTick`。
若不顶住原版冷却（玩家只有 10 tick，因为 `Player#getDimensionChangingDelay` 覆写为 10），
NBT 冷却一到期就会立刻重新登记并重试——**玩家站在门里时会无界重试**，每轮都刷一次日志与提示。
该方法把原版冷却顶到"比 NBT 冷却晚 1 tick 到期"。**仅门方块调用**。

**时间基准的前提（必须维持）**：三个相关维度（主世界、龙宫、天灾）都是 `natural: true` 且由
同一服务端推进，`getGameTime()` 同步递增。**若将来出现 `natural: false` 的维度、或用指令单独
改动某维度时间，冷却时长会出现偏差。**

### 7.3 主线程纪律（硬约束）

```java
// CoordinateLanding 的判定顺序（顺序本身是行为的一部分）
1. 落点区块不在内存 → null（"还没好"，应重试）
2. 坐标越界（|x| 或 |z| ≥ 3000 万）→ null
3. 高度图取 MOTION_BLOCKING（含流体 ⇒ 海洋列得到的是水面，刻意"水面就放水面"）
4. 列为虚空 → null
```

| 禁止 | 原因 |
|---|---|
| `Level#getChunk` / `Level#getHeight`（阻塞版） | 主线程在 `managedBlock` 上等待一个永不完成的生成 future ⇒ **永久静默卡死，无 crash report** |
| 在非主线程调用 | `getChunkNow` 在非主线程恒返回 `null` ⇒ 静默退化为"永远拿不到落点"，表现为传送永不成功而**不报错** |

完整根因与复盘见 `docs/天灾传送门主线程死锁-根因与修复复盘.md`。

区块预热用 `CoordinateLanding#requestChunk`：落点区块不在内存时申领
`TicketType.PORTAL`（半径 0 = 只加载落点所在的那 1 个区块；原版下界门用 3），
**不等待、不 join、不检查返回值**。刷新职责在调用方。

### 7.4 必须走 API 的调用方

| 调用方 | 用的入口 |
|---|---|
| `block/DisasterPortalBlock`（天灾门双向） | `DimensionTeleport.toCurrentCoords` |
| `block/LoongPalacePortalBlock`（龙宫门双向） | `DimensionTeleport.toTarget` |
| `ability/TpLoongPalaceEffect`（技能） | `DimensionTeleport.toTarget` |
| `transport/DimensionTransportHandler`（坠虚空兜底） | `DimensionTeleport.toTarget` |

**新增跨维度传送功能时，必须走本包，禁止自行调用 `Entity#changeDimension` 或
`ServerPlayer#teleportTo` 拼落点。**

### 7.5 `CoordinateLanding` 与 `util/LandingY` 的分工（**不要合并**）

| | `CoordinateLanding` | `util/LandingY` |
|---|---|---|
| 精度 | 必须精确落点 | 精度可以让步 |
| 拿不到时 | 返回 `null`，由调用方决定等还是兜底 | 返回调用方给的兜底值（**一定给一个值**） |
| 用在哪 | 天灾门（可等一 tick） | 龙宫 ↔ 主世界的 `teleportTo` 旧路径 |

差异集中在"拿不到值时怎么办"。合并会丢掉这个区别。

### 8.2 判定链与绕过权限

```
玩家编辑类（shouldPreventEdit）
  ├─ 维度不是龙宫 → 放行
  ├─ FTB Chunks manager 未就绪 → 阻止（并记录一次 WARN：isManagerLoaded 为假时无法判绕过）
  └─ 否则 → !hasBypass(player)

环境类（shouldPreventEnvironment）
  └─ shouldPrevent(level, actor) ∧ enabled ∧ category
       ├─ 客户端侧 → 放行（不干预客户端预测）
       ├─ 维度不是龙宫 → 放行
       └─ !hasBypass(actor)
```

**绕过权限**来自 FTB Chunks：`api.getManager().getBypassProtection(uuid)`。这意味着：

- **拥有 FTB Chunks 绕过权限的玩家可以在龙宫自由编辑**（整合包管理员/建造者需要这个）；
- `FakePlayer` **永不**拥有绕过权限（`hasBypass` 显式排除）；
- **FTB Chunks 缺席时**：`isManagerLoaded()` 为假 ⇒ `hasBypass` 恒假 ⇒ **保护仍然生效**（fail-safe），
  但会在服务端启动时记录一条 WARN。

> ⚠️ **服务器启动时的历史认领警告**：`ServerStartedEvent` 会统计龙宫维度里已存在的
> FTB Chunks 认领并记 WARN——**它们不会被自动清除**（需手动清理）。
> 已认领的区块不享受本表的"玩家编辑"保护（因为那套逻辑只看绕过权限，不看认领状态），
> 但环境类保护仍生效。

### 8.3 提示文本

玩家被拦下时显示 **FTB Chunks 自带的** `ftbchunks.action_prevented`（金色），
**不是本模组的消息键**——沿用 FTB Chunks 的既有观感，避免玩家看到两套"保护"提示。
`FakePlayer` 不提示。

## 十、龙宫专属机制

### 10.1 化龙池水

**作用**：玩家碰到指定区域内的水 ⇒ 打开龙之生存的化龙祭坛 GUI（选龙种）。

**区域数据** `data/beloong/beloong/beloong_water_regions/loong_palace_pool.json`：

```json
{ "dimension": "beloong:loong_palace",
  "min": { "x": -54, "y": 68, "z": -312 },
  "max": { "x":  8,  "y": 77, "z": -272 } }
```

**加载**（`BeloongWaterRegionLoader`，`SimpleJsonResourceReloadListener`）：

- 资源路径 `beloong/beloong_water_regions`（注意：`data/beloong/` 下的**子目录也叫 `beloong`**）
- 按**维度**建索引：`Map<ResourceKey<Level>, List<BeloongWaterRegion>>`，支持多维度多区域

**触发链**（`BeloongWaterContactHandler#onPlayerTick`，`PlayerTickEvent.Post`）：

```
① 维度早退：当前维度没有区域文件 → 完全不检测（零开销）
② 方块坐标未变化 → 跳过扫描（避免静止时每 tick 全量扫描）
③ 纯函数判定 isTouching：
     玩家碰撞箱 ∩ 区域盒 → 逐格取流体状态
     只认 Fluids.WATER / Fluids.FLOWING_WATER
     fluidState.getHeight() 得到真实液面高度，再与玩家碰撞箱求交
④ contactTracker.update(...)：只在"未接触 → 接触"的跳变沿返回 true
⑤ 冷却闸：Config.BeloongWater.triggerCooldownTicks（默认 200 tick，范围 0–72000）
⑥ openDragonAltar：龙之生存祭坛冷却未到 → 系统消息提示；否则写祭坛冷却并发送 OpenDragonAltar 包
```

**状态清理**：`PlayerChangedDimensionEvent` / `PlayerRespawnEvent` / `PlayerLoggedOutEvent`
三处都要清 `contactTracker`、坐标缓存、冷却记录。

> 设计要点：维度早退 + 坐标不变早退 + 跳变沿触发 + 冷却，**四层**共同保证这个方法在
> 主城这种人流密集场景下不会成为性能负担。

### 10.2 传送石碑（Waystones）

**作用**：龙宫是固定地图，石碑的位置/名字/类型/UUID 都是确定的常量，因此**不依赖存档里的
`waystones.dat`**——每当龙宫区块加载（或玩家进入龙宫）时，对预设石碑做一次**幂等校正**。

> **术语**：代码里的类名沿用 Waystones 的 `Waystone*`（`WaystonePlacement*`），
> 中文一律称**传送石碑**。
> 数据目录名、类名、配置项名中的 `waystone` 一律不改——**重命名只发生在中文表述层面**。

**数据** `data/beloong/beloong/waystone_placement/loong_palace.json`：

| id | pos（**下半块**） | style | name |
|---|---|---|---|
| `main_hall` | `[0, 78, -57]` | `prismarine_waystone` | 龙宫·主殿 |
| `hill` | `[-24, 196, -404]` | `mossy_waystone` | 龙宫·仙岛山巅 |
| `arena` | `[0, 64, 150]` | `waystone` | 龙宫·演武场 |

**两个易错点**：

1. `pos` 是**下半块**坐标，上半块由代码用 `lowerPos.above()` 补（`WaystonePlacementEntry` 的
   `pos` 注释即为此意）；
2. 数据文件里**没有维度字段**——维度由处理器**硬编码**成龙宫
   （`WaystonePlacementHandler.LOONG_PALACE`）。文件放错目录也不会报错，只会永远不生效。

**确定性 UUID**：

```java
UUID.nameUUIDFromBytes(("beloong:waystone_placement:" + id).getBytes(UTF_8))
```

⇒ 同名石碑在**所有存档中共享同一个 UUID**。即使 `waystones.dat` 丢失导致数据重建，
UUID 也不会漂移，玩家对该石碑的激活状态与绑定物品因此不会失效。

**幂等校正的四个分支**（`doEnsureWaystone`）：

| 分支 | 条件 | 动作 |
|---|---|---|
| 1 | 方块不存在 | 放置上下两块 + 注入固定 UUID + 固定名字 |
| 2 | 固定 UUID 记录丢失（`waystones.dat` 数据丢失） | 清理孤儿记录 + 重建（**存档迁移后的自愈**） |
| 3 | 方块实体与固定 UUID 脱节 | 重新绑定到固定 UUID 的实体 |
| 4 | 正常 | **仅在名字被清空时**补回预设名（玩家改名会被尊重） |

**防卡死设计**（本机制最容易出事的地方）：

| 措施 | 原因 |
|---|---|
| 校正一律**延迟到下一个 tick**（`server.tell(new TickTask(...))`） | 彻底脱离区块加载调用栈 |
| **跳过未完全加载的区块**（`level.isLoaded(lowerPos)`） | 否则 `setBlock` 会触发同步区块加载 |
| 重入锁 `ENSURING`（`synchronizedSet`） | 防止嵌套校正 |

要防的是这条链：`setBlock → 邻居更新加载相邻区块 → ChunkEvent.Load → 再次校正` ⇒ **加载风暴**。

**两条触发路径**：

| 事件 | 范围 |
|---|---|
| `PlayerChangedDimensionEvent`（进入龙宫） | 全部预设石碑 |
| `ChunkEvent.Load`（龙宫区块加载） | 只校正落在该区块内的石碑 |

**style 解析**：不带命名空间时默认加 `waystones:` 前缀；解析失败记 WARN 并回退 `WaystonesStyles.DEFAULT`。

> **实机观察**：2026-09-16 的测试会话里只出现了 `main_hall` 与 `arena` 两条放置日志，
> `hill` 未出现——因为它在 `(-24, 196, -404)`，该区块从未被加载过，被 `isLoaded` 直接跳过。
> **这是设计内的行为，不是缺陷**。

## 十三、设计决策记录

> 本文的决策编号**独立于**《天灾维度总设计》（那份已用到 35+）与《龙宫天空渲染总设计》
> （那份有自己的编号体系）。跨文档引用时请写明文档名。

1. **龙宫是纯数据包维度，无自定义 Java 维度类** —— 复用原版超平坦生成器的最短路径，
   升级维护成本最低。生成器 `layers` 为空 ⇒ 不放置任何地层方块。
2. **`effects: beloong:loong_palace` 是唯一使用自定义天空的维度** —— 天灾用
   `minecraft:overworld`。把天空系统的影响范围严格限制在龙宫，避免两套维度机制相互干扰。
3. **在维度类型层硬禁自然刷怪，而不是靠 tick 清理怪物** —— `monster_spawn_light_level: 0`
   与 `monster_spawn_block_light_limit: 0` 是**零开销**的维度层手段；靠事后清理既费性能又不可靠。
   这是约束 1 的第一层。
4. **门的框架由方块 tag 判定，而不是 NeoForge 的 `isPortalFrame` 谓词** —— 后者默认只认黑曜石，
   荧石不是。用 tag 还让整合包可以通过数据包换框架方块。
5. **"框内为空"必须包含水** —— 否则"注水激活"这条链路在第一步就走不通（水格会被当成非空）。
   这是与天境一致的关键语义。
6. **坠虚空兜底不走统一冷却（唯一的特例）** —— 它是抢救机制：若走冷却，玩家会因为"刚传送过"
   而在虚空里摔死；若写冷却，掉一次虚空会连带禁用技能 3 秒。因此**既不检查也不写**。
7. **激活走方块事件而不是 tick 轮询** —— 水的进入必然伴随 `NeighborNotifyEvent`，是方块驱动、
   零开销的；项目里既有的轮询是为"每 tick 查玩家 Y"设计的，用在这里纯属浪费。
8. **刻意不取消邻居通知事件（与天境不同）** —— 天境会 `setCanceled(true)`，但取消会吞掉这次
   方块更新，而原版水与荧石的后续结算依赖邻居更新。
9. **龙宫侧落点有两套独立坐标，这是刻意行为，不统一** —— 本模组的
   `targetX/targetZ/fallbackY`（默认 `0.5 / 0.5 / 65.0`，服务门与技能）与 LockDown 的
   `login_spawn_target`（`0.5 / 64.0 / 0.5`，服务首次进入）数值不同。
   **本模组取 `y = 65` 作为落点高度的目的是"防止玩家卡在地下"**——两套坐标服务不同路径，
   不需要对齐，也不需要修复。
10. **传送过渡 0 tick** —— 不用原版下界门的 80 tick：那 4 秒死等待在落点已就绪时也会发生
    （天灾门当年的实机回归结论）。视角扭曲仍用原版同款 `CONFUSION`。
11. **准入判定用 `DragonStateProvider.isDragon`，且不缓存** —— 门是方块，任何实体都能走进去，
    因此必须每次判定。技能不需要判（能按出技能就说明是龙）。
12. **失败提示走 actionbar + 每玩家 20 tick 节流** —— 门是持续接触的方块，不节流会刷满聊天框；
    actionbar 会被新消息直接替换，不会排成行。冷却期内**不提示**（持续接触时提示无意义）。
13. **传送冷却硬编码 60 tick，删除全部相关配置项** —— 冷却属结构性内容。原
    `[disaster_portal].teleportCooldownTicks` 与 `[dimension_transport].loongPalaceToOverworld.cooldownTicks`
    均已删除。**NBT 键名 `beloong_portal_cooldown` 不得更改**（改了等于让所有已存在的冷却失效）。
14. **门方块额外顶住原版冷却** —— 原版玩家冷却只有 10 tick，撑不过 60 tick 的 NBT 冷却；
    不顶住会导致"玩家站在门里无界重试"，每轮刷一次日志与提示。
15. **`Spawn` 目标的 Y 不查高度图** —— 出生点是维度自身的数据，与"那一列现在有什么方块"无关。
    这是需求明确的口径。
16. **扩散自实现，不复用原版 `adjustSpawnLocation`** —— 原版内部用阻塞的 `level.getChunk`，
    违反 §7.3 的硬约束。自实现的代价是"未加载的候选被跳过"，结果可能落在稍远的候选上。
17. **扩散忽略游戏模式与天空光判断** —— 用户指定；调用方只在主世界用，天空光必然满足。
18. **扩散失败时原样返回出生点坐标，不做"上顶/下踩"** —— 用户指定。宁可站不住，也不要擅自
    把玩家挪到方块里或方块上。
19. **环境保护的绕过硬编码为 FTB Chunks 的 bypass 权限** —— 整合包管理员/建造者需要能编辑主城。
    没有引入本模组自己的权限开关（避免两套权限体系）。
20. **FTB Chunks 未就绪时保护仍生效（fail-safe）** —— `hasBypass` 在 manager 未加载时返回 false
    ⇒ 保护照常阻止，并记一条 WARN。宁可挡住管理员，也不要让主城被人编辑。
21. **禁止认领龙宫区块** —— 防止玩家用"认领"绕过 §8 的保护（认领后的行为由 FTB Chunks 自己的
    规则接管，而本模组的保护不看认领状态）。历史遗留的认领**只警告不自动清除**（可能含有玩家心血）。
22. **环保提示沿用 FTB Chunks 自己的文本** —— 避免玩家看到两套"保护"提示。
23. **化龙池水用"区域数据 + 跳变沿触发"而不是检测特定方块** —— 池子是整合包建的水体，
    本模组只声明"哪一块空间算池水"。这样整合包改建筑时不需要改代码。
24. **化龙池水的四层早退** —— 维度无区域 → 早退；方块坐标未变 → 早退；跳变沿 → 才判定；
    冷却闸 → 才开 GUI。主城人流密集，这四层共同保证它不是性能负担。
25. **传送石碑用确定性 UUID** —— `nameUUIDFromBytes("beloong:waystone_placement:" + id)`。
    这样即使 `waystones.dat` 丢失，玩家对石碑的激活状态与绑定物品也不会失效。
26. **传送石碑的校正一律延迟 1 tick + 跳过未加载区块 + 重入锁** —— 要防的是
    `setBlock → 邻居更新加载相邻区块 → ChunkEvent.Load → 再次校正` 这条**加载风暴**链。
27. **传送石碑的数据文件不含维度字段** —— 维度由处理器硬编码。代价是"文件放错目录不报错、
    只是永不生效"；收益是数据文件更短。**登记为易踩坑点**（§14）。
28. **主线程绝不使用阻塞式 `Level#getChunk` / `Level#getHeight`** —— 2026-09-12 死锁事故后立下的
    硬约束。所有落点解析必须用 `getChunkNow` + 非阻塞票据 + 下一 tick 重试 + 有界超时。
29. **三种入口共用一套落点类型与一份冷却** —— 门、技能、兜底全部走 `teleport` 包。
    统一的是"落点怎么算"与"冷却怎么写"，而不是"怎么触发"。
30. **龙宫维度 ID 的 6 处硬编码暂不统一** —— 用户决策。`teleport/TeleportTarget.LOONG_PALACE_LEVEL`
    是收口点，新增调用方应引用它（§2.3）。

## 十四、已知问题与后续可选项

| 项 | 说明 |
|---|---|
| **龙宫侧落点不在化龙池水上方** | 默认 `targetX/Z = 0.5`、`fallbackY = 65.0`，而化龙池水在 `x[-54,8] y[68,77] z[-312,-272]`——**两者在 Z 轴上不相交**（`0.5` 不在 `[-312,-272]` 内）。玩家从门/技能进入后落在 `(0.5, 65, 0.5)` 的半空中，要去化龙池需自行飞行。`TpLoongPalaceEffect` 的类注释把这条标为"已知缺陷（勿当成设计）"。**待整合包确定主城中央坐标后改配置**，不需要改代码 |
| ~~两套落点坐标不一致~~ | **不是缺陷，是刻意行为**：本模组用 `y = 65` 作为落点高度以**防止玩家卡在地下**，LockDown 的 `64.0` 服务另一条路径。见决策 9 |
| **`travel` 音效缺 subtitle** | `sounds.json` 里 `block.beloong.loong_palace_portal.travel` 没有 `subtitle` 字段，两个语言文件也没有对应键。`ambient` 与 `trigger` 都有。属遗漏，补 3 行即可（sounds.json + 两个 lang） |
| **传送门三条分支未被实机走到** | ① 水面落点（`MOTION_BLOCKING` 含流体 ⇒ 海洋列得到水面）② 上行兜底 Y ③ 下行超时（600 tick 未就绪）。都需要特定场景才能触发，目前只有静态审查 |
| **门的"三条失败门"提示未逐条实机验证** | `NON_DRAGON` / `WRONG_DIMENSION` / `TELEPORT_FAILED` 三条中，后两条需要构造异常场景（非龙玩家、把门放进下界）。节流行为（20 tick）也未实机计时 |
| **`TELEPORT_FAILED` 是防御分支** | 门方块自己的注释写明"At 目标有配置兜底、Spawn 目标不查高度图 ⇒ 实际不会发生"。它的存在只为免于静默失败 |
| **环境保护与认领的历史遗留** | 龙宫维度里已存在的 FTB Chunks 认领**不会被自动清除**，只在启动时记 WARN（§8.2）。这些区块的"玩家编辑保护"仍按绕过权限判定，不受认领影响 |
| **FTB Chunks manager 未就绪的窗口期** | 启动早期 `isManagerLoaded()` 为假 ⇒ 所有玩家的编辑都会被阻止（fail-safe）。这只影响启动瞬间，但若某个模组延迟加载 FTB Chunks，窗口会更长 |
| **维度 ID 的 6 处硬编码** | 见 §2.3 与决策 30。**用户决策：暂不统一** |
| **`TeleportTarget` 的命名空间用字面量 `"beloong"`** | 其余几处用 `BeLoongCore.MODID`。当前等价，但改 modid 时会漏 |
| **地图模板内容属于整合包资产** | 模板里若有本模组无法识别的方块，加载时退化为默认方块并记可恢复错误。这是模板与包体一致性问题（§1.3），**不是本模组缺陷** |
| **`Config` 中 4 个配置界面语言键缺失** | `beloong_water.button` / `beloong_water.tooltip` / `template_update.button` / `dragon_summon.button`（zh_cn 与 en_us 皆缺）；另有 2 个残留键 `cooldownTicks` / `teleportCooldownTicks`。**用户决策：无所谓，不是 BUG** |
| **`[dimension_transport.overworldToLoongPalace]` 节名有误导性** | 它只描述"其他世界 → 龙宫"的落点，不描述触发方式，也不覆盖"龙宫 → 主世界"。节名为历史沿用 |
| **`util/LandingY` 与 `CoordinateLanding` 并存** | 分工见 §7.5。**不要合并**——差异集中在"拿不到值时怎么办" |
