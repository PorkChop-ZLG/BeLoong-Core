## 五、魔改扩展点

骑士用**旧式** `AbstractBossEntity`（该类本身 `@Deprecated`，`AbstractBossEntity.java:71`），**没有注册表**。

1. **状态表**：`private static final Map<String, State> STATES`(`:179`)，静态块 `addState(new State(name, duration))`(`:1561-1598`，32 个)；`getStates()`(`:338-341`) 直接返回**可变**静态 map（无去重保护，`put` 静默覆盖）。
   - 新增状态：① 静态块加 `addState`；② 在 `tick()` **服务端第一段 `switch`**(`:714-1091`) 加逻辑；③ 在**第二段 `switch`**(`:1093-1269`) 给后继状态 —— **漏写会永久卡死在该状态**。
2. **攻击表**：`Attack` 是 record `(int id, String name, SoundEvent sound, int animTime)`(`AbstractBossEntity.java:533-545`)，骑士用 `Attack(String)` 构造 ⇒ **`id/animTime` 恒为 0**（`DATA_ATTACK_PHASE/DATA_ATTACK_ANIMTIME` 对骑士永远是 0）。

## 七、已排除（避免误报）

1. **`CustomBakedModelFactory` 访问客户端渲染器"看似必崩"，实际不崩**：geckolib 模型烘焙在服务端确会执行，但服务端 `ResourceManager` 按 `PackType.SERVER_DATA` 构造，只能看到 `data/**/geo/*.json`；模组在 `data\` 下只放了 3 个模型，identifier 是 `geometry.unknown`/`geometry.sandworm`，**都不等于 `geometry.helvar`** ⇒ 该分支不执行。
2. **配置 `SPEC = BUILDER.build()` 顺序**：反编译源码里看似在 `define()` 之前，`javap` 证实真实 `<clinit>` 里在所有 `define()` 之后 ⇒ **不是 bug**（Vineflower 重排）。
3. 52 处"非 client 包引用客户端类"**逐条有有效守卫**（`@EventBusSubscriber(Dist.CLIENT)`、网络包 `flow()` 前置、`IClientItemExtensions`、`dist != DEDICATED_SERVER` 等）。
4. 49 处 `addFreshEntity` **无无界循环**；`defineSynchedData` **0 处缺失**；`mixins.json` 26 条与磁盘文件一一对应、注入目标经真实字节码验证存在。

### 关于 `@OnlyIn(Dist.CLIENT)` 的更正

- 早期判断"NeoForge 已移除 `RuntimeDistCleaner`、该注解不起作用"**不成立**：`loader-4.0.43.jar` 里**存在** `net/neoforged/fml/common/asm/RuntimeDistCleaner.class`，且 **`FMLLoader.class` 引用它**；本机开发服务端日志也出现过其特征报错 `Attempted to load class … for invalid dist DEDICATED_SERVER` ⇒ **该清理器在本环境活跃**。
- 正确结论：① 它**确实按端剥离**被标注成员 ⇒ `@OnlyIn` **不是**空操作，模组 130+ 处用法属 Forge 时代正规做法；② 但它**不是"调用点的运行时守卫"** —— 只删被标注的成员，不拦通用代码里的调用 ⇒ 判断"服务端会不会加载客户端类"仍必须看 `isClientSide`/dist 分支。
- **对魔改的含义**：**不要**把服务端可能需要的方法标 `@OnlyIn(Dist.CLIENT)`（会被剥离 ⇒ `NoSuchMethodError`/`NoClassDefFoundError`）；客户端专属成员可以放心标。`KnightMarkEntity.tick()` 之所以安全，是因为原版 `Entity.tick()` 只是转调 `baseTick()`。

## 十一、无敌判定与"破防"全链（含本次太阳破防魔改索引）

> 本节是 §二/§三 的补充与固化：把"骑士为什么打不动 / 什么能打穿 / 破防怎么发生"整理成可直接查表的形式，并登记本次跨模组魔改。

### 11.1 无敌不是原版无敌

- `isInvulnerable() = getImmuneStacks() > 0 || super.isInvulnerable()`（`UnderworldKnightEntity.java:351-353`）——**没有**设置原版 `invulnerable` 字段。
- 判定完全在它自己重写的 `hurt`/`processHurt` 里；`hurt` 只是 `return processHurt(ds, amount, false)`（`:411-413`）。

### 11.2 `processHurt` 分支表（`:415-516`）

| 条件 | 行为 |
|---|---|
| `state == "dead"`，或（**该伤害在 `#minecraft:bypasses_invulnerability` 里 且 这一下会致死**） | `return super.hurt(ds, amount)` ⇒ 直接结算，**无视层数与过场** |
| `isCinematic()`（开场 377t / 复活 440t） | `return false`（**连 bypass 伤害也被拦**，除非上一条的"致死型 bypass"） |
| `flag = fromMark \|\| 伤害在 bypasses_invulnerability 里` 为真 | 跳过元素黑名单与护盾 ⇒ 走血量闸门后 `super.hurt`（`:485-486`） |
| 非 flag：客户端 / `DATA_UNDEAD_CINEMATIC > 0` / `in_fire`、`fall`、`lightning_bolt`、`wither`、`wither_skull` | `return false`（**元素黑名单是绝对免疫**） |
| 非 flag 且 `!isInvulnerable()`（层数 0） | 正常结算（含 75/50/25% 血量闸门逻辑 `:430-483`） |
| 非 flag 且层数 > 0 且 `state == "stuck"` | **破防姿势**：扣 1 层 + 伤害压到 `min(20, amount*0.1)`（`:487-504`） |
| 非 flag 且层数 > 0 且非 `stuck` | 播 `KNIGHT_BLOCK`，`return false`（`:505-507`） |

**关键事实**：被格挡的命中**从不调用 `super.hurt`** ⇒ NeoForge 的伤害事件（`LivingIncomingDamageEvent` 等，插点在 `LivingEntity.hurt`/`actuallyHurt` 内）**一个都不会触发**；因此"用事件监听被挡的命中"这条路不通，只能注入 `hurt`。

### 11.4 模组自带的破防路径（供对照）

1. **逼出 `stuck` 姿势**：有盾期间累计"连续 3 次轻击"或"3 次重击（血量 ≤50% 时 5 次）"（`doAttack` 收尾 `:1530-1549` 的 `lightCounter`/`heavyCounter`）⇒ 下一次重击结束时 `setState("stuck")`（`:1179-1186`，70t）。在 `stuck` 里打本体：扣 1 层、伤害 `min(20, amount*0.1)`，层数归零则 `idle_to_knocked_down`(46t) → `knocked_down`(35t) → `knocked_down_to_idle`(41t)。
2. **打「冥界印记」**（`KnightMarkEntity.hurt:100-138`）：伤害 ×2、记 1 层、**强制 `setState("knocked_down")`**，并以 `processHurt(..., true)`（`fromMark`）无视护盾全额结算；`setState("stuck")` 时必定生成 scale=1.0 的印记（`setState` 覆写 `:1294-1301`）。

### 11.5 本次魔改：太阳破防（跨模组）

- **数据**：3 个 `mowziesmobs:` 伤害类型（`solar_flare`/`solar_beam`/`sun_strike`）+ 语义标签 **`beloong:underworld_knight_guard_break`**（唯一判定入口）+ 三类型补回 `#minecraft:is_player_attack` / `#minecraft:is_projectile` + 中英死亡信息。
- **转换层**（Mowzie 侧 `@ModifyArg`，保留 `on_fire`）：`SolarFlareAbility.beginSection`（`player_attack`→`solar_flare`）、`EntitySolarBeam.tick`（`dealMixedDamage` index 1 + `Entity.hurt` index 0）、`EntitySunstrike.damageEntityLivingBaseNearby`（两处 `Entity.hurt`，靠 `on_fire` 判别）、**`EntitySuperNova.tick`（`dealMixedDamage` index 1 + `Entity.hurt` index 0，第四招"超新星燃烧"）**。
- **判定层**（骑士侧单点注入）：`UnderworldKnightEntity#hurt` HEAD ⇒ 命中标签时 `processHurt(source, amount, true)`（穿透 + 正常结算），**仅当返回 true 且层数 > 0** 才 `removeOneImmuneStack()` ⇒ **只扣 1 层，不倒地、不 ×2**。
- **配置**：COMMON `[solar_guard_break] enabled`（默认 true）。
- **实测（2026-10-09，dev `runClient`）**：耀斑命中骑士 ⇒ 日志锚点 `source=mowziesmobs:solar_flare stacks=1->0 dealt=true`，用户确认**确实可以破防**；射线/打击在本轮之前未接线（已补），伤害量级小、范围小、无反馈特效 ⇒ 体感不明显属预期。
- **相关文档**：设计 [2026-10-09-underworld-knight-solar-guard-break-design.md](plans/2026-10-09-underworld-knight-solar-guard-break-design.md)、计划 [同上-plan](plans/2026-10-09-underworld-knight-solar-guard-break-plan.md)、验收 [2026-10-09-…-acceptance.md](reviews/2026-10-09-underworld-knight-solar-guard-break-acceptance.md)。
- **魔改入口**：任何整合包/模组把自己的伤害类型追加进 `data/beloong/tags/damage_type/underworld_knight_guard_break.json`（默认 `"replace": false` 即并集）即可破防，**骑士侧无需改代码**。⚠️ 追加**别的模组**的类型时必须写 `{"id": "...", "required": false}`，否则该模组缺席时整条标签加载失败（原版 `TagLoader` 对缺失的 required 条目直接失败）。

### 11.6 两条可复用的工程结论

1. **Mixin `@ModifyArg` 的多匹配行为**：官方 javadoc（`@ModifyArg` 的 `expect`/`allow` 说明）明确"注入点默认匹配目标方法里**每一条**候选指令"，`expect` 仅在 `mixin.debug.countInjections` 打开时生效、`allow` 只是上限校验 ⇒ **同一方法里有多处同类调用时，不写 `ordinal` 也会全部注入**（本调研据此避免了随重编译漂移的序号）。
2. **被实体自行"吞掉"的伤害不触发任何 NeoForge 事件**（见 11.2）⇒ 设计"跨模组穿盾/破防"时必须注入目标实体的 `hurt`，或把类型并入原版 `#bypasses_invulnerability`（代价是全局语义变化，且只能造成伤害、不能改状态）。
