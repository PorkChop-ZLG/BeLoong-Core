## 三、根因（双层）

### 3.1 L1（模组侧，必修）

`DisasterPortalBlock.entityInside()` L136 在**玩家移动回调**里做**跨维度同步区块加载**：

```java
targetLevel.getChunk(blockX >> 4, blockZ >> 4);   // ← 主线程 managedBlock 自旋
```

`managedBlock` 只能推进主线程自己的任务队列，**覆盖不到区块生成流水线与后台 worker 的协同**；
而目标区块 future 的完成事实上依赖主线程继续跑 tick → 互相等待、无超时、无异常。NeoForge 的
`currentlyLoading` 旁路只在 FULL 同步载入窗口有效，本次故障发生在更早的结构生成阶段，旁路失效。

**结论：在服务器主线程上同步等待跨维度区块生成是不受支持的用法。**

### 3.2 L2（区块生成侧，**已查明**，整合包侧已修复）

该 future 之所以"永不完成"，是因为目标区块生成时 worker 线程抛了 `StackOverflowError`（§2.2），
而递归的来源是两个**天灾专用结构集互相写了 `exclusion_zone`**（原文取自实例仓库
`D:\BeLoong\.minecraft\versions\BeLoong` 分支 `dev` 的 `HEAD` 版本）：

| 结构集 | 修复前 `placement.exclusion_zone.other_set` | `chunk_count` |
|---|---|---|
| `beloong:disaster_set_ground` | `beloong:disaster_set_underground` | 10 |
| `beloong:disaster_set_underground` | `beloong:disaster_set_ground` | 10 |

```jsonc
// 修复前 kubejs/data/beloong/worldgen/structure_set/disaster_set_ground.json（节选）
"placement": {
  "type": "minecraft:random_spread", "spacing": 32, "separation": 16, "salt": 20260921,
  "exclusion_zone": { "other_set": "beloong:disaster_set_underground", "chunk_count": 10 }
}
```

**机制链条**：二者构成 **2 环** → `hasStructureChunkInRange(underground)` →
`underground.placement.isStructureChunk` → 其 `ExclusionZone.isPlacementForbidden` →
`hasStructureChunkInRange(ground)` → `ground.placement.isStructureChunk` → 其 `isPlacementForbidden` →
…… 无限递归，直到栈溢出（实测打印 **1024 帧**后被 HotSpot 默认上限截断）。

**为什么只有天灾维度炸**：`hasStructureChunkInRange` 本身不看群系，但进入环的**入口**要求该结构集出现在
当前维度的 `possibleStructureSets` 里，而这两个 `beloong:` 集只在天灾维度满足群系条件 ——
这正好解释了"主世界正常、天灾维度必炸"。

**为什么变成主线程卡死**：worker 抛 `StackOverflowError` 后异常从任务逃逸，区块 future **永不完成**；
而 L1 的同步 `getChunk` 正在等这个 future → 主线程永久自旋。

**修复（整合包侧，2026-09-12 19:54:14 完成）**：两个文件中的 `exclusion_zone` 块被整体删除
（`kubejs/data/beloong/worldgen/structure_set/disaster_set_{ground,underground}.json`）。
对照原文、复核命令与"为什么初版取证漏掉了这个环"见
[`reviews/2026-09-12-structure-exclusion-recursion-probe.md`](reviews/2026-09-12-structure-exclusion-recursion-probe.md)。

> **修正记录**：本文档初版曾据"全实例扫描 0 环"断言该环"只能来自运行时（疑似结构整合类 mod）"，
> **该结论是错的**——初版扫描是在实例被并发修复期间执行的，恰好测到了修复后的状态。
> 教训已写入 §八。

**关键因果**：同步等待把「一个本来可上报/可重试的异步失败」变成「**不可观测、不可恢复的服务器永久卡死**」。

## 四、修复方案（L1）

采用**原版传送门范式**（`implements Portal`）：`entityInside` 只登记 → 原版 `handlePortal()`
回调 `getPortalDestination()` → 非阻塞求落点 → `DimensionTransition` 换维度。

```
entityInside：冷却检查 → 骑乘则 stopRiding() → setAsInsidePortal() → 非阻塞预热落点区块
handlePortal → getPortalDestination：
  下行：getChunkNow 探测（不阻塞）
        未就绪 → addRegionTicket(TicketType.PORTAL, 半径 0) + setPortalCooldown(0) + return null（下一 tick 重试）
        已就绪 → LevelChunk#getHeight(MOTION_BLOCKING)+1+1 → DimensionTransition
  上行：重生点 → 世界出生点 → (0,64,0) → DimensionTransition
postDimensionTransition：fallDistance = 0 + 写 NBT 冷却（键名不变）
```

### 4.1 关键决策与理由

| 决策 | 理由 |
|---|---|
| `getPortalTransitionTime()` 取 `0`（曾短暂改 `80`，**2026-09-13 实机回归后撤销**） | 初版取 `0` 以保留旧"即时"手感，等待由"未就绪 → return null → 重试"承担。2026-09-12 曾改为 `80`（= 原版下界门默认 `playersNetherPortalDefaultDelay`）以求"扭曲涨满与开始换维度同步"，但实机证明代价不可接受：**落点已就绪时也要白等 81 tick（≈4 s）**（`run/logs/debug-2.log` 连续 4 次 `waited=81 tick`），而落点未就绪时它并不能让传送提前 ⇒ 最终回到 `0`：接触即开始传送尝试。代价是落点**立即就绪**时扭曲几乎不可见（加载屏马上接管），把可见性交给慢路径 |
| 用 `getChunkSource().getChunkNow(...)` | **唯一确定不阻塞**的"区块是否在内存"探测；`Level#getHeight` 会经 `hasChunk`（票级）再落回阻塞 `getChunk` |
| 高度读 `LevelChunk#getHeight(MOTION_BLOCKING) + 1 + 1` | 与旧 `Level#getHeight(...) + 1.0` **逐字等价**（`Level` 版 = `chunk` 版 + 1），且不触发加载 |
| 预热用 `addRegionTicket(TicketType.PORTAL, …, 半径 0, 门坐标)` | 公开、非阻塞、幂等、寿命 300 tick；半径 0 只强制 1 个区块 |
| **必须** `player.setPortalCooldown(0)` | 原版先设冷却再问落点，而 `setAsInsidePortal` 在冷却期只刷新冷却、不登记 `insidePortalThisTick` —— 不清冷却则玩家站在门里**永远拿不到重试机会** |
| 超时 `DESTINATION_WAIT_TIMEOUT_TICKS`：`200` → **`600`**（2026-09-13 实机回归后调整） | 用**有界失败**取代无限等待（实测故障是即时 SOE）。该上限**自进门第一 tick 起算**（`waitedTicks` = `portalProcess.getPortalTime()`，与倒计时长度无关）。原 200 tick 对本维度太紧：地形生成实测 122–130 tick（`debug-4.log` 的 `waited=122`、`latest.log` 的 `waited=130`，约 6–6.5 s），余量仅约 1.5 倍；600（≈30 s）给出约 4.6 倍余量。"有界"指不会永久阻塞主线程，且失败后**停止重试直到玩家离开传送门**（见下一条） |
| 骑乘在**登记前** `stopRiding()` | 原版 `handlePortal` 用 `canUsePortal(false)` 作闸门，仍骑乘的玩家永不被登记 |
| **失败后**在 NBT 冷却期内把原版冷却顶住（2026-09-12 增补） | `failDestination` 承诺"停止重试直到玩家离开传送门"，但**原版玩家冷却只有 10 tick**（`Player#getDimensionChangingDelay` 覆写 `Entity` 的 300），撑不过 NBT 冷却（默认 100）：NBT 一到期就会重新登记、重试（约每 300 tick 一轮、无界，反复刷 error 日志与玩家消息）。现于 `entityInside` 的冷却早退分支把原版冷却设为"剩余 NBT 冷却 + 1"，使 NBT 到期那一刻 `setAsInsidePortal` 仍被 `isOnPortalCooldown()` 拦住（只刷新不登记），承诺才真正成立 |
| 日志加 ASCII 锚点 `[DisasterPortal:wait/teleport/timeout/error]` | 实例日志是 GBK，中文锚点不便脚本判读 |
| ~~不覆写 `getLocalTransition()`~~ | 初版取默认 `NONE` = 维持当时现状（旧实现无 `Portal`，也就没有原版门那种视角扭曲叠加层）。**2026-09-12 后续改动已改为 `CONFUSION`**（下界门同款扭曲过渡）+ 注册天灾维度专用「加载地形中」背景，见 [`plans/2026-09-12-disaster-portal-transition-design.md`](plans/2026-09-12-disaster-portal-transition-design.md) |

### 4.2 被否方案

| 方案 | 结论 |
|---|---|
| 固定倒计时后再同步 `getChunk` | ❌ 只把卡死推迟 N tick。（与"曾短暂取 80 tick 进门倒计时"无关：那条是原版 `PortalProcessor` 的倒计时，无论取 0 还是 80，落点解析始终是 `getChunkNow` 探测 + `return null` 重试，全程无同步加载；且该倒计时已按实机回归撤销为 0） |
| `getChunkFuture(...).thenAccept(...)`（任务书备选方案 2 的字面写法） | ❌ `ServerChunkCache.getChunkFuture` **在主线程也会 `managedBlock`**；必须把调用派发到非主线程才成立，复杂度不划算 |
| 仅 `getChunkNow` 探测、不申领票据 | ❌ 没有票据 ⇒ 区块永远不会加载 ⇒ 变成"永远不传送" |
| 用 `Level#getHeight` 取高度 | ❌ 区块未加载时仍会阻塞；语义也不清晰 |
| 给维度加 `structure_overrides` / Mixin 保护结构递归（L2 修法） | ⏸ 用户已定：只修传送门 + 只读取证，L2 交整合包侧 |
| 顺带修 `DimensionTransportHandler` / `TpLoongPalaceEffect` 的同类 `getChunk` | ✅ 已在本次修复之后单独完成（2026-09-12）：改为零状态纯函数 `util/LandingY.resolveOrFallback`。设计文档：[`plans/2026-09-12-dimension-transport-nonblocking-design.md`](plans/2026-09-12-dimension-transport-nonblocking-design.md) |

## 七、实机验收协议（整合包侧执行）

**准备**：用本次构建的 `build/libs/beloong-0.9.1.jar` 覆盖 `mods\beloong-0.9.1.jar`。

**第 0 步｜回归确认环已断开（30 秒）**
```
/execute in beloong:disaster run forceload add 0 0
```
整合包侧已于 2026-09-12 19:54:14 删除环上的两处 `exclusion_zone`
（`beloong:disaster_set_ground` ⇄ `beloong:disaster_set_underground`），**本步应不再出现**
`StackOverflowError`。若仍出现 ⇒ 还有别的环，按取证文档 §四 的复核命令与 §六 的方法重新比对实例 git revision。
（该命令会改变该区块生成状态，请用测试存档。）

**第 1 步｜下行（关键）**：选一个**天灾侧从未生成**的存档/位置，在选定 XZ 建门
（或直接 `/setblock x y z beloong:disaster_portal_block`），**持续移动**穿门。
- 期望日志：`[BeLoongCore][DisasterPortal:wait]` →（加载完成后）`[BeLoongCore][DisasterPortal:teleport] … waited=N tick`；
- 期望结果：出现在天灾维度**地表上方 1 格**，无卡顿；
- 期望日志：**不再**出现 `A single server tick has taken` / `Thread Dump:`（ModernFix）与
  `Timed out waiting for world statistics`（spark）。

**第 2 步｜反向**：从天灾维度走回门 → 回到重生点（无重生点则世界出生点），朝向保留。

## 八、教训

1. **任何主线程 `getChunk` 都要假设它可能"永不返回"**：`managedBlock` 的"边等边跑"覆盖不了区块流水线；
   future 一旦因异常逃逸或逻辑等待而永不完成，卡死是**静默**的（无 crash report、无异常、无超时）。
2. **同步等待会把异步失败放大成不可恢复故障**：L2 本身只是一次区块生成失败，本应可重试/可上报。
3. **原版范式自带一层"防呆"**：`handlePortal` 先设冷却再问落点 —— "返回 null"不是"重试"而是"退避"；
   不理解这层就会写出"站在门里永不重试"的新 bug（本轮以 `setPortalCooldown(0)` + 注释固化）。
4. **日志锚点用 ASCII**：实例日志 GBK，中文锚点在 UTF-8 工具链里会被误读。
5. **"卡死消失"与"功能成功"是两件事**：本次修复保证前者（主线程永不阻塞），后者受生成侧数据制约；
   必须提供生成失败的判别步骤，避免下一轮把"该 XZ 生不出来"误判成"修复失败"。
6. **递归类问题的转储会被 `-XX:MaxJavaStackTraceDepth=1024` 截断**，入口点与集合名永远不会出现；
   定位只能靠"复现 + 二分"或"数据侧对齐时间线"，读转储读不出真凶。
7. **扫描整合包数据不能只认一个字段名，也不能只认一种位置**：本包同时存在 `exclusion_zone` /
   `super_exclusion_zone` / `enhanced_exclusion_zone`，后两者指向**标签**；另外还有两处把
   `exclusion_zone` 写在 JSON 顶层而**静默失效**的声明。jar-in-jar 也必须展开。
8. **在"活着的实例"上取证必须先锁 revision** —— 本次最大的教训。修复动作发生在 19:54:14，
   而我的全实例扫描（先扫 228 个 jar、最后才扫 `kubejs`）恰好在其后读到目标文件，
   于是得出了"声明图无环、环只能来自运行时"的**错误结论**。实例目录本身是 git 仓库，
   `HEAD` 里一直是故障版本；只要先跑 `git status` / `git show HEAD:<path>`，或先记录
   文件 mtime + SHA256 并在扫描后再核一次，就能立刻发现"测到的是移动靶"。
   **实机证据是硬证据，数据扫描只是解释工具——不能用它否定转储。**
9. **对称配置要成对验证**：A 排除 B 是正常的，B 又排除 A 就是死循环。
   本次的真凶正是 `beloong:disaster_set_ground` ⇄ `beloong:disaster_set_underground`
   互写 `exclusion_zone`（各 `chunk_count=10`）。
