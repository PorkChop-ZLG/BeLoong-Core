## 四、逐条发现

### A 组：主线程阻塞面

#### R-A1 [次要] `getSharedSpawnPos()` 的世界边界分支仍会在主线程同步加载区块（唯一残留）

- **结论**：四个文件里已无直接的 `getChunk`/`getHeight`，但三处 `getSharedSpawnPos()` 在"出生点落在世界边界外"时会经 `getHeightmapPos → Level#getHeight → Level#getChunk → managedBlock` 同步等待。
- **mod 证据**：`DisasterPortalBlock.java:340`、`DimensionTransportHandler.java:164`、`TpLoongPalaceEffect.java:113`。
- **参考证据**：`Level.java:864-872`（`!getWorldBorder().isWithinBounds(levelData.getSpawnPos())` → `getHeightmapPos`）、`LevelReader.java:86-88`、`Level.java:383-398`（`hasChunk` 为真才 `getChunk`）、`ServerChunkCache.java:136-168`（`managedBlock` + `join`）。
- **主审复核**：已亲读 `Level.java:864-873` 与 `ServerChunkCache` 阻塞路径，属实。
- **可达性**：默认世界边界包含出生点 → 直接返回，不查询高度图（红队也走通了这条路径并同意"平时不命中"）。**旧代码同款调用，非本批回归**。
- **建议**：改用 `overworld.getLevelData().getSpawnPos()`（不查高度图），或在该分支保留非阻塞兜底。

#### R-A2 [次要] `POST_TELEPORT` 寿命只有 5 tick，注释把它当成长期加载保证

- **结论**：票据确实申领了，但它 5 tick 就过期。落点区块的长期加载保证来自玩家自身的 `PLAYER` 票（无寿命），不是 `POST_TELEPORT`。
- **mod 证据**：`DimensionTransportHandler.java:161-163`、`LandingY.java:27-29`；同类归因还写在 `docs/天灾维度总设计.md:995`、`docs/plans/2026-09-12-dimension-transport-nonblocking-design.md:32,37,69`。
- **参考证据**：`TicketType.java:15,17-18`（`PLAYER` 无寿命、`PORTAL=300`、`POST_TELEPORT=5`）、`Ticket.java:65-68`（`timedOut`）、`DistanceManager.java:68-94`（每 tick `purgeStaleTickets`）+ `:230-237`（玩家票）。
- **主审复核**：已亲读 `TicketType.java:13-19`、`Ticket.java:65-68`，属实。
- **影响**：结论"落点最终会被加载"仍成立（玩家到位即由 `PLAYER` 票无限期加载），所以**现在不出问题**。风险在维护侧：后续可能有人据此弱化 `DisasterPortalBlock` 的 PORTAL 预热，或以为 5 tick 足以覆盖生成耗时。
- **定级异议**：红队建议升为「重要」（理由：该说法被写进两份设计文档，属于被当作契约的加载保证）。主审**维持「次要」**：它是注释/文档事实错误，不改变运行时行为。
- **建议**：注释改为「落点由该区块上的玩家票（`PLAYER`，无寿命）长期保证，`POST_TELEPORT` 只覆盖传送瞬间」。

#### R-A3 [已证伪] 「注释只在 `teleportCooldownTicks >= 300` 时成立」——前提与结论都错

- **原结论（A 组）**：`Entity.getDimensionChangingDelay()` 对玩家 = 300，故默认 100 下 `failDestination` 的 javadoc 成立，只有 `T >= 300` 时失效。
- **红队证伪 + 主审确认**：**玩家不是 300，而是 10。** `Player.java:467-470` 覆写了 `Entity.java:2294-2297` 的默认 300：

  ```java
  // mc/net/minecraft/world/entity/player/Player.java:467-470
  @Override
  public int getDimensionChangingDelay() { return 10; }
  ```

  因此 `setPortalCooldown()`（`Entity.java:508-513`）对玩家写入的是 **10**。主审此前只 grep 了 `ServerPlayer.java`（确实无覆写），漏掉了它的父类 `Player`——这是本次审查中**主审自己的错误**。
- **正确推论**：失败当刻 NBT 冷却 = `T`（默认 100）、原版冷却 = 10。NBT 冷却期内 `entityInside` 早退（`DisasterPortalBlock.java:153-155`）**不**调用 `setAsInsidePortal`，所以原版那 10 tick 会正常走完；NBT 一到期，`setAsInsidePortal` 发现 `isOnPortalCooldown() == false` ⇒ **立刻重新登记并重试**。也就是说 javadoc 描述的"停止重试直到玩家离开传送门"在**默认配置下就不成立**（只有当 `T < 10`，例如 `T = 0` 时才成立）。
- **处置**：该条被 R-B3 完全吸收，不再单独立项。

#### R-A4 [次要] `LandingY` 的「逐字等价」论证与旧代码实际执行路径不符

- **结论**：公式分支逐条等价，但 javadoc 的**归因**错了——旧代码在本行之前已 `getChunk` 强制加载，所以旧实现的 `hasChunk == false` 分支在旧代码里不可达。真实差异是设计已批准的 B-1（未加载即兜底），不是"旧代码也会落兜底"。
- **mod 证据**：`LandingY.java:14-20`（尤其 `:17-18`）、`:52-53`、`:56-62`。
- **参考证据**：旧实现 `git show 6cacda2:src/.../DisasterPortalBlock.java`（`:136` `targetLevel.getChunk(blockX >> 4, blockZ >> 4)`）与 `git show c953112 -- src/.../DimensionTransportHandler.java`；`Level.java:201-214`（`ChunkStatus.FULL, true`）；`ServerChunkCache.java:160-167`（`requireChunk` 且 null → 抛异常，不会静默返回）；空列语义 `ChunkAccess.java:184-196` + `Heightmap.java:103-113`。
- **可达性**：±3000 万分支要求 `getChunkNow(±1875000, …)` 命中内存区块。主审认为**实际不可达**（世界边界上限约 ±29,999,984，边界外区块不会被加载）；红队指出理论上可经 `currentlyLoading` 旁路命中（`ServerChunkCache.java:154-155,191`）——**保留红队这一保留意见**，但两者都不影响 javadoc 结论。
- **建议**：javadoc 改写为「公式逐分支等价；未加载时旧代码会先强制加载，故实际差异是设计批准的『未加载即兜底』；虚空列另见 R-N3」。

#### R-A5 [仅记录] `getChunkNow` 的 `currentlyLoading` 旁路在主线程不可观测；即便返回也可安全读高度图

- **参考证据**：`ServerChunkCache.java:173-203`（`:174-175` 非主线程恒 `null`；`:181-184` 缓存命中非 `LevelChunk` 也 `null`；`:188-189` holder 为 null → `null`；`:191` `currentlyLoading != null` 直接返回；`:192-200` `getChunkIfPresent(FULL)`）、`GenerationChunkHolder.java:36`、写入方在主线程执行器上（`ChunkStatusTasks.java:191-223`、`ChunkMap.java:192,216`、`ServerChunkCache.java:557-560`）、高度图已 prime（`ChunkStatusTasks.java:149-152`、`ChunkSerializer.java:229`、`LevelChunk.java:105-109,143-147`）。
- **判定**：两处调用点都只在同一 tick 内读高度图、不跨 tick 持有 `LevelChunk` 引用 ⇒ 不构成竞态风险。红队把"即便返回也安全"标为**证据不足**（无法从源码闭合"`hasPrimedHeightmap` 恒真"，需实机/断点），主审**接受该保留**：本条仅为观察项，不主张已验证的安全性。
- **建议**：无需改代码；可在 javadoc 补一句"`currentlyLoading` 旁路在主线程不可达（需实机确认）"。

#### R-A6 [仅记录] 下行 `DimensionTransition` 未使用 `PLACE_PORTAL_TICKET`

- **参考证据**：`DimensionTransition.java:19-28,40-42` → `Entity.java:2764-2768`；原版 `NetherPortalBlock.java:172`（`PLAY_PORTAL_SOUND.then(PLACE_PORTAL_TICKET)`）。
- **判定**：返回 transition 前区块已在内存、等待循环刚申领的 PORTAL 票尚有约 300 tick、随后玩家票永久接管 → **不会**"到达时未加载"。少的是与"原版范式"的完全对齐：一层额外保险 + 到达侧 `ClientboundLevelEventPacket 1032` 音效（体验差异，非阻塞面）。
- **建议**：若要完全对齐，可在 `postTransition()` 上 `.then(DimensionTransition.PLACE_PORTAL_TICKET)`。

### B 组：原版范式与双端对称性

#### R-B1 [重要] `getPortalTransitionTime() == 0` 使 CONFUSION 视角扭曲在正常路径上几乎不可见

- **结论**：`getPortalTransitionTime()` 返回 `0`（`DisasterPortalBlock.java:175-178`），而 `PortalProcessor.processPortalTeleportation` 的判定是 `this.portalTime++ >= transitionTime`（`PortalProcessor.java:27`）→ 首次评估 `0 >= 0` 即成立，**同一/下一 tick 就传送**。客户端 `spinningEffectIntensity` 每 tick 只 +0.0125（`LocalPlayer.java:925`），达到 1.0 需约 80 tick；而玩家一旦进入加载屏，`LocalPlayer.java:728` 直接跳过该效果处理 → 强度**冻结在约 0.0125**。此时 `Gui` 的紫幕走 `alpha = alpha²·alpha²·0.8 + 0.2`（`Gui.java:1355-1360`）≈ **0.2 的下限**，镜头扭曲幅度也极小。
- **mod 证据**：`DisasterPortalBlock.java:175-178`、`:191-194`（`getLocalTransition() = CONFUSION`）、`:144-147`（客户端登记）。
- **参考证据**：`PortalProcessor.java:21-29`、`LocalPlayer.java:904-933`（`:925` f=0.0125F、`:929-930` 衰减 −0.05F、`:933` clamp）、`LocalPlayer.java:728-731`（`ReceivingLevelScreen` 期间跳过）、`Gui.java:290-295`（`f1 > 0` 才画）与 `:1355-1360`（alpha 下限）、原版对照 `NetherPortalBlock` 用 `Math.max(1, gamerule)` 的真实倒计时。
- **主审复核**：以上行号均已亲读确认（`LocalPlayer.java:900-934`、`Gui.java:285-296,1350-1371`）。
- **红队保留**：严格说"服务端同 tick 传送"已证实，但"玩家实际能看到几帧扭曲"属跨端观感，**证据不足**（需实机帧计数）。主审采纳该保留——结论已按"几乎不可见（0.2 下限 + 冻结在 0.0125）"表述，未声称精确帧数。
- **影响**：你明确要求的效果是"和**下界传送门一样**的视角扭曲过渡"。当前实现拿到了机制（CONFUSION + 局部过渡 + 音效 + 自动关容器），但**拿不到时间**。
- **可选方案**（**需要你决策**，本报告不动代码）：
  - **A. 保持 0**：不做过渡。理由：旧实现的"即时传送"手感。
  - **B. 改为约 80 tick**（≈4 秒，`LocalPlayer` 加满所需）：与下界门观感一致，但传送前要等 4 秒。**这是"和下界传送门一样"的方案**。
  - **C. 折中 20–40 tick**：能看到明显扭曲（强度 0.25–0.5），延迟 1–2 秒。
  - 注意：若选 B/C，`DESTINATION_WAIT_TIMEOUT_TICKS = 200` 的等待预算含义要重新表述（等待从"进门后"变成"倒计时结束后"）。

#### R-B2 [次要] 「服务端故意不试，客户端仍在演完整个传送」——失败路径的双端不同步

- **原结论（B 组）**："NBT 冷却期内客户端仍累积扭曲但不传送"，定为「重要」。
- **主审修正**：方向对，但**机理和范围都不对**，定级降为「次要」。原版其实**会**把冷却同步给客户端，只是只在"发重生产物包"的那一刻。完整证据链（全部亲读）：
  1. 冷却随生成信息下发：`ServerPlayer.createCommonSpawnInfo(ServerLevel)` 把 `this.getPortalCooldown()` 放进 `CommonPlayerSpawnInfo`（`ServerPlayer.java:2124-2136`；字段定义 `CommonPlayerSpawnInfo.java:24`，序列化 `:49`）；跨维度传送时 `ServerPlayer.java:907` 发送 `ClientboundRespawnPacket(createCommonSpawnInfo(serverlevel), 3)`；客户端在 `ClientPacketListener.java:1227`（重生/换维度）与 `:455`（登录）应用 `setPortalCooldown(...)`。
  2. 因此**传送成功**后客户端冷却 = 服务端冷却（成功路径不清冷却 ⇒ 两者同为 `Player.getDimensionChangingDelay()` = **10**，`Player.java:467-470`）⇒ 客户端 `setAsInsidePortal` 因 `isOnPortalCooldown()` 只刷新不登记（`Entity.java:2257-2267`）⇒ **不会**出现"冷却期内白扭曲"。原结论这一半**不成立**。
  3. 但**传送失败**时（`failDestination`，`DisasterPortalBlock.java:315-324`）没有换维度 ⇒ **没有** `ClientboundRespawnPacket` ⇒ 客户端冷却始终保持 0，于是客户端 `entityInside`（`:144-147`，无任何冷却判定）每 tick 登记，`spinningEffectIntensity` 在约 80 tick 内涨到 1.0（`LocalPlayer.java:925,933`）并**维持满值**（只有离开门才会以 −0.05/tick 衰减，`:929-930`）。
  4. 结合 R-B3：服务端在每轮失败后会有约 `teleportCooldownTicks` 的"故意不试"窗口，而客户端在这段时间里始终显示满强度扭曲 ⇒ 玩家看到的是"传送门在演，但什么都不会发生"。
- **mod 证据**：`DisasterPortalBlock.java:144-147,153-155,315-324`。
- **参考证据**：`ServerPlayer.java:907,2124-2136`、`CommonPlayerSpawnInfo.java:24,49`、`ClientPacketListener.java:455,1227`、`Entity.java:2257-2267`、`Player.java:467-470`、`LocalPlayer.java:904-933,728-731`。

#### R-B3 [重要] 200 tick 超时**不**停止重试：重试环路无界，且 javadoc 把机制写反了

- **结论**：`failDestination`（`DisasterPortalBlock.java:315-324`）的 javadoc 声称「原版自身的 10 tick 传送冷却配合 `setAsInsidePortal` 的冷却刷新语义，会让本轮停止重试，直到玩家离开传送门」。**这句是错的**：原版冷却只有 10 tick，会在 NBT 冷却（100 tick）走完之前就归零，玩家**不离开门**也会重新登记 → 新一轮 200 tick 等待 → 再失败 → 无限循环。

- **定级说明**：`次要` → **`重要`**（采纳红队建议）。理由：它是本批修复自己声称的安全性属性（有界失败）未达成，且失败场景下玩家可感知（聊天刷屏 + 持续扭曲）。
- **修复建议**（二选一，见 §八）：
  - **最低成本（推荐先做）**：修正 javadoc 为「失败后写入 NBT 冷却限流；玩家继续站在门里时每约 `teleportCooldownTicks + 200` tick 重试一轮，直到落点就绪或玩家离开」，并把每轮的 `error` 日志降级/加限流说明。
  - **行为修法（可选，需你确认）**：在 `entityInside` 的冷却早退分支加一行，让 NBT 冷却期内原版冷却也被刷新：

    ```java

        player.setPortalCooldown((int) (cooldownEnd - level.getGameTime()) + 1); // 让原版冷却比 NBT 冷却晚 1 tick 到期

    ```

## 五、关键裁决

### 5.1 R-B3 vs R-A3：谁对"超时后是否继续重试"说对了？

- A 组（R-A3）：注释在默认配置下**成立**（玩家必须离开门 300 tick 才能再试）。
- B 组（R-B3）：注释**不成立**，超时后仍会重试。

**裁决：R-B3 成立，R-A3 证伪。** 关键就是一行覆写：

```java
// mc/net/minecraft/world/entity/player/Player.java:467-470
@Override
public int getDimensionChangingDelay() { return 10; }
```

它让 `Entity.getDimensionChangingDelay()`（`Entity.java:2294-2297`）返回的 300 **对玩家无效**。于是失败后的原版冷却只有 10 tick，在 NBT 冷却（默认 100）走完前就归零，且 `entityInside` 在 NBT 冷却期根本不调用 `setAsInsidePortal`（`DisasterPortalBlock.java:153-155`），原版冷却得以正常倒数 ⇒ NBT 一到点就重新登记、重新等待 200 tick ⇒ **周期约 300 tick 的无界重试**。

主审为什么先判错：只 grep 了 `ServerPlayer.java`（确实没有覆写），据此认定玩家沿用 `Entity` 的 300，把 A 组"300"的假设当成了事实。红队直接去读 `Player.java` 才推翻了这个假设。

### 5.2 R-N1：主审自己的结论被推翻

同上：`DisasterPortalBlock.java:312` 的「原版自身的 10 tick 传送冷却」是**正确**的注释，主审一度判为"应为 300"。该条撤回，并在 §八 的修复清单中不再出现。

**两条裁决的共同教训**：本仓库审查里凡是"原版某个数值"的结论，都必须落到**最终生效的那一层**（这里是 `Player`），而不是"基类默认值 + 子类没覆写"的推断。

## 十一、R-B1 决策记录与「B ≈80 tick」的连带必改项

**决策（2026-09-12，用户选择）**：采纳方案 **B** —— `getPortalTransitionTime()` 返回 **80 tick**（≈4.05 s）。

### 为什么 80 恰好等价于原版下界门

- 原版 `NetherPortalBlock` 取 gamerule `playersNetherPortalDefaultDelay`（默认 80），而 `PortalProcessor.processPortalTeleportation` 是 `portalTime++ >= transitionTime`（`PortalProcessor.java:27`）⇒ 两者都是"进门后第 **81** tick 传送"，节奏完全一致。
- 离开门后原版 `decayTick` 每 tick −4（`PortalProcessor.java:40-42`）⇒ 80 → 0 需 20 tick，也与原版相同。
- 客户端 `spinningEffectIntensity` 每 tick +0.0125（`LocalPlayer.java:925`）⇒ 80 tick 恰好涨满 1.0，**传送那一刻扭曲刚好到最强**，紫幕 alpha 也从 0.2 一路到 1.0——这正是"和下界传送门一样"的观感。

§八 第 6 项曾建议"把 `stopRiding()` 移到确认拿到落点之后"——**该修法不成立**。原版 `Entity.handlePortal` 用 `canUsePortal(false)` 作闸门（`Entity.java:2274`；`canUsePortal` 要求 `!isPassenger()`，`Entity.java:2781-2783`），玩家仍在骑乘时 `processPortalTeleportation` 直接返回 `false`，`getPortalDestination` **根本不会被调用**，于是永远拿不到落点。因此"登记即下车"是该范式的必然结果，只能文档说明，不能后移。
