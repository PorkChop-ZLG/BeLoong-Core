## 1. 复检方法

单靠"编译通过"不足以证明兼容：`beloong.mixins.json` 中 `injectors.defaultRequire = 1`，
任何**解析不到**的注入点都会在启动期直接崩溃，而 Mixin 注入点的合法性**不参与编译检查**。
因此本次采用三层验证：

| 层 | 手段 | 覆盖的问题 |
|---|---|---|
| 编译 | `gradlew compileJava`（BUILD SUCCESSFUL） | DS API 成员/签名是否仍存在（方法、字段、类型） |
| 字节码 | `javap -p -c` 反汇编 8973485 产物 | 注入点是否存在、描述符是否匹配、被 `@Redirect` 的 INVOKE 是否仍在方法体内 |
| 源码 | 逐个精读 DS 对应实现 | 语义是否偏移、我们的修复是否已被上游吸收 |

补丁对比窗口：产物 2.0.71 相对上次基线（`d6baf03b3`）新增 4 个 DS 提交：
`5d8bc96c3 fix #1028`、`243d9d2f4 attribute retrieval check`、

### 3.1 DS 2.0.71 的 `flightControl` 是"守卫 + 委托 lambda"结构

字节码显示 2.0.71 的 `flightControl` 本体只有 26 条指令、单一 `return`：

```
0: Minecraft.getInstance()          // 取 client
...
10: ifnull 52                       // player == null  -> return
17: ifne   52                       // isPassenger     -> return
26: ifne   52                       // isPaused        -> return
36: ifne   52                       // LEVITATION      -> return
44: invokedynamic accept:(LocalPlayer)Consumer
49: Optional.ifPresent(...)          // ← 真正的飞行数学在 lambda$flightControl$2 里
52: return
```

四个守卫都是**跳向同一条 return**，不是提前返回，因此 `@At("TAIL")` 依然 100% 可达；
且本模组的 HEAD（摘除零重力修饰符）与 TAIL（回加）之间的 `ifPresent(...)` 同步执行完整飞行数学，
一 tick 内配对成功。`stableHover` 的两处读取（源码 `ClientFlightHandler.java:480,496`）都在该 lambda 内，
位于 HEAD 与 TAIL 之间。✅

我们的飞行修复所依赖的前提也再次确认未变：`flightControl` 仍读取 `Attributes.GRAVITY`，
仍调用 `ServerFlightHandler.isFlying/isGliding`，`Player.isInWater` 仍在场。

## 4. 新发现：新版 DS 吸收了本模组的修复，两处代码现已冗余

DS 在这个窗口内的两个提交（`243d9d2f4 attribute retrieval check`、
`aea39e9d1 add more pvp checks ...`）主动修掉了本模组此前"替 DS 打的补丁"。
这不构成兼容性破坏（两边都不崩），但需要决定是否保留。

### N-1（中）`ProjectileDamageEffectMixin` 的存在理由已被上游消除，且取消路径存在语义偏移

- **上游已修**：`ProjectileDamageEffect.java:42-45`
  ```java
  if (owner instanceof Player) {
      // Attribute is only applied to players and will cause an exception if not present
      damageAmount *= (float) owner.getAttributeValue(DSAttributes.DRAGON_ABILITY_DAMAGE);
  }
  ```
  该属性只 attach 给 `EntityType.PLAYER`，故 `owner instanceof Player` 恰好等价于"具备该属性"——
  正是本模组 mixin 的取消条件 `!owner.getAttributes().hasAttribute(...)` 的补集。
  **即：mixin 会取消的每一个场景，DS 现在都已经安全处理。**

- **语义偏移**：取消路径自行实现伤害
  （`ProjectileDamageEffectMixin.java:41-43`）
  ```java
  float damageAmount = self.amount().calculate(level);
  target.hurt(new DamageSource(self.damageType(), projectile, owner), damageAmount);
  owner.setLastHurtMob(target);          // ← 无 wasHurt 门控
  ```
  而 DS 2.0.71 是
  ```java
  boolean wasHurt = target.hurt(...);
  if (wasHurt && owner != null) { owner.setLastHurtMob(target); }
  ```
  差异仅在 `setLastHurtMob` 的门控：目标实际未受伤（无敌帧、伤害被其他模组事件取消等）时，
  本模组仍会写入 `lastHurtMob`，会影响 `OwnerHurtTargetGoal`（怪物 AI 反击目标）与战利品归属。
  影响面小，但确实是行为偏移。

- **未发生的问题（澄清）**：取消路径**不会**绕过 DS 新增的 PvP 检查。
  DS 的检查条件是 `owner instanceof Player && target instanceof Player && !canHarmPlayer(...)`，
  而取消路径只有在 owner **不具备**该属性时触发，那种 owner 必非 Player，故两边结论一致。

- **处置（2026-09-27 已执行）**：删除 `ProjectileDamageEffectMixin.java`，并连带删除
  `Config.FIX_DS_PROJECTILE_CRASH`（原 `Config.java:64-67`，键 `fixDragonsurvivalProjectileCrash`）
  及其 4 条语言键（`zh_cn.json` / `en_us.json` 各 `.` 与 `.tooltip`），
  同时在 `beloong.mixins.json` 的 `mixins` 列表移除对应条目。
  这与本项目此前"DS 原版处理更新了，就删除本模组对应修复代码"的既定处理方式一致。
  代价：失去一个纯理论场景的保护——owner 是 Player 但其属性表缺失 `DRAGON_ABILITY_DAMAGE`
  （正常不可能，该属性由 `DSAttributes.attachAttributes` 统一 attach 给 PLAYER）。

### N-2（低-中）`DamageEffectMixin` + `ModifierMixin` 已被 DS 新增的 `LevelBasedValueMixin` 覆盖

**崩溃成因（已复核为真）**：1.21.1 原版 `LevelBasedValue.Lookup.calculate(int)` 是

```java
return level <= this.values.size() ? this.values.get(level - 1) : this.fallback.calculate(level);
```

`level == 0` 时走前半句 → `values.get(-1)` → `IndexOutOfBoundsException`。
（`LevelBasedValue.java` 反编译源，`ng_execute/.../transformed/net/minecraft/world/item/enchantment/LevelBasedValue.java`）

触发源是**数据包技能**：DS 自带数据与 BeLoong 自身资源中都没有 `lookup`，
但 `DiHuang-Loong\src\main\resources\data\dragonsurvival\dragonsurvival\dragon_ability\associated_rock_armor.json`
使用了它（`fallback` 为 `linear base=20 per_level_above_first=20`，`values=[10,25,...]`）。
未学习（等级 0）时渲染其 tooltip 即触发。

**上游已修**：新类 `mixins/LevelBasedValueMixin.java`
```java
@Inject(method = "calculate", at = @At("HEAD"), cancellable = true)
private void dragonSurvival$skipLevelZero(final int level, final CallbackInfoReturnable<Float> callback) {
    if (level == 0 && DragonSurvival.PROXY.shouldGuardLevelBasedLookup()) {
        callback.setReturnValue(fallback.calculate(level));
    }
}
```
标志由 `DragonAbility.getInfo` 置位/复位（`:103` 置 true、`:142` 置 false）。

**为什么这正好覆盖我们两个 mixin** ——`getInfo` 全仓库只有一个调用者，
且是纯客户端路径（`AbilityAndPenaltyTooltipRenderer.java:256`，`Minecraft.getInstance()`），
与"渲染未学习技能 tooltip"完全重合：

| 我们的 mixin | 生效路径 | 是否落在 `getInfo` 窗口内 |
|---|---|---|
| `DamageEffectMixin` | `DamageEffect.getDescription` ← `AbilityTargeting.getAllEffectDescriptions:135,141,145` ← `DragonAbility.getInfo:131`（唯一调用者） | ✅ 是 |
| `ModifierMixin` | `ModifierEffect`/`ModifierWithDuration.getDescription(int):61` ← `getInfo` | ✅ 是 |
| `ModifierMixin` 的窗口外路径 | `ModifierWithDuration.Instance.getDescription():116-117` ← `EffectRenderingInventoryScreenMixin:173` | ❌ 否，但等级来自 `appliedAbilityLevel()`，而 `tickActions` 受 `canBeCast()` ⇒ `isUsable()` ⇒ `level > 0` 门控（`DragonAbilityInstance.java`），存量实例恒 ≥ 1 |
| `ModifierMixin` 的窗口外路径 | `DragonBodyButton:206`（字面量 1）、`GrowthCrystalButton:108`（显式等级） | ❌ 否，但均非 0 |

**⇒ 等级 0 已不存在任何"未被 DS 守卫覆盖且会被我们 mixin 接住"的路径。**
两个 mixin 仍能正常注入（见 §2），保留不会崩，代价只是**显示数值被改写**：
以 `associated_rock_armor.json` 为例，等级 0 时

- DS 守卫：`fallback.calculate(0)` = `20 + 20×(0−1)` = **0**
- 我们的钳制：`values[0]` = **10**

**处置（2026-09-27 已执行）**：用户裁定**删除** `DamageEffectMixin` 与 `ModifierMixin`
（同时从 `beloong.mixins.json` 的 `client` 列表移除），完全交还 DS 的 fallback 口径——
未学习技能描述自此由 DS 决定显示值（上例显示 **0** 而非 **10**）。
删除后 `client` 列表剩 5 项（`ClientFlightHandlerAccessor`、`ClientFlightHandlerMixin`、
`BossClientEventsMixin`、`FSweepButtonControlMixin`、`AsteorBarHealthFixMixin`），
DS 侧 mixin 文件由 17 个减至 14 个、注入点由 23 个减至 19 个。

### N-3（信息）DS 新守卫为客户端专属且未用 try/finally

`getInfo` 里 `setShouldGuardLevelBasedLookup(true)` / `(false)` 直接前后包裹，无 `try/finally`。
若 `getInfo` 中途抛异常，标志会残留为 true，导致该客户端此后所有 `Lookup.calculate(0)`
静默返回 fallback。这是 DS 自身的健壮性问题，**与本模组无关**，也不影响我们
（我们的钳制在更早的调用点短路，压根不会以 0 进入 `Lookup`）。仅作记录。

### N-4（低，沿用 I-5）lambda 裸序号注入仍然脆弱，但本轮未破

`DragonDestructionHandlerMixin` 依赖 `lambda$destroyBlocksInRadius$1`、
`lambda$checkAndDestroyCollidingBlocks$0` 两个**编译器生成的裸序号名**。
本轮 DS 在 `checkAndDamageCrushedEntities` / `checkAndDestroyCollidingBlocks` 内新增了
PvP 检查与 `setLastHurtMob`（`aea39e9d1`），javap 确认**未新增 lambda、序号未位移**，
两个目标方法描述符与上一版逐字一致：

```
private static void lambda$destroyBlocksInRadius$1(BlockEvent$BreakEvent, float, ServerPlayer, BlockPos);
private static void lambda$checkAndDestroyCollidingBlocks$0(MiscCodecs$DestructionData, PlayerTickEvent, BlockPos);
```

也就是说这次是**运气**而非稳定性——DS 只要在该类里再插一个 lambda 且序号排在前面就会破。
I-5 的加固选项（改为注入具名方法 + 局部捕获，或改用 `@Slice`/`@Redirect` 到更稳的锚点）依旧开放。
