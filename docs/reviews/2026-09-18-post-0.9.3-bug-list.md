## 一、严重（7 条）

### 1. `terrablender` 未锁版本，旧版会导致服务端启动失败

- **位置：** `src/main/templates/META-INF/neoforge.mods.toml:137`、`src/main/java/com/zonlong/beloong/mixin/CloneParameterListMixin.java:79`
- **问题：** `:79` 的 `receiver.clone()` 位于 `try {`（`:93`）**之外**，无任何防护。TerraBlender ≤ 4.1.0.7 的 `clone()` 体内含 `newUniqueness.get()`，而本项目的 `@Redirect` 拦截了唯一初始化调用点并改为在克隆体上初始化 ⇒ `receiver` 永不被初始化 ⇒ `newUniqueness == null` ⇒ **NPE**。
- **后果：** NPE 穿透无 try/catch 的 `LevelUtils.initializeOnServerStart` 循环 ⇒ **服务端启动失败**。可达性已证：BWG 2.6.0 自己只要求 `terrablender [4.1.0.0,)`，把 pre-fix 版本放了进来。
- **修法：** `mods.toml` 补 `versionRange="[4.1.0.8,)"`。

### 2. 4 个 mixin 未遵守项目自己的可选依赖约定，第三方改名会启动崩溃

- **位置：** `src/main/resources/beloong.mixins.json:49-51`、`mixin/betterendisland/DragonSummonMixin.java:23`、`mixin/betterendisland/ExitPortalUtilsMixin.java:24`、`mixin/NetMagnetItemMixin.java:27`、`mixin/AsteorBarHealthFixMixin.java:26`、`mixin/FSweepButtonControlMixin.java:23`
- **问题：** 项目约定的写法是 `@Pseudo` + `require = 0`（样板见 `mixin/legendarymonsters/AnnihilationPursuerDamageCapMixin.java:19-26`，是 5 个里唯一照做的）。这 4 个没写。
- **后果：** 模组缺席时静默跳过；**第三方改名时启动崩溃**。更糟的是 `asteorbar`/`fsweep` **根本不在 `mods.toml` 里**，`betterendisland`/`beyonddimensions` 也**没有 `versionRange`** ⇒ 崩溃现场查不到任何依赖线索。
- **修法：** 按样板补 `@Pseudo` + `require = 0`；或把这两个模组补进 `mods.toml` 并加 `versionRange`。

### 3. waterlogged 方块被判为「空」，点亮门时无掉落吞掉玩家方块

- **位置：** `src/main/java/com/zonlong/beloong/block/LoongPalacePortalShape.java:209-214`、`block/LoongPalacePortalActivation.java:42`
- **问题：** 把「**流体状态**是水」当成「空格」与「注水触发」。而 waterlogged 方块的流体态由方块态派生（`LevelChunkSection.java:42-43`、`StairBlock.java:255-256`）⇒ 判定面比设计 §3.1 的「空气 ∨ 水 ∨ 门方块」宽。
- **后果：** 在完整荧石框内放**一个 waterlogged 台阶**就立刻点亮门，并把框内 waterlogged 方块**无掉落静默替换**成门方块（`createPortalBlocks:233-238`）。**唯一"玩家可自然触发且造成物品损失"的缺陷。**
- **修法：** 把「流体是水」与「方块是水」区分开，判定面收回到设计 §3.1。

### 4. 上行兜底 Y 在第 1 个未就绪 tick 就生效，落点可能嵌进实心方块

- **位置：** `src/main/java/com/zonlong/beloong/block/DisasterPortalBlock.java:281-292`（构成要件在 `teleport/DimensionTeleport.java:52-55`）
- **问题：** `:283` 把 `player.getY()` 作 `fallbackY` 传下去，而该 API 是 `resolve()` 返回 null 就**同 tick** 用兜底 ⇒ 上行方向只要目标区块不在内存就立刻传送，`waitForDestination`/`failDestination` 在上行**结构上不可达**。这与 `2026-09-16-disaster-portal-bidirectional-1to1-design.md:206`(D5)、`:280`(V3)、`docs/天灾维度总设计.md:802` **三处明文**以及该行自己的注释全部矛盾。
- **后果：** 跳过高度图落点，且 `DimensionTeleport.java:68-71` 不做碰撞搜索 ⇒ **可能把玩家嵌进实心方块**（原版 `NetherPortalBlock.java:224` 有 `PortalShape.findCollisionFreePosition`）。
- **实测铁证：** `D:\BeLoong\.minecraft\versions\BeLoong\logs\` 里 **6 次上行传送的 `waited=` 全部是 `1`**，而 3 次下行是 `84/165/206`。
- **修法：** 让上行也等满 600 tick 再兜底（建议），或改文档并补落点安全搜索。

### 5. 照文档重跑贴图脚本会静默改写 2/10 张已提交贴图（已实跑复现）

- **位置：** `tools/convert_element_sources.py:293-313`、`tools/generate_light_dark_sprites.py:254-262`
- **问题：** 执行 `python tools\convert_element_sources.py --install`（`tools/README-element-essence.md:46` 记载的方式）产出的冰是 **12×15**、风是 **13×15**，而仓库提交的是 **12×14 / 13×14** ⇒ 一次照文档操作就静默改掉 **2/10 张**。
- **加重：** 备份落在被 `.gitignore:52` 忽略的 `preview/` 下；另一个脚本**完全没有备份**；`tools/README-element-essence.md:33` 还把备份位置写成 `textures/item/`（脚本注释 `:295-297` 判定会让 jar 多发一个 sprite 的有害旧位置）。
- **修法：** 脚本对已存在的目标文件做**内容比对后拒绝覆盖**。

### 6. 技能 `cooldown: 5.0` 的单位是 tick 不是秒，双重冷却差 20 倍

- **位置：** `src/main/resources/data/dragonsurvival/dragonsurvival/dragon_ability/tp_loong_palace.json:35`
- **问题：** DS 的 `activation.cooldown` **无秒→tick 换算**（锁定 jar 2.0.67 `javap -p -c` 实证：`tickCooldown` 每次 `cooldown - 1`、`cooldown()` 返回裸 int）⇒ `5.0` = **5 tick**。而 `TeleportCooldown.TICKS` 在 `7498df6` 已硬编码为 **60**。
- **后果：** 技能在传送后第 5 tick 就能再按，NBT 冷却还剩 55 tick ⇒ 这 55 tick 内每次按键只弹 actionbar —— **正是该改动想消除的现象**，方向与文档相反。
- **修法：** `"cooldown"` 改 `60.0`；或改文档（`2026-09-16-loong-palace-teleport-api-design.md:68-70`、`-implementation.md:22,74`）。

### 7. 龙宫传送改用 `changeDimension` 后丢失 `POST_TELEPORT` 落点票据

- **位置：** `src/main/java/com/zonlong/beloong/teleport/DimensionTeleport.java:68-71`
- **问题：** 只有 `ServerPlayer.teleportTo(ServerLevel,…)` 申领该票（`ServerPlayer.java:1534-1553`），`changeDimension`（`:887-941`）**不申领**；而去龙宫的两条调用方（`TpLoongPalaceEffect`、`LoongPalacePortalBlock`）**都不调** `CoordinateLanding.requestChunk`（全仓仅 `DisasterPortalBlock.java:200,315` 调用）。
- **后果：** `2026-09-12-dimension-transport-nonblocking-design.md:36-38` 与 `memory/learned-patterns.md` 用来论证"不需要等待机制"的**唯一依据失效**；而 `DimensionTransportHandler.java:94-96` 的注释反而新写了这句错话。
- **修法：** 补 `post.andThen(DimensionTransition.PLACE_PORTAL_TICKET)`，或让调用方补 `requestChunk`。

## 二、中等（10 条）

### 8. `"安装脚本自动清理 .mcmeta"` 的护栏不存在

- **位置：** `tools/convert_element_sources.py:293-313`、`tools/generate_light_dark_sprites.py:254-262`
- **问题：** `docs/plans/2026-09-13-element-essence-design.md:337`（写进了设计契约的验证计划）、`memory/learned-patterns.md:507`、`memory/decisions-log.md:672` 三处都声称脚本会自动清理残留 `.mcmeta`，但实测 **`tools/` 下 `mcmeta` 零命中**，被点名的 `generate_element_sprites.py` 早已删除。
- **后果：** 防回归能力实际等于"人记得"，而这正是该条目当年被写下来的原因。
- **修法：** 两个 `--install` 分支各加 3 行兜底删除；或把表述降级为人工 checklist 并修掉那三处。

### 9. `SpawnSpreadResolver` 的"水面排除"判定与原版取反

- **位置：** `src/main/java/com/zonlong/beloong/teleport/SpawnSpreadResolver.java:105`
- **问题：** 原版是 `j <= i && j > OF`，本实现写成 `worldSurface > motionBlocking && worldSurface > oceanFloor`。
- **后果：** 地表之上有高草/花/火把的列被**错误拒绝**（原版接受）；水列只是靠 `:112` 的流体 break 间接拒绝。类 javadoc 声称"复刻原版"不成立。
- **修法：** 按原版条件重写。

### 10. 落点扫描用 `Level#getBlockState`，内部是 `requireChunk=true` 的阻塞路径

- **位置：** `src/main/java/com/zonlong/beloong/teleport/SpawnSpreadResolver.java:111`、`block/LoongPalacePortalShape.java:38-39`（**两处独立发现**）
- **问题：** `Level.getBlockState`（`Level.java:406-413`）→ `getChunk` → `getChunk(x,z,FULL,**true**)` → `ServerChunkCache.java:136-152` 的 `managedBlock`。当前不阻塞**只因为** `:94` 的 `getChunkNow` 刚把同一区块放进了 4 项 `lastChunk` 缓存（`ServerChunkCache.java:180-184,194`）或 `currentlyLoading` 旁路 —— **一条无注释、无断言的隐式契约**。`LoongPalacePortalShape` 的类头还写了「本类不做区块加载」这个**假 invariant**。
- **后果：** 一旦缓存被驱逐或平台改策略，就退化成 2026-09-12 那次主线程 `managedBlock` 自旋。
- **修法：** 改用已拿到的 `LevelChunk`：`chunk.getBlockState(pos)`（与同方法的高度图调用同源，天然不阻塞），并在 javadoc 写明不要改回。

### 11. `@Shadow` 缺 `@Mutable` 却写 final 字段

- **位置：** `src/main/java/com/zonlong/beloong/mixin/PossibleBiomesFilterMixin.java:77-78`（字段在 `:131`）
- **问题：** 同项目 `mixin/ParameterListAccessor.java:53` 用对了同一手法。平台侧 `MixinApplicatorStandard.java:399-412` **只在 `@Mutable` 时**才剥 `ACC_FINAL`。用 ASM 生成等价类**必抛** `IllegalAccessError`。
- **⚠️ 注意：** 运行时证据**反向**（`latest.log:848` 表明注入体没抛），故**后果待确认**；一次 `-Dmixin.debug.verbose=true` 启动即可定论。
- **修法：** 直接补 `@Mutable`，不必等复现。

### 12. `Config.java` 默认召唤方块指向完全未声明的模组，且不校验

- **位置：** `src/main/java/com/zonlong/beloong/Config.java:414`、`compat/betterendisland/DragonSummonHelper.java:39-42`
- **问题：** 默认值指向 `bosses_of_mass_destruction`，而该模组**在 `mods.toml` 与 `build.gradle` 里都不存在**；代码也不校验方块是否存在。
- **后果：** **静默死功能**（末影龙召唤仪式默认不可用且无任何提示）。
- **修法：** 加存在性校验并在不可用时**响亮报错**，或补声明。

### 13. `AmplificationCharmEffect` 实现 `ICurioItem` 但无守卫

- **位置：** `src/main/java/com/zonlong/beloong/item/effect/AmplificationCharmEffect.java:20`
- **问题：** `curios` 在 `mods.toml:149-153` 是 **optional**，此处**无 `isLoaded` 守卫**。
- **后果：** 当前不可触发（`lendercataclysm` 把 curios 声明为 required，FML 强制校验）——属「**借来的安全**」。
- **修法：** 补 `isLoaded("curios")` 守卫，或把 curios 声明补正。

### 14. `biomeswevegone` 未锁版本，旧版会让全部 BWG 映射失效

- **位置：** `src/main/templates/META-INF/neoforge.mods.toml:131`
- **问题：** `javap` 实测锁定 2.6.0 是 `biomes` + 非 Supplier（**本项目反射正确**），但旧构建是 `enabledBiomes` + `Supplier` ⇒ `getField("biomes")` 抛 `NoSuchFieldException`。
- **后果：** 装旧 BWG 时**全部 BWG 映射目标**判为不可用 ⇒ 天灾维度退回原版群系。
- **修法：** 补 `versionRange`。

### 15. region 树账目缺少设计要求的 ERROR 升级

- **位置：** `src/main/java/com/zonlong/beloong/worldgen/DisasterBiomeSubstitution.java:423-425`
- **问题：** 设计 `2026-09-11-disaster-phase2-implementation.md:344`（T3）要求「残留集合非空时按 **ERROR** 级别报出」，实现只有 INFO。同时 `logPossibleBiomes:485` 又对三个"残留本属正常"的维度打同一个 `(!)` 标记。
- **后果：** 这是**唯一**能发现 region 树泄漏的仪器；标记贬值后真正的残留反而不显眼。
- **修法：** 按设计要求升级为 ERROR，并把 `(!)` 限定到天灾维度。

### 16. 进度 JSON 的 `parent` 若不存在，子进度被移出进度树（奖励照给、toast 与界面永远没有）

- **位置：** `docs/plans/2026-09-16-claw-sword-advancement-design.md:132`（模板仍带 `"parent": "beloong:claw_sword/swap"`）
- **问题：** 包侧若只建 `kill` 不建 `swap`：`AdvancementTree.java:68-72` 的 `tryInsert` 恒 `false` → `:60` 只留一行 `ERROR Couldn't load advancements` → 子进度**被移出进度树**，但 `ServerAdvancementManager` 的 map 里还在 ⇒ 判据照旧授予、进度照旧存档；而 `PlayerAdvancements.java:215-220` 的 `markForVisibilityUpdate` 拿到 null ⇒ **永不进 `visible`** ⇒ `:265-269` 的 `flushDirty` **永不发客户端**。
- **后果：** **奖励与聊天公告照给，toast 与进度界面永远不出现** —— 症状极具欺骗性。
- **修法：** 在模板旁显式声明"父级必须存在"，或改为不依赖父级的单条。

### 17. ambient 音效改写的根因判断与平台源码矛盾（该改写是等价改写）
