## 一、结论摘要

1. **无 [阻塞] 级问题。** 渲染管线在正确性层面整体良好：12 步矩阵是标准共轭 `A·T·A⁻¹`（与参考模组逐位同序同角）、三个混合模式逐字正确且无状态泄漏窗口、状态复位与原版逐项对齐、几何缓存的两条纪律严格遵守、`FACES` 六面法线全部朝内（剔除被重新启用也不丢面）、提前 `return true` 未遗漏任何必要恢复。
2. **唯一的资源级问题是显存**：9 张贴图占 **180.77 MiB**，且**加载后整个会话常驻、无释放路径**。可保守降到 **≈45.4 MiB（省 74.9%）**。这是本子系统最大的单项成本，且此前从未被评估。→ **显存部分已达成：现为 45.38 MiB（−135.39 MiB，−74.9%）**，分两轮实施完（第九、十节）。**「会话常驻、无释放」这一半仍未处理**（见第十节 §10.4）。
3. **唯一的代码缺陷是 [次要]**：进入龙宫时首帧会用上一次离开时的陈旧 alpha 渲染（窗口 ≤1 client tick）。
4. **唯一的视觉偏差是 [次要]**：日月**贴图**相对原版在天空平面内滚转 90°（位置、高度、交替时刻逐位一致；仅月牙朝向不同），且与参考模组行为一致。→ 第九节的重制**刻意未做旋转**，该问题状态不变。
5. **权威文档本身有 11 处断言需修正 + 7 处自洽性问题**，其中 3 处由两个批次独立命中。文档的「零视觉变化可证明」这一论证**依据无效**（结论仍成立，但需换一个论据）。→ **总设计文档已按本案结论修正 4 处**（§8.1 缓冲字节数、§9.5 贴图表、§12.3 显存、§13 优化记录）；其余 D 项待办见第七节。
6. 有 **4 项**曾被怀疑但**核验为非问题**（详见第五节），建议在后续工作中不再重复怀疑。→ 第八节又**结案 3 项**（`skyboxRotation` 默认值、N8 双太阳、`FACES` 来源）。

## 二、问题清单

### 2.1 [重要 → 已解决（显存部分）] I1 —— 天空贴图显存 180.77 MiB，且整个会话常驻无释放

- **证据**：实测 9 张贴图（自读 PNG 头）合计 RGBA8 显存 **180.77 MiB**（189,548,544 B）。解码路径 `NativeImage.read` 恒请求 4 分量并以 `GL_RGBA`/`GL_UNSIGNED_BYTE` 上传（`NativeImage.java:100-118,469,851-856`）。
  释放路径只有 `TextureManager.release`（本模组从未调用）与 `TextureManager.close`（仅 `Minecraft.java:1128` 关闭时调用）；`AbstractTexture.reset` 让 `F3+T` 复用同一对象与 GL id。**维度切换 / 退出世界都不经过 TextureManager。**
- **影响**：只要进过一次龙宫并经历一个昼夜，**所有维度、会话剩余时间都背着这 180.77 MiB**。`skybox/sun.png` / `sunflare.png` 在没经历黄昏/黎明的会话里不加载，但其余 7 张必然加载。
- **与文档的关系**：§9.5 / §12.3 已正确量化总量，**但未涉及"常驻无释放"**；§8.4 只论证了几何缓冲「无失效面」，而**贴图与缓冲正相反**（会重载、会常驻）。
- **处置结果**：**显存已降至 45.38 MiB（−135.39 MiB，−74.9%）**，达成本项当初给出的「可保守降到 ≈45.4 MiB」目标。
  两轮都只采用「整体等比降采样」，因为所有天空盒图层共用一份立方体 UV 表（`FACES`），
  **裁剪必须改代码**（逐层 UV 表 + 逐层 `VertexBuffer`）——那是本项当初没有纳入的方案，见第十节讨论。
  - 第一轮（第九节）：月相 30.52 → 3.13、`mask_moon` 24.00 → 6.00 MiB。
  - 第二轮（第十节）：`day`/`night`/`stars`/`mask`/`sun` 5×24.00 → 5×6.00 MiB，并补齐 `.mcmeta`。
- **仍未解决的那一半**：**「加载后整个会话常驻、无释放路径」**。降采样只把常驻量从 180.77 压到 45.38 MiB，
  **没有改变「进过一次龙宫就永久占着」这个性质**。要真正解决需自定义 `AbstractTexture` 子类 +
  离开维度时 `TextureManager.release(rl)`，代价是再次进入时重新解码（与 I2 的卡顿同源）。见 §10.4。

### 2.2 [重要] I2 —— 首次绘制同步解码+上传，入夜那一帧同时上传 4 张大图（≈96 MiB）

- **证据**：`CubeAtlasSkyRenderer.java:135` 的 `setShaderTexture` 仅在该层 `alpha > 0` 时执行（`DramaticSkyRenderer.java:143-153`）；调用链 `RenderSystem._setShaderTexture:722-728` → `TextureManager.getTexture:109-117` → `register:62-74` → `loadTexture:90-107` → `SimpleTexture.load:29-49`；因 `RenderSystem.isOnRenderThreadOrInit()` 为真，`doLoad:51-54` **内联**完成 readResource + stb 解码 + `prepareImage` + `_texSubImage2D`。全仓 grep `preload|PreloadedTexture` **0 命中** ⇒ 无预加载路径。
- **最坏同帧**：第 0/1/2/4 层的 alpha 来源同为 `NIGHT`、淡入区间同为 `13333→13666`（`DramaticSkyRenderer.java:29-32`），`moveTowards` 首步 0.05 > 0 ⇒ stars + mask_moon + mask + night **在同一帧一起加载**（PNG 2,044 KB / 上传 **96 MiB**）。
- **影响**：入夜、首次进入维度、每次 `F3+T` 的一次性掉帧。
- **与文档的关系**：§4/§5 只描述 alpha 门控，§9.5/§12.3 只算显存 ⇒ **文档未涉及**。
- **修复建议**：进入维度时用 `TextureManager.preload(rl, Util.backgroundExecutor())` 预取。**注意**：`PreloadedTexture.getId()` 在加载完成前返回未初始化 id，该层会短暂不可见，需与 §5 的 alpha 淡入配合评估。

### 2.3 [重要] I3 —— `mask_moon.png`：31 KB 的 PNG 占 24 MiB，内容仅 88×88 纯黑圆盘

- **证据**（逐像素实测）：6,291,456 px 中仅 **6,099 px（0.097%）** 非透明；只有 **12 种**不同 ARGB；全部 RGB = `(0,0,0)`；内容是一个 **88×88 的纯黑 alpha 圆盘**，bbox `x[468,555] y[468,555]`。
- **影响**：单张性价比落差最大者——**24 MiB 存 6 KB 内容**。
- **与文档的关系**：§9.5「几乎是全透明图，24 MB 基本是浪费」**实测成立且比描述更极端**。
- **修复建议**（择一）：① 整体降采样至 1536×1024（省 18 MiB，配合 `blur:true` 减轻块状化）；② 把圆盘裁成独立 128×128 贴图 + 独立 quad（**省 23.9 MiB 且零质量损失**，但需改 UV 与绘制代码）。

### 2.4 [次要] M1 —— 进入龙宫时首帧渲染陈旧 alpha

- **证据**：`reset()` **只挂在 tick 路径**（`LoongPalaceSkyTickHandler.java:38-40`，全仓库唯一调用点），而 `render` 只在 `!initialized` 时重建 alpha（`DramaticSkyRenderer.java:125`）；离开龙宫后 `initialized` 恒为 true。换维度所在帧若 tick 数为 0（`Minecraft.java:1161` runAllTasks 换 level → `1165-1168` tick 循环 → `1201` render；>20 FPS 时约 **2/3** 的帧 `i=0`），首帧用上一次龙宫访问时冻结的 alpha。
- **影响**：窗口 ≤1 client tick（≈50 ms；60 FPS 下典型 1 帧，高帧率下最多约 9 帧）。`ReceivingLevelScreen` 的模糊/压暗背景会削弱可见度。用 `/time set` 造成时间差时，陈旧值与目标可差满量程（如午夜进龙宫先闪一帧正午天空）。
- **与文档的关系**：**文档未涉及**。§12.2 问的是另一个问题；§12.4 把「进出维度」标为已确认，**未覆盖帧级时序**。
- **修复建议**：把「进入龙宫」的判定上移到渲染侧——在 `LoongPalaceSkyEffects.renderSky` 中比对 `level.dimension()` 与上次渲染的维度，变化时先 `reset()` 再 `render()`。**注意 §8.2 的禁止项：不要**在 `reset()` 中加入丢弃几何缓冲的钩子。

### 2.5 [次要] M2 —— 日月贴图相对原版滚转 90°（位置/轨迹正确）

- **证据**：`SkyDecorationsRenderer.java:62` 应用 `DECORATION_ROTATION` = `(0,0,1,…)`（`SkyRotation.java:19`）⇒ 净变换 `R_z(θ)`；原版为 `R_y(−90)·R_x(θ)`（`LevelRenderer.java:1658-1659`）。由 `R_y(−90)R_x(θ) = R_z(θ)R_y(−90)`（θ=90° 数值验证）得 **本模组矩阵 = 原版矩阵 · `R_y(+90)`**。
  显式例（θ=90°，太阳 v0 局部 `(−30,100,−30)`）：本模组 `(−100,−30,−30)`，原版 `(−100,30,−30)`。日月**中心**相同（`R_y` 不动 Y 轴）⇒ 位置、高度、交替时刻逐位一致。纹理基换算：本模组 `(u,v) = (原版 v, −原版 u)`。
- **影响**：太阳贴图径向对称 ⇒ 不可见。`moon_phases.png` 是原版同名贴图的替换贴图 ⇒ **月牙朝向偏 90°**（相位索引本身正确，错的是朝向）。
- **与文档的关系**：**文档未涉及**。与参考模组**一致**（`AbstractSkybox.java:256` 把原版那行 `YP(−90)` 注释掉了；`Rotation.java:12` 的 `DECORATIONS` 与本模组 `DECORATION_ROTATION` 逐字段相同）⇒ 属「忠实移植参考模组」，非独创偏差。
- **修复建议**：`SkyRotation.java:19` 的 `static` 由 `(0,0,0)` 改 `(0,−90,0)`，得 `M = R_z(θ)·R_y(−90) ≡ R_y(−90)R_x(θ)`，不动位置而朝向对齐原版。
  ⚠ **前置条件**：本审查**无法排除**「资源包的 `moon_phases.png` 本就按滚转 90° 绘制」。**改前必须先目视比对月牙朝向**，否则可能把「正确」改成「错误」。

### 2.6 [次要] M3 —— 无任何关闭自定义天空的开关（同项目已有先例）

- **证据**：`Config.java` 中与天空相关的开关只有 `DISABLE_MALKUTH_HELLSCAPE_SKYBOX`（`:26-28`，针对 FDBosses 的 Malkuth 天空盒，其 tooltip 明写「**解决渲染异常的问题**」）。全项目 grep `disableSky|enableSky|skyEnabled|customSky` **0 命中**；`[loong_palace]` 配置节（`:217-290`）只涉及环境保护。
- **影响**：若龙宫自定义天空在特定驱动 / 光影组合下出现渲染异常，**用户没有退路**——而项目已经为「天空盒出渲染异常」建立了加开关的先例。
- **与文档的关系**：文档未涉及。
- **修复建议**：增加一个客户端布尔配置（默认 `true`），关闭时 `LoongPalaceSkyEffects.renderSky` 直接返回 `false` 以回退原版天空。命名与文案可对齐 `disableMalkuthHellscapeSkybox`。

### 2.7 [次要 → 已解决] M4 —— 月相图集：16-bit 精度被丢弃、分辨率远超需要

- **证据**：PNG 头 `depth=16, colorType=2`；`NativeImage.read` → `STBImage.stbi_load_from_memory(..., RGBA.components)`，请求的恒是 **8-bit 分量** ⇒ 降位到 8-bit、不异常。实测 889,778 个红通道采样中 **86.21% 是 257 的倍数**（即仅 8-bit 有效精度）。
  原版对照（从 `neoforge-21.1.236-client-extra-aka-minecraft-resources.jar` 取字节读头）：`environment/moon_phases.png` = **128×64 depth 8 colorType 3，835 B**；`environment/sun.png` = 32×32 colorType 3。本模组原为 4000×2000，月相 cell 1000×1000。
- **分辨率换算（含一处更正）**：本报告初版写「盘面约 520 px、屏幕约 349 px」，**两项均有误**。逐像素实测满月盘面为 **425×425**（bbox x[288,712] y[288,712]，居中），而 349 px 是**整个四边形**的屏幕尺寸。正确推导：
  ```
  四边形 ±20 @ 距离 100 → 半角 atan(0.2) = 11.31°
  focal = (1080/2) / tan(35°) = 771 px
  四边形屏幕 = 2 × 771 × 0.2 = 308.5 px
  盘面屏幕   = 308.5 × (425/1000) = 131 px
  ```
  ⇒ 原图 425 texel ↔ 131 px = **3.25× 过采样**。
  ⚠ **裁剪会改变盘面的相对占比**：裁到 560 后画布只覆盖原格 56%，输出 320 时盘面 = `425 × 320/560` = **243 texel** ⇒ 相对 131 px 是 **1.85×** 余量（而非按 `320/1000` 直算的 1.04×）。
- **与文档的关系**：§9.5/§12.3 关于「16-bit 无意义」的结论**正确**。
- **处置**：**已实施**（见第九节）。原建议「降至 2000×1000」已由更彻底的「拆 8 张 + 裁黑边 + 320×320」取代。

### 2.8 [次要 → 已解决] M5 —— 天空盒图集为 `GL_NEAREST` 且无 mipmap；mcmeta 可零显存换取 `GL_LINEAR`

- **证据**：`SimpleTexture.doLoad` 硬编码 `prepareImage(getId(), 0, w, h)` 且 mipmap 参数写死为 false ⇒ **即使加 mcmeta 也拿不到 mipmap，只能拿到 `GL_LINEAR`**（`blur:true`）。
- **状态**：月相 8 张 + `mask_moon` 于第九节加；`day` / `night` / `stars` / `mask` / `skybox/sun` / `sunflare`
  于第十节加。`stars.png` 在 §10.7 曾**一度**改回 `GL_NEAREST`（删除 mcmeta）以保星点锐度，
  **但实机目视后用户判定 LINEAR 更好，mcmeta 已加回**。
  ⇒ 现状：**7 张图集 + 月相 8 张全部 `GL_LINEAR`**。
- **影响**：不改变显存，但决定降采样的观感代价——平滑渐变层几乎无损；点/盘状特征（`stars` / `sunflare`）会块状化。
  **这项改动与第十节的降采样是强耦合的**：天空盒各面只覆盖屏幕采样的 0.71×，降到 2× 后仅 0.36×，
  每个 texel 放大到约 2.8 px；**若用 NEAREST 就是马赛克**，加 mcmeta 拿到 LINEAR 才把代价压成「变柔」。
- ⚠ **本项改动造成过一次真实回归（§10.7）**：加 `GL_LINEAR` 后，因 `FACES` 的 UV 精确落在图集格子边界，
  双线性取样把邻格的边缘纹素混进每个面边缘，在立方体棱上产生明显的**黑缝**。
  **「加 mcmeta」与「半纹素内缩」必须成对做**——本报告在第九/十节初稿中只写了前半句，是漏项。

### 2.9 [次要] M6 —— `void_start_platform` 声明被 `features:false` 门控失效（死声明）

- **证据**：`dimension/loong_palace.json` 的 flat 生成器写 `"features": false`；原版门控 `FlatLevelGeneratorSettings.java:150`：
  ```java
  boolean flag = (!this.voidGen || biome.is(Biomes.THE_VOID)) && this.decoration;
  if (flag) { ...从 biomegenerationsettings.features() 复制... }
  ```
  而 `features` → 内部 `decoration`（`Codec.BOOL.fieldOf("features").orElse(false)`，`:44`）。⇒ `decoration = false` ⇒ 群系里声明的 `minecraft:void_start_platform`（`worldgen/biome/loong_palace.json` 的 `features[10]`）**永远不会生成**。
- **影响**：死声明。是否需要该平台取决于龙宫出生点是否由模板/结构保证。
- **修复建议**：二选一——删除该声明，或按需把 flat 生成器的 `features` 打开。

## 八、审查后补充调查（原资源包取证）

初稿把两处列为「无法判定 / 无据」。后续在原始资源包
`D:\Minecraft\闭源模组解压文件\optifine-master\Dramatic Skys`（OptiFine / MCPatcher / Celestial /
fabricskyboxes 四种格式并存）中取证，**全部得到结论**。

### 8.1 `skyboxRotation` 默认值是 `true` —— 移植正确

NeoForgeSkyboxes `util/object/Rotation.java` 的 CODEC：

```java
Codec.BOOL.optionalFieldOf("skyboxRotation", true)
```

而 fabricskyboxes 原始定义中，凡使用 `rotY` 的 7 个层（`sky2_day` / `sky3_mask` / `sky3_night` /
`sky4_day` / `sky4_sunset` / `sky5_sunrise` / `sky5_night`）**都省略了该字段** ⇒ 取默认 `true`。
这与我们 `DAY_ROTATION` / `SUN_ROTATION` 的 `true` **一致**。

⇒ §6.2 的分支归属（`{DAY,SUN}` → `skyboxRotation=true` 匀速；`{STAR,FLARE,DECORATION}` → `false`
原版曲线）与来源包**完全吻合**。此前怀疑过的「均匀 vs 原版曲线」不成立。

### 8.2 N8 结案：两套「太阳」是资源包原设计

原始定义里 `sky4_sunset` / `sky5_sunrise` 用 `skybox/sun.png` + `rotY=1.0`（匀速 Y 轴，仰角恒定），
而 `sunmoon.json` / `sky8_sunmoon.json` 是 `type: "monocolor"` 配 `decorations.showSun/showMoon: true`
——**日月装饰**由这一层启用，与天空盒的 `sun.png` 层是两套独立机制。

⇒ **N8 改判为「确认设计如此，无缺陷」。**

### 8.3 我们的 `FACES` 表是 Celestial 定义的**逐字移植**

`celestial/sky/overworld/objects/` 下 `sky1_stars.json` / `sky2_mask_moon.json` / `sky3_mask.json`
各自内联了 **24 个顶点**（6 面 × 4）。逐条比对：坐标、**UV 数值与顺序**与
`CubeAtlasSkyRenderer.FACES` **完全一致**。

⇒ 这是对几何表最强的来源验证——它不是自创，而是原定义的直接翻译。

### 8.4 那 8 张 `celestial/moon/*.png` 在全包里**没有任何引用**

唯一的月亮定义（`objects/moon.json`、`objects/sky9_moon.json`）都指向 **图集**
`minecraft:textures/environment/moon_phases.png` 且 `"has_moon_phases": true`。
全包 grep `celestial/moon|full_moon|waxing|waning|first_quarter|third_quarter` **零命中**。

⇒ **图集才是权威月亮贴图**；8 张独立文件是未被引用的遗留（1000×1000 8-bit **RGBA**）。
**不能直接替换**：其 alpha 是恒定的 423 直径硬掩膜、盘外 RGB=0，而月亮用 `SRC_ALPHA, ONE`
混合 ⇒ RGB 会再乘 alpha，**月亮会变小变暗**。

### 8.5 `mask_moon.png` 的用途取证

**权威定义**（`fabricskyboxes/sky/sky2_mask_moon.json` 与对应的 Celestial 定义）：

| 项 | 值 | 与我们的 `LAYERS[1]` |
|---|---|---|
| texture | `skybox:mask_moon.png` | ✅ 同 |
| blend | `alpha` | ✅ 同 |
| fade | `13333/13666 .. 22333/22666` | ✅ 同（= `SkyAlphaSource.NIGHT`）|
| rotation | `rotationSpeedZ = 1.0`，`skyboxRotation = false` | ✅ 同（= `STAR_ROTATION`）|
| alpha | `night_fade * (1 - rainAlpha)` | ✅ 同 |
| **顶点** | 24 个全立方体 | ✅ 与 `FACES` 逐字一致 |

**内容实测**（逐像素）：

- 只有 **Bottom 单元格**有内容：**88×88 抗锯齿近黑圆盘**，居中，**12 个 alpha 级**
- **99.9% 为 `alpha=0`**（完全透明，**不是黑**）⇒ ALPHA 混合下不产生任何效果
- 各格内容中心偏移 **≤3 px**

**用途：强假设是「遮住月亮背后的星空」**，三条证据：

1. **位置重合** —— 盘在 Bottom 面中心、绕 Z 按 `skyAngle`；月亮与太阳相对（净效果同为 `skyAngle`）
2. **尺寸匹配** —— 盘约 **119 px** vs 月亮 **131 px**，略小，正好避免在月亮边缘留下可见黑环
3. **图层顺序** —— 它是图层 1，紧接星图层 0 之后、其他夜层之前 ⇒ 先遮星空，再由后续夜层叠加

**验证方法**（便宜且决定性）：临时把图层 1 从 `LAYERS` 移除，看月亮背后是否出现星点。

### 8.6 `mask_moon.png` 的硬约束：**只能整体降采样，不能裁剪**

所有天空盒图层**共用同一份立方体 UV 表**（`FACES`）——这也是 9 层能合并成 1 个 `VertexBuffer`
的原因。因此遮罩盘的**归一化位置与大小必须保持**：

- ✅ 整体等比降采样安全
- ❌ 裁剪会使圆盘移位/变形
- 圆盘的 88 texel 要求采样区至少 1024 宽 ⇒ **单纯降采样必然降低圆盘的分辨率**
- 现状已欠采样：88 texel ↔ 约 119 px = **0.74×**

### 9.1 月相：4×2 图集 → 8 张独立 320×320

管线（**先裁后缩**，使重采样只处理 560² 而非 1000²）：

```
① 4000×2000 图集按 4×2 切出 8 个 1000×1000 单元格
② 每张居中裁 560×560     ← 保住 553 px 内容（含暗盘）+ 3.5 px 黑边余量
③ 缩放到 320×320         ← 比例 0.32
④ 存为 8-bit RGB（无 alpha，与源图一致）
```

| 项 | 原 | 现 |
|---|---|---|
| 文件 | 1 × 4000×2000 16-bit RGB | **8 × 320×320 8-bit RGB** |
| PNG 体积 | 4316 KB | **724 KB** |
| 显存 | 30.52 MiB | **3.13 MiB** |
| 满月盘 texel | 425 | **243**（↔ 屏幕 131 px = **1.85×** 余量）|
| quad | 40 世界单位 | **22.4**（`20 × 0.56`，角尺寸不变）|

裁剪框**必须居中且 8 张一致**：每格除亮部外还有一个固定尺寸的暗盘（earthshine，实测各格内容均
延伸到 541–549 px），它是相位间位置一致性**与新月可见性**的来源（相位 4 在 `≥16` 下完全无内容，
只有暗盘）。按各相位自己的亮部 bbox 裁剪会让月牙随相位横跳。

**顺带收益**：首帧只需解码当前相位的 1 张小图，而非整张 4.4 MB 的 16-bit 图集 ⇒
**部分缓解 I2**（首次进龙宫那一帧的同步解码 + 96 MiB 上传）。

## 十、第二轮：天空盒图集整体降采样（2026-09-11）

> 目标：处理 §2.1 剩下的 120 MiB（5 张 3072×2048）。
> **纯资源改动，零代码改动** —— 用户明确排除代码改动，因此「内容裁剪」方案出局。

### 10.1 为什么只能降采样、不能裁剪

所有天空盒图层**共用同一份立方体 UV 表**（`FACES`），这也是 9 层能合并成 1 个 `VertexBuffer` 的原因。
裁剪会让该层内容在面上移位，必须给该层**单独一套 UV 表 + 单独的 `VertexBuffer`** 才能裁 —— 那是代码改动。

本报告**第九节 §9.2** 曾提出「升级路径：给 `mask_moon` 专属 UV 表」，
第十节第一版的讨论也列出了「无损裁剪」方案（可省约 24 MiB 且零画质代价），
但**两者都以代码改动为前提**。在「不动代码」的约束下，均匀等比降采样是唯一手段。
**这两件事不矛盾**：第九节说的是「共用 UV 表时不能裁」，裁剪方案必须自带新代码。

### 10.2 实施内容

`day` / `night` / `stars` / `mask` / `skybox/sun` 由 **3072×2048 → 1536×1024**，
重采样用 **BOX（2×2 平均）** —— 整数倍降采样下 BOX 是数学上正确的抗混叠，Lanczos 会带振铃。
`stars` 按用户决定同样用 BOX（备选 MAX 未采用）。
`mask.png` 原为 Palette + tRNS，其 RGB 实测**最大值为 0**（信息全在 alpha），故转为 RGBA 无语义影响。

同时为这 5 张 + `sunflare.png` 补 `.mcmeta`（`{"texture":{"blur":true}}`），
使**全部 7 张天空盒图集统一 `GL_LINEAR`**。

## 10.7 【回归与修复】`GL_LINEAR` 引发的立方体棱黑缝 + 星星变暗变糊

> 用户实机验收发现两个问题（截图 `2026-09-11_23.53.23.png` 裸眼、`_23.53.28.png` 望远镜放大）。
> **这是第十节引入的真实回归**，本报告第九/十节初稿未预见。

### 10.7.1 症状

1. **天空盒出现明显黑色缝隙**，望远镜放大后极明显；
2. **星星变得暗淡且模糊**。

### 10.7.2 根因（已用数据钉死）

**缝隙在立方体的棱上，不在面内。** 望远镜截图里那个「Y」形交汇就是三个面交于一个立方体角。

`CubeAtlasSkyRenderer.FACES` 里每个面的 UV 都**精确落在图集的格子边界**上：
`u ∈ {0, 1/3, 2/3, 1}`、`v ∈ {0, 1/2, 1}`。

`GL_LINEAR` 下，`u = 1/3` 对应纹素坐标 `1536/3 − 0.5 = 511.5` ⇒ `floor = 511`、`frac = 0.5`
⇒ **取「左邻格最后一个纹素」与「本格第一个纹素」各一半**。而相邻格子是天空的另一面：

| 资源 | 边界 | 左侧格 | 右侧格 | 落差 |
|---|---|---|---|---|
| `mask.png` | v=1/2 | 188.8 | 28.9 | **6.5×** |
| `mask.png` | u=1/3 | 235.3 | 108.1 | 2.2× |
| `night.png` | u=1/3 | 9.1 | 22.3 | 2.4× |
| `night.png` | v=1/2 | 10.4 | 28.8 | 2.8× |
| `day.png` | v=1/2 | 92.5 | 133.2 | 1.4× |
| `sun.png` | v=1/2 | 54.3 | 81.3 | 1.5× |

**为什么是「黑色」**：`mask.png` 是「alpha 越大越暗」的遮罩。v=1/2 混合后 = 108.9，
上排三面（West/North/East）的上缘 alpha 从 28.9 抬到 108.9 ⇒ 透光率 `0.887 → 0.573`，**暗约 35%**。

**截图实测吻合**：最强暗线残差 **35**（x=740, y=360），横向剖面
`159 160 160 160 159 [156 122 140] 158 157` ⇒ 约 2 px 宽、暗约 23%；天空区 **0.11%**
的像素比局部背景暗 >10。

**两项关键判断**：

1. **与降采样无关**：上表两侧数值在 3072×2048 与 1536×1024 下**几乎逐位相同**
   （如 `night` u=1/3：9.1|22.3 对 9.1|22.2）。**即使保持原分辨率、只加 mcmeta，也会出同样的缝**，
   只是线宽减半。⇒ 根因是 `GL_LINEAR` + UV 落在格子边界，降采样只是把线加宽 2×。
2. **纯资源修不掉**：预补偿法（把边缘纹素改成 `2·edge − neighbor`）数学上精确，但**在极值处被 clamp 打败**——
   `mask.png` v=1/2 需要 `2×28.9 − 188.8 = −131` → 夹到 0 → 混合后 94.4，而目标是 28.9。
   而最黑的缝恰好长在这种地方。

### 10.7.3 修复

**A. 半纹素内缩（`CubeAtlasSkyRenderer`，唯一彻底的办法）**

新增常量 `ATLAS_WIDTH = 1536` / `ATLAS_HEIGHT = 1024` 与 `INSET_U = 0.5F/ATLAS_WIDTH`、
`INSET_V = 0.5F/ATLAS_HEIGHT`；`FACES` 之后加一个 `static` 块，**按每个面自己的 4 个 UV 极值**
推出它占用的格子区间，再把四边各内缩半个纹素：

```java
for (float[] face : FACES) {
    // 先求该面 4 个顶点的 uMin/uMax/vMin/vMax（即它的格子区间）
    // 再把等于 min 的挪到 min+INSET，等于 max 的挪到 max−INSET
    face[v*5+3] = (u == uMin) ? uMin + INSET_U : uMax - INSET_U;
    face[v*5+4] = (w == vMin) ? vMin + INSET_V : vMax - INSET_V;
}
```

由数据自身推出上下界，**无需手工改 48 个字面量**（那正是最容易出错的地方）。

**离线证明**（用脚本模拟 GL 双线性取样，与理想 NEAREST 值比较）：

| 资源 | 修复前最大边界误差 | 修复后 |
|---|---|---|
| `mask.png`（alpha） | **127.5 / 255 = 50%** | **0.0** |
| `day.png`（亮度） | 26.0 | **0.0** |

代价：每面内容缩 `1/512 ≈ 0.2%`，肉眼不可见；**显存不变**。

⚠ **新增的硬约束**：内缩量由 `ATLAS_WIDTH/HEIGHT` 算出 ⇒ **7 张天空盒贴图必须同为 1536×1024**，
且**改任何一张的尺寸都必须同步改这两个常量**。这也是「stars 恢复 3072×2048 而其余保持 1536×1024」
**不可行**的原因——那样 stars 的边界会落到 `1024.5`，50/50 混合，缝隙原样回来；
要单独恢复 stars 的分辨率必须给它**独立的 UV 表 + 独立的 `VertexBuffer`**。

### 10.7.4 星星：亮度与锐度是两件事，必须分开修

| 指标 | 原图 3072×2048 | BOX（回归版） | **MAX（修复版）** |
|---|---|---|---|
| 亮度总和 | 2,061,010（100%） | 533,465（**25.9%**） | 1,148,963（**55.7%**） |
| `≥200` 的亮星数 | 28 | **0** | **24** |
| `≥100` 的像素 | 3,385 | 492 | 2,086 |
| 前 0.01% 均值 | 178.4 | 150.1 | 193.6 |

- **暗淡**的根因是 BOX 平均：1 texel 的星点 255 → 约 64，亮星**一个不剩**。**MAX 修好了这一半**，
  且逐像素比较 **MAX 没有任何一个像素比 BOX 更暗**。
- **模糊 MAX 修不好**：它来自放大倍率 `2.8 px/texel` + LINEAR 放大，与滤波方式无关。
  当时据此**去掉了 `stars.png` 的 mcmeta（改 `GL_NEAREST`）**，让星点变成约 2.8 px 的亮方块。
- **最终结论（用户实机目视后）：mcmeta 加回，`stars` 仍走 `GL_LINEAR`。**
  即：**MAX 保留了这一改动**（它解决的是真实的亮度损失），**NEAREST 那一步被否决**。
  两条备选经验都保留，按观感二选一即可：嫌块状 → 留 mcmeta；嫌发虚 → 删 mcmeta。
- MAX 实现：`ImageChops.offset(im, 1, 0/1/1)` 造 4 个位移副本 → `ImageChops.lighter` 逐像素取最大
  （等价 2×2 形态学膨胀）→ `transform(AFFINE (2,0,0,0,2,0), NEAREST)` 取偶数格点，
  得到与「左上对齐的 2×2 最大池化」精确一致的结果。

### 10.7.6 本次教训（可复用）

1. **给图集贴图开 `GL_LINEAR` 前，必须先确认 UV 是否落在格子边界上**；落在边界就必须同时做半纹素内缩。
   本报告第九/十节初稿只写了「加 mcmeta」，漏了后半句，直接导致了 §10.7 的回归。
2. **降采样滤波与过滤模式是两个独立决策，要分开验证**：
   BOX → MAX 解决的是**亮度损失**（实测亮星 0 → 24 个），这一步被保留；
   LINEAR → NEAREST 解决的是**锐度**，但会引入块状观感，实机后被否决。
   点特征贴图的正确做法是**先保亮度（MAX），过滤模式再按观感二选一**，
   不要指望一个开关同时解决两件事。
3. **`docs/` 里「全部 / 唯一 / 不再有」这类绝对断言极易被后续改动推翻**：本文件 §2.8 先写
   「不再有 `GL_NEAREST` 的天空贴图」→ §10.7 改为「`stars` 是唯一 NEAREST 例外」→
   最终又回到「7/7 LINEAR」。**陈述结论时要带上成立条件**（如「在 `stars` 走 LINEAR 的前提下」），
   而不是写成无条件的全局断言。
