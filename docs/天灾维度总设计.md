# 天灾维度总设计

> 状态：**现行实现**（与 `master` 分支代码一致，含 PR #6 的 Iris 兼容渲染改造）
> 覆盖范围：`beloong:disaster` 维度的定义、进入方式、群系构成、结构联动
> 本文取代此前所有分散的天灾相关设计/计划文档（见文末「已废弃文档」）

---

## 一、设计目标

天灾维度是「化龍」整合包的高价值战利品区域，同时也是**主世界群系构成的独立副本**。三条核心设计意图：

1. **第二个主世界**：地形、群系、结构、洞穴、矿物全部复用原版主世界，玩家不需要学习新的世界生成规则。
2. **BWG 群系迁移**：Oh The Biomes We've Gone (BWG) 的生物群系**从主世界整体迁移到天灾维度**。主世界退回纯净原版群系，天灾维度承载原版 + BWG 的完整群系构成。
3. **唯一的进出通道**：进出只能通过「天灾传送门」。传送门需要集齐 12 种来自 Cataclysm / FDBosses 的眼球，构成进入天灾的进度门槛。

设计意图 2 意味着：**在主世界禁用 TerraBlender 是刻意行为，不是缺陷。** 详见第四节。

## 二、维度定义

天灾维度是**纯数据包维度**，没有任何自定义 Java 维度类。

### `data/beloong/dimension_type/disaster.json`

| 字段 | 值 | 说明 |
|---|---|---|
| `natural` | `true` | 保留昼夜与天气 |
| `coordinate_scale` | `1.0` | 1:1 坐标传送的维度侧前提 |
| `has_skylight` | `true` | 有天空光 |
| `has_ceiling` | `false` | 无天花板（区别于下界） |
| `ambient_light` | `0.0` | 无环境光补正 |
| `bed_works` | `true` | 床可睡、可设重生点 |
| `respawn_anchor_works` | `false` | 重生锚不可用 |
| `has_raids` | `true` | 可触发袭击 |
| `min_y` / `height` / `logical_height` | `-64` / `512` / `512` | 与原版主世界一致 |
| `infiniburn` | `#minecraft:infiniburn_overworld` | 火焰蔓延规则同主世界 |
| `monster_spawn_light_level` | `uniform 0~7` | 原版主世界刷怪光照规则 |
| `piglin_safe` | `false` | — |
| `effects` | `minecraft:overworld` | **保留原版主世界天空与天气** |

**关于 `effects: minecraft:overworld`**：天灾维度**不**使用自定义天空盒。龙宫的 Dramatic Skys 天空渲染、雾处理、天气禁用等全部限定在 `beloong:loong_palace`，天灾维度不受任何影响。这是刻意的范围划分，避免天空系统与战利品维度的职责耦合。

### `data/beloong/dimension/disaster.json`

```json
{
  "type": "beloong:disaster",
  "generator": {
    "type": "minecraft:noise",
    "settings": "minecraft:overworld",
    "biome_source": {
      "type": "minecraft:multi_noise",
      "preset": "minecraft:overworld"
    }
  }
}
```

- `settings: minecraft:overworld` → 地形、洞穴、矿物、海平面、结构集全部与主世界一致
- `biome_source: multi_noise` → **这是 TerraBlender 能够介入的前提**（TerraBlender 只处理 `MultiNoiseBiomeSource`）
- 维度种子由存档种子独立派生，因此地形与主世界不同，但**生成规则相同**

### 维度 ID 的硬编码点

`DisasterPortalBlock` 中维度 ID 是编译期常量，**不受配置控制**：

```java
private static final String DISASTER_DIM = "beloong:disaster";
```

## 三、进入方式：天灾传送门

传送门模仿原版末地传送门 + End Remastered：**5×5 环形框架，12 个框架各嵌入 1 种不同眼球后激活**。

### 3.1 结构形状

```
?  v  v  v  ?      角落：任意方块（不参与匹配）
>  ?  ?  ?  <      四边：各 3 个框架，朝向指向结构内部
>  ?  ?  ?  <      中间 3×3：激活后填充天灾传送门方块
>  ?  ?  ?  <
?  ^  ^  ^  ?
```

用 `BlockPatternBuilder` 匹配（`DisasterPortalFrame.getCompletedPortalShape(boolean requireEyes)`）：

- `requireEyes = true` → 仅匹配 `EYE_TYPE != EMPTY` 的框架，用于**激活检测**
- `requireEyes = false` → 匹配所有框架，用于**去重检测**（框架可能在眼球未放满时就已搭好）

四个符号各自的朝向是固定的：顶边朝 SOUTH、底边朝 NORTH、右边朝 WEST、左边朝 EAST。`FACING` 在放置时取玩家水平朝向的反方向。

### 3.2 方块清单

| 方块 / 实体 | ID | 职责 |
|---|---|---|
| `DisasterPortalFrame` | `beloong:disaster_portal_frame` | 框架，`Block implements EntityBlock` |
| `DisasterPortalFrameEntity` | `beloong:disaster_portal_frame_entity` | 持久化眼球槽位编号 |
| `DisasterPortalBlock` | `beloong:disaster_portal_block` | 传送门本体，接触传送 |
| `DisasterPortalBlockEntity` | `beloong:disaster_portal_block_entity` | 纯渲染载体，无数据 |

**框架方块属性**：`strength(50, 1200)`、`requiresCorrectToolForDrops()`（下界合金镐）、绿色地图色、玻璃音效、发光 1、`pushReaction BLOCK`、掉落自身。

**BlockState 属性**（共 `4 × 2 × 13 = 104` 种组合）：

| 属性 | 类型 | 值 |
|---|---|---|
| `FACING` | `EnumProperty<Direction>` | `north` / `east` / `south` / `west` |
| `HAS_EYE` | `BooleanProperty` | `true` / `false` |
| `EYE_TYPE` | `EnumProperty<EyeType>` | `"0"`（空）+ `"1"`~`"12"` |

**传送门方块属性**：`strength(-1, 3600000)` 不可破坏、`noLootTable()`、`noCollission()`、发光 11、`RenderShape.INVISIBLE`（视觉完全交给 BlockEntity 渲染器）、碰撞箱 16×12×16。

### 3.3 EyeType 与配置的映射

`block/EyeType` 是 13 值枚举，实现 `StringRepresentable`，BlockState 序列化名即数字字符串：

```
EMPTY("0")
SLOT_1("1") ... SLOT_12("12")
```

映射规则：**`Config.DisasterPortal.eyeItems` 列表的位置索引 + 1 = 槽位编号**。

| 配置列表索引 | 槽位 | 枚举值 | 纹理 |
|---|---|---|---|
| — | 0 | `EMPTY` | `disaster_portal_frame_top.png` |
| 0 | 1 | `SLOT_1` | `disaster_portal_frame_top_1.png` + `_eye_1.png` |
| … | … | … | … |
| 11 | 12 | `SLOT_12` | `disaster_portal_frame_top_12.png` + `_eye_12.png` |

`registry/ModBlocks#getEyeSlot(ItemStack)` 负责查询：在配置列表中查找物品完整 ID，命中返回 `索引 + 1`，未命中返回 `0`。

> **为什么是数字槽位而非语义化命名**：早期实现用 `"cataclysm:mech_eye"` 等语义短键，导致枚举与硬编码 Map 绑定、改配置不生效。改为数字槽位后，配置列表里放任意物品 ID 都能工作，纹理由槽位编号决定。

### 3.4 激活流程

```
玩家手持眼球右键框架
  → HAS_EYE 已为 true？                        → PASS
  → getEyeSlot(stack) 返回 0（非有效眼球）？     → PASS
  → 客户端？                                   → SUCCESS（触发交互包发往服务端）
  → isEyeAbsent(level, pos, eyeType) 为 false？ → 提示「该眼球已放置在传送门中」→ FAIL
  → setBlock(HAS_EYE=true, EYE_TYPE=对应槽位)
  → BlockEntity.setEyeId(String.valueOf(slot))
  → stack.consume(1, player)
  → 播放 SoundEvents.END_PORTAL_FRAME_FILL
  → getCompletedPortalShape(true).find(level, pos)
      命中？→ 中间 3×3 填充 DisasterPortalBlock
            → globalLevelEvent(1038)（原版末地门激活特效）
  → CONSUME
```

**去重机制**：`isEyeAbsent()` 用 `requireEyes=false` 的模式定位 5×5 结构，遍历 25 格找出所有 `DisasterPortalFrame`，比较 `EYE_TYPE`。若模式未匹配到（框架不完整），返回 `true` 放行。

### 3.5 破坏行为

框架方块 `onRemove()`：扫描**以自身为中心的 7×7 水平范围**（覆盖整个 5×5 结构），对所有 `DisasterPortalBlock` 调用 `level.destroyBlock(pos, false)`。借原版 `destroyBlock` 免费获得与下界传送门破碎一致的音效和粒子。传送门方块本身不掉落任何物品。

### 3.6 传送逻辑

全部逻辑位于 `DisasterPortalBlock.entityInside()`，**仅服务端执行，仅处理 `ServerPlayer`**。

```
冷却检查：player.getPersistentData().getLong("beloong_portal_cooldown")
          > level.getGameTime() ? 直接 return

┌─ 当前维度 ≠ beloong:disaster（下行）
│    X / Z 原样保留（1:1）
│    targetLevel.getChunk(x>>4, z>>4)     ← 强制加载，否则高度图查不到数据
│    topY = targetLevel.getHeight(MOTION_BLOCKING, x, z)
│    player.isPassenger() ? stopRiding()
│    teleportTo(targetLevel, x, topY + 1.0, z, Set.of(), yRot, xRot)
│    player.fallDistance = 0
└─ 当前维度 == beloong:disaster（上行）
     respawnPos = player.getRespawnPosition()      // 床 / 重生锚
     respawnDim = player.getRespawnDimension()
     无重生点？→ 回退 overworld.getSharedSpawnPos() + Level.OVERWORLD
                 → 最终兜底 new BlockPos(0, 64, 0)
     teleportTo(targetLevel, respawnPos.getX() + 0.5, respawnPos.getY(), respawnPos.getZ() + 0.5, ...)
     player.fallDistance = 0

写入冷却：persistentData.putLong("beloong_portal_cooldown",
                                level.getGameTime() + Config.DisasterPortal.teleportCooldownTicks)
```

要点：
- **下行是 1:1 坐标映射**（靠 `coordinate_scale: 1.0` + 手动保留 X/Z）
- **上行照搬原版末地返回逻辑**，回到玩家重生点而非坐标对应点
- 朝向在双向传送中均保留
- 冷却写入玩家持久化 NBT，跨维度/重登有效

### 3.7 渲染

`client/DisasterPortalRenderer`（`@OnlyIn(Dist.CLIENT)`）是原版 `TheEndPortalRenderer` 的**完全重新实现**——原版渲染器在字节码层把 BlockEntity 硬转型为 `TheEndPortalBlockEntity`，无法靠子类化复用。

- **渲染管线**：`RenderType.entitySolid(beloong:textures/disaster_portal.png)`，即原版标准实体管线 `rendertype_entity_solid`。**不使用自定义着色器。**
- **顶点数据**：8 个浮点坐标、4 顶点绕序与原版 `TheEndPortalRenderer` **逐字相同**；每个顶点写入 color(1,1,1,1)、overlay、`LightTexture.FULL_BRIGHT`（与原版末地传送门一致恒全亮）以及该面的法线
- **UV**：在 Java 侧用**变换后的世界坐标**计算 `u = x/3 + 1/3`、`v = z/3 + 1/3`，与旧核心着色器的公式一致，使相邻传送门方块共享连续纹理坐标
- 6 面立方体一次提交；上下表面内收（`down = 0.375` / `up = 0.75`）形成收窄的立体感
- 每个面经 `DisasterPortalBlockEntity#shouldRenderFace(Direction)` 判定，仅 Y 轴方向可见（与原版一致）

> **为什么必须是标准管线（Iris 兼容性）**
>
> 本项目曾使用自研 `ShaderInstance`（`beloong:rendertype_disaster_portal`，`.vsh`/`.fsh` 照搬原版 `rendertype_end_portal`）。该方案在 Iris 光影下**完全不渲染**：Iris 只把原版管线映射到 shader pack 的 `gbuffers_*`（其 `ShaderKey` 枚举中可见 `ENTITIES_SOLID`、`TERRAIN_SOLID`、`TEXTURED` 等对应项），自定义着色器 ID 不在映射表内，开启光影且禁用未知着色器时整块被丢弃。
>
> 改用 `entitySolid` 后映射到 `ENTITIES_SOLID` → shader pack 的 `gbuffers_entity_solid`，原版与光影下均有输出。
>
> **已知代价**：原版 `end_portal` 着色器在片元里做多层视差采样，形成随视角滑动的星空隧道；标准管线只有一次采样，观感退化为按世界坐标连续平铺的静态星空贴图（无视差纵深）。此外传送门会接受 shader pack 对 `gbuffers_entity_solid` 的光照/PBR/阴影处理。这两点是获得光影可见性的必然取舍，已由实机确认可接受。

## 四、群系构成：BWG 迁移方案

这是天灾维度设计中最需要理解的一环。

### 4.1 目标状态

| 维度 | 群系构成 |
|---|---|
| 主世界 `minecraft:overworld` | **纯净原版**群系，BWG 完全不介入 |
| 天灾 `beloong:disaster` | 原版群系 + **全部 BWG 群系**（含 BWG 配置中禁用的那些） |

### 4.2 实现机制：精准排除主世界

`data/terrablender/tags/dimension_type/overworld_regions.json`：

```json
{
  "replace": true,
  "values": [
    "beloong:disaster"
  ]
}
```

TerraBlender 通过 `LevelUtils.getRegionTypeForDimension()` 查询维度类型 tag `terrablender:overworld_regions`，命中才返回 `RegionType.OVERWORLD` 并执行群系注入。TerraBlender 自带的同名文件是 `replace: false` + `minecraft:overworld`。

**原理**：原版 `TagLoader` 在加载每个数据包的同名 tag 文件时：

```java
TagFile tagfile = TagFile.CODEC.parse(...).getOrThrow();
if (tagfile.replace()) {
    list.clear();          // 清空此前所有数据包累积的条目
}
tagfile.entries().forEach(e -> list.add(new EntryWithSource(e, sourcePackId)));
```

`replace: true` 会**清空列表**，从而抹掉 TerraBlender 自己注入的 `minecraft:overworld`。最终该 tag 只含 `beloong:disaster`：

- 主世界 → `getRegionTypeForDimension()` 返回 `null` → TerraBlender 直接 `return`，不做任何群系注入
- 天灾 → 返回 `RegionType.OVERWORLD` → 正常注入 BWG 群系

> ⚠️ **该文件是「一票否决」式的全局开关，改动它等于同时动两个维度。** 若要恢复主世界的 BWG 群系，需改为 `"replace": false` 并把 `minecraft:overworld` 加回 `values` 数组。

### 4.3 防污染：CloneParameterListMixin

`mixin/CloneParameterListMixin`（`@Pseudo`，目标 `terrablender.util.LevelUtils`）

天灾维度与主世界共用 `minecraft:overworld` 的 `multi_noise` 预设，而 TerraBlender 的 `initializeForTerraBlender` 是**在 `Climate.ParameterList` 实例上原地初始化**的。若不干预，初始化天灾维度会把共享的 `ParameterList` 标记为已完成初始化，导致 BWG 群系**泄漏回主世界**。

Mixin 用 `@Redirect` 拦截 `initializeBiomes` 中对 `IExtendedParameterList.initializeForTerraBlender(...)` 的调用：

```java
Climate.ParameterList cloned = (Climate.ParameterList) receiver.clone();
((IExtendedParameterList) cloned).initializeForTerraBlender(targetRA, regionType, targetSeed);
MultiNoiseBiomeSource biomeSource = (MultiNoiseBiomeSource) chunkGenerator.getBiomeSource();
((MultiNoiseBiomeSourceAccess) biomeSource).setParameters(Either.left(cloned));
```

**先 clone、再初始化、再写回**，使天灾维度持有独立的参数列表副本，主世界的共享实例保持未被污染。

因 TerraBlender 是可选依赖，Mixin 使用 `@Pseudo` + `remap = false`，TerraBlender 缺席时静默失效。

### 4.4 表面规则与结构

- **表面规则**：无需额外处理。TerraBlender 的 `NamespacedSurfaceRuleSource` 按群系命名空间（`biomeswevegone`）自动分发 BWG 已注册的表面规则，天灾维度中 BWG 群系的地表表现正确。
- **结构**：BWG 结构经由 `NoiseGeneratorSettings` 的 structure settings 生效，与主世界共享 `settings: minecraft:overworld`，行为一致。
- **群系筛选**：BWG 配置文件中被禁用的群系在主世界和天灾维度**都不会出现**（不再有"天灾维度跳过配置过滤"的特殊行为——早期设计文档中的 `DisasterBiomeRegion` 方案未采用）。

### 4.5 实测确认

对 `run/saves/mowzie生物` 存档做区块 NBT 的 `sections[].biomes.palette` 解析（180 区块抽样）：

```
天灾维度：minecraft:plains 4416 | biomeswevegone:maple_taiga 1344
          minecraft:river 448  | biomeswevegone:coconino_meadow 64 | minecraft:deep_dark 2
主世界  ：仅原版群系，biomeswevegone:* 命中 0
```

运行日志中 TerraBlender 仅为 `minecraft:the_nether` 和 `beloong:disaster` 打印初始化行，主世界**从不出现**——与设计意图一致。

## 五、结构效果与禁空联动

天灾维度承载 Cataclysm 与 FDBosses 的高难度结构。进入这些结构范围时对玩家施加**禁空**效果，限制龙类飞行能力。

数据文件：`data/beloong/beloong/structure_effects/disaster.json`

| 结构 | 效果 | amplifier | duration |
|---|---|---|---|
| `cataclysm:acropolis` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:ancient_factory` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:burning_arena` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:cursed_pyramid` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:frosted_prison` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:ruined_citadel` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:soul_black_smith` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:sunken_city` | `beloong:flight_ban` | 5 | 100t |
| `fdbosses:chesed_arena` | `beloong:flight_ban` | 6 | 100t |
| `fdbosses:geburah_arena` | `beloong:flight_ban` | 6 | 100t |
| `fdbosses:malkuth_arena` | `beloong:flight_ban` | 6 | 100t |

**注意：该文件按结构 ID 匹配，不含维度限定条件。** 文件名 `disaster.json` 只是归类约定；若同 ID 结构出现在其他维度，效果同样生效。目前这些结构仅生成于天灾维度，因此实际作用范围等价。

### 配套实现

- `structure/StructureEffectLoader` — Codec 驱动的 `SimpleJsonResourceReloadListener`，扫描 `beloong/structure_effects/*.json`，解析为 `Map<ResourceKey<Structure>, List<EffectEntry>>`
- `structure/StructureEffectHandler` — 触发时机：
  - `ServerTickEvent.Post`：仅在玩家**所在区块坐标变化**时检测（避免每 tick 全量扫描）
  - `PlayerChangedDimensionEvent` / `PlayerRespawnEvent` / `PlayerLoggedInEvent`：清缓存并立即检测
  - `MobEffectEvent.Expired` / `Remove`：对 `Config.StructureEffects.watchedEffects` 中的效果，过期或被牛奶/指令移除时重检，若仍应生效则取消移除（防闪烁）
  - 命中判定：玩家 AABB 与结构 `StructureStart` 包围盒求交
  - 支持可选的 `advancement` 条件（进度已完成则跳过该效果）

### 效果本体

`registry/FlightBanEffect` — 每级降低 1 点 `dragonsurvival:flight_level`：

- 属性修饰符由 `ModMobEffects` 注册时通过 `addAttributeModifier` 挂到该属性上，原版按 `amount × (amplifier + 1)` 自动缩放
- `onEffectStarted()` 在修饰符生效后检查：若飞行等级 `< 0` 且玩家正在展翅，**强制收翅**并向所有追踪该玩家的客户端同步 `SyncWingsSpread`，同时发送 `message.beloong.flight_banned`
- 效果结束后**不自动恢复飞行**，玩家需手动按 G 键重新展翅
- 与 `BROKEN_WINGS` 的区别：`BROKEN_WINGS` 无条件收翅；禁空仅在等级降至负数时才收翅，保留了「低等级禁空只削弱悬停、不阻止飞行」的梯度

> ⚠️ **待复核项**：`flight_ban` 的等级 5/6 对应 `-6 / -7` 飞行等级。请对照《飞行等级系统》确认 DS 侧 `flight_level` 的实际量程——若上限远低于此，则该效果的梯度差异在实际游戏中不可观测，只剩下「强制收翅」这一行为。

## 八、设计决策记录

1. **纯数据包维度，无自定义 Java 维度类** — 复用原版主世界生成规则的最短路径，升级维护成本最低。
2. **`effects: minecraft:overworld`** — 天灾不需要自定义天空。把天空系统的影响范围严格限制在龙宫，避免两套维度机制相互干扰。
3. **用 `replace: true` 排除主世界而非 Mixin** — 在 tag 层做取舍是纯数据驱动方案，不引入对 TerraBlender 内部实现的耦合，也不需要 Mixin 即可达成「主世界退回原版」。
4. **`CloneParameterListMixin` 必须存在** — 主世界与天灾共用同一个 `multi_noise` 预设，TerraBlender 的原地初始化会跨维度泄漏。clone 是保证隔离的最小改动。
5. **数字槽位而非语义化眼球键** — 早期用 `"cataclysm:mech_eye"` 等短键导致枚举与硬编码 Map 绑定、配置形同虚设。数字槽位让配置列表与纹理解耦，任意物品 ID 均可工作。
6. **multipart 而非 variants** — variants 需穷举 104 种排列，multipart 靠条件匹配天然忽略非法组合。
7. **重实现渲染器而非继承 `TheEndPortalRenderer`/`TheEndPortalBlock`** — 原版渲染器在字节码层把 BlockEntity 硬转型为 `TheEndPortalBlockEntity`，无法子类化复用，只能重实现。（注：此处只说"必须自己写渲染器"，**不代表必须自研着色器**——用哪条管线是独立决策，见第 11 条。）
8. **上下行判断用「当前维度是否为天灾」** — 而不是判断「是否为配置的源维度」。这让任意维度（不只主世界）进入传送门都能去天灾，且下行逻辑无需区分来源。
9. **冷却写入玩家持久化 NBT** — 跨维度、跨重登保持，避免玩家在传送门两侧反复弹跳。
10. **框架破坏时用 `level.destroyBlock`** — 直接复用原版破碎音效与粒子，无需自行实现特效。
11. **渲染改用标准实体管线（Iris 兼容），代价是放弃视差隧道** — 最初实现为自研 `ShaderInstance`（`beloong:rendertype_disaster_portal`，`.vsh`/`.fsh` 照搬原版 `rendertype_end_portal`），在 Iris 光影下**完全不渲染**：Iris 只把原版管线映射到 shader pack 的 `gbuffers_*`，自定义着色器 ID 不在其映射表内，开启光影且禁用未知着色器时整块丢弃。改为 `RenderType.entitySolid()` 后映射到 `ENTITIES_SOLID`，原版与光影下均可见。
    - **代价**：原版 `end_portal` 着色器的多层视差采样（随视角滑动的星空隧道）无法在标准管线中复现，观感退化为按世界坐标连续平铺的静态星空贴图；且传送门会接受 shader pack 对 `gbuffers_entity_solid` 的光照/PBR/阴影处理。已由实机测试确认可接受。
    - **随之删除的死代码**：`BeLoongCoreClient.disasterPortalShader` 字段、`onRegisterShaders` 事件处理器、`assets/beloong/shaders/core/rendertype_disaster_portal.{json,vsh,fsh}`。改造后它们已无任何消费方。
    - **不引入 Iris 依赖**：全程只用原版 `RenderType`，因此不需要 `compileOnly`/`localRuntime` 任何光影模组，也不需要 `ModList.isLoaded` 守卫。
