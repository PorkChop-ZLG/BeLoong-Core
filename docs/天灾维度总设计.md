## 一、设计目标

天灾维度是「化龍」整合包的高价值战利品区域，同时也是**独立的群系舞台**。三条核心设计意图：

1. **第二个主世界**：地形、结构、洞穴、矿物全部复用原版主世界，玩家不需要学习新的世界生成规则。
2. **群系全面替换**：Oh The Biomes We've Gone (BWG) 的生物群系**从主世界整体迁移到天灾维度**，
   并进一步**剔除天灾维度里不需要的原版群系**——主世界退回纯净原版群系，天灾维度只保留
   BWG 群系 + 21 个白名单原版群系（BWG 在参数空间上不覆盖的 13 处结构缺口 + 8 处刻意保守，
   最终计划用自制群系接管）。详见第四节。
3. **唯一的进出通道**：进出只能通过「天灾传送门」。传送门需要集齐 12 种来自 Cataclysm / FDBosses 的眼球，构成进入天灾的进度门槛。

设计意图 2 意味着：**在主世界禁用 TerraBlender 是刻意行为，不是缺陷。**

> **分阶段目标**
> - **第一阶段（已完成）**：天灾维度 53 个原版主世界群系中，32 个替换为 BWG 群系、21 个白名单保留；
>   被替换的 32 个从 `possibleBiomes()` 中消失（`/locate` 搜不到、自然罗盘只显示在主世界）。
> - **第二阶段（未开始）**：用 `beloong:` 命名空间的自制群系接管这 21 个。见第十节。

## 二、维度定义

天灾维度是**纯数据包维度**，没有任何自定义 Java 维度类。

### `data/beloong/dimension_type/disaster.json`

| 字段 | 值 | 说明 |
|---|---|---|
| `natural` | `true` | 保留昼夜与天气 |
| `coordinate_scale` | `1.0` | 1:1 坐标传送的维度侧前提 |
| `has_skylight` | `true` | 有天空光 |
| `has_ceiling` | `false` | 无天花板（区别于下界） |
| `ambient_light` | `0.0` | 无环境光补正 |
| `bed_works` | `true` | 床可睡、可设重生点 |
| `respawn_anchor_works` | `false` | 重生锚不可用 |
| `has_raids` | `true` | 可触发袭击 |
| `min_y` / `height` / `logical_height` | `-64` / `512` / `512` | 与原版主世界一致 |
| `infiniburn` | `#minecraft:infiniburn_overworld` | 火焰蔓延规则同主世界 |
| `monster_spawn_light_level` | `uniform 0~7` | 原版主世界刷怪光照规则 |
| `piglin_safe` | `false` | — |
| `effects` | `minecraft:overworld` | **保留原版主世界天空与天气** |

**关于 `effects: minecraft:overworld`**：天灾维度**不**使用自定义天空盒。龙宫的 Dramatic Skys 天空渲染、雾处理、天气禁用等全部限定在 `beloong:loong_palace`，天灾维度不受任何影响。这是刻意的范围划分，避免天空系统与战利品维度的职责耦合。

### `data/beloong/dimension/disaster.json`

```json
{
  "type": "beloong:disaster",
  "generator": {
    "type": "minecraft:noise",
    "settings": "minecraft:overworld",
    "biome_source": {
      "type": "minecraft:multi_noise",
      "preset": "minecraft:overworld"
    }
  }
}
```

- `settings: minecraft:overworld` → 地形、洞穴、矿物、海平面、结构集全部与主世界一致
- `biome_source: multi_noise` → **这是 TerraBlender 能够介入的前提**（TerraBlender 只处理 `MultiNoiseBiomeSource`）
- 维度种子由存档种子独立派生，因此地形与主世界不同，但**生成规则相同**

### 维度 ID 的硬编码点

`DisasterPortalBlock` 中维度 ID 是编译期常量，**不受配置控制**：

```java
private static final String DISASTER_DIM = "beloong:disaster";
```

## 三、进入方式：天灾传送门

传送门模仿原版末地传送门 + End Remastered：**5×5 环形框架，12 个框架各嵌入 1 种不同眼球后激活**。

### 3.1 结构形状

```
?  v  v  v  ?      角落：任意方块（不参与匹配）
>  ?  ?  ?  <      四边：各 3 个框架，朝向指向结构内部
>  ?  ?  ?  <      中间 3×3：激活后填充天灾传送门方块
>  ?  ?  ?  <
?  ^  ^  ^  ?
```

用 `BlockPatternBuilder` 匹配（`DisasterPortalFrame.getCompletedPortalShape(boolean requireEyes)`）：

- `requireEyes = true` → 仅匹配 `EYE_TYPE != EMPTY` 的框架，用于**激活检测**
- `requireEyes = false` → 匹配所有框架，用于**去重检测**（框架可能在眼球未放满时就已搭好）

四个符号各自的朝向是固定的：顶边朝 SOUTH、底边朝 NORTH、右边朝 WEST、左边朝 EAST。`FACING` 在放置时取玩家水平朝向的反方向。

### 3.2 方块清单

| 方块 / 实体 | ID | 职责 |
|---|---|---|
| `DisasterPortalFrame` | `beloong:disaster_portal_frame` | 框架，`Block implements EntityBlock` |
| `DisasterPortalFrameEntity` | `beloong:disaster_portal_frame_entity` | 持久化眼球槽位编号 |
| `DisasterPortalBlock` | `beloong:disaster_portal_block` | 传送门本体，接触传送 |
| `DisasterPortalBlockEntity` | `beloong:disaster_portal_block_entity` | 纯渲染载体，无数据 |

**框架方块属性**：`strength(50, 1200)`、`requiresCorrectToolForDrops()`（下界合金镐）、绿色地图色、玻璃音效、发光 1、`pushReaction BLOCK`、掉落自身。

**BlockState 属性**（共 `4 × 2 × 13 = 104` 种组合）：

| 属性 | 类型 | 值 |
|---|---|---|
| `FACING` | `EnumProperty<Direction>` | `north` / `east` / `south` / `west` |
| `HAS_EYE` | `BooleanProperty` | `true` / `false` |
| `EYE_TYPE` | `EnumProperty<EyeType>` | `"0"`（空）+ `"1"`~`"12"` |

**传送门方块属性**：`strength(-1, 3600000)` 不可破坏、`noLootTable()`、`noCollission()`、发光 11、`RenderShape.INVISIBLE`（视觉完全交给 BlockEntity 渲染器）、碰撞箱 16×12×16。

### 3.3 EyeType 与配置的映射

`block/EyeType` 是 13 值枚举，实现 `StringRepresentable`，BlockState 序列化名即数字字符串：

```
EMPTY("0")
SLOT_1("1") ... SLOT_12("12")
```

映射规则：**`Config.DisasterPortal.eyeItems` 列表的位置索引 + 1 = 槽位编号**。

| 配置列表索引 | 槽位 | 枚举值 | 纹理 |
|---|---|---|---|
| — | 0 | `EMPTY` | `disaster_portal_frame_top.png` |
| 0 | 1 | `SLOT_1` | `disaster_portal_frame_top_1.png` + `_eye_1.png` |
| … | … | … | … |
| 11 | 12 | `SLOT_12` | `disaster_portal_frame_top_12.png` + `_eye_12.png` |

`registry/ModBlocks#getEyeSlot(ItemStack)` 负责查询：在配置列表中查找物品完整 ID，命中返回 `索引 + 1`，未命中返回 `0`。

> **为什么是数字槽位而非语义化命名**：早期实现用 `"cataclysm:mech_eye"` 等语义短键，导致枚举与硬编码 Map 绑定、改配置不生效。改为数字槽位后，配置列表里放任意物品 ID 都能工作，纹理由槽位编号决定。

### 3.4 激活流程

```
玩家手持眼球右键框架
  → HAS_EYE 已为 true？                        → PASS
  → getEyeSlot(stack) 返回 0（非有效眼球）？     → PASS
  → 客户端？                                   → SUCCESS（触发交互包发往服务端）
  → isEyeAbsent(level, pos, eyeType) 为 false？ → 提示「该眼球已放置在传送门中」→ FAIL
  → setBlock(HAS_EYE=true, EYE_TYPE=对应槽位)
  → BlockEntity.setEyeId(String.valueOf(slot))
  → stack.consume(1, player)
  → 播放 SoundEvents.END_PORTAL_FRAME_FILL
  → getCompletedPortalShape(true).find(level, pos)
      命中？→ 中间 3×3 填充 DisasterPortalBlock
            → globalLevelEvent(1038)（原版末地门激活特效）
  → CONSUME
```

**去重机制**：`isEyeAbsent()` 用 `requireEyes=false` 的模式定位 5×5 结构，遍历 25 格找出所有 `DisasterPortalFrame`，比较 `EYE_TYPE`。若模式未匹配到（框架不完整），返回 `true` 放行。

### 3.5 破坏行为

框架方块 `onRemove()`：扫描**以自身为中心的 7×7 水平范围**（覆盖整个 5×5 结构），对所有 `DisasterPortalBlock` 调用 `level.destroyBlock(pos, false)`。借原版 `destroyBlock` 免费获得与下界传送门破碎一致的音效和粒子。传送门方块本身不掉落任何物品。

### 3.6 传送逻辑

全部逻辑位于 `DisasterPortalBlock.entityInside()`，**仅服务端执行，仅处理 `ServerPlayer`**。

```
冷却检查：player.getPersistentData().getLong("beloong_portal_cooldown")
          > level.getGameTime() ? 直接 return

┌─ 当前维度 ≠ beloong:disaster（下行）
│    X / Z 原样保留（1:1）
│    targetLevel.getChunk(x>>4, z>>4)     ← 强制加载，否则高度图查不到数据
│    topY = targetLevel.getHeight(MOTION_BLOCKING, x, z)
│    player.isPassenger() ? stopRiding()
│    teleportTo(targetLevel, x, topY + 1.0, z, Set.of(), yRot, xRot)
│    player.fallDistance = 0
└─ 当前维度 == beloong:disaster（上行）
     respawnPos = player.getRespawnPosition()      // 床 / 重生锚
     respawnDim = player.getRespawnDimension()
     无重生点？→ 回退 overworld.getSharedSpawnPos() + Level.OVERWORLD
                 → 最终兜底 new BlockPos(0, 64, 0)
     teleportTo(targetLevel, respawnPos.getX() + 0.5, respawnPos.getY(), respawnPos.getZ() + 0.5, ...)
     player.fallDistance = 0

写入冷却：persistentData.putLong("beloong_portal_cooldown",
                                level.getGameTime() + Config.DisasterPortal.teleportCooldownTicks)
```

要点：
- **下行是 1:1 坐标映射**（靠 `coordinate_scale: 1.0` + 手动保留 X/Z）
- **上行照搬原版末地返回逻辑**，回到玩家重生点而非坐标对应点
- 朝向在双向传送中均保留
- 冷却写入玩家持久化 NBT，跨维度/重登有效

### 3.7 渲染

`client/DisasterPortalRenderer`（`@OnlyIn(Dist.CLIENT)`）是原版 `TheEndPortalRenderer` 的**完全重新实现**——原版渲染器在字节码层把 BlockEntity 硬转型为 `TheEndPortalBlockEntity`，无法靠子类化复用。

- **渲染管线**：`RenderType.entitySolid(beloong:textures/disaster_portal.png)`，即原版标准实体管线 `rendertype_entity_solid`。**不使用自定义着色器。**
- **顶点数据**：8 个浮点坐标、4 顶点绕序与原版 `TheEndPortalRenderer` **逐字相同**；每个顶点写入 color(1,1,1,1)、overlay、`LightTexture.FULL_BRIGHT`（与原版末地传送门一致恒全亮）以及该面的法线
- **UV**：在 Java 侧用**变换后的世界坐标**计算 `u = x/3 + 1/3`、`v = z/3 + 1/3`，与旧核心着色器的公式一致，使相邻传送门方块共享连续纹理坐标
- 6 面立方体一次提交；上下表面内收（`down = 0.375` / `up = 0.75`）形成收窄的立体感
- 每个面经 `DisasterPortalBlockEntity#shouldRenderFace(Direction)` 判定，仅 Y 轴方向可见（与原版一致）

> **为什么必须是标准管线（Iris 兼容性）**
>
> 本项目曾使用自研 `ShaderInstance`（`beloong:rendertype_disaster_portal`，`.vsh`/`.fsh` 照搬原版 `rendertype_end_portal`）。该方案在 Iris 光影下**完全不渲染**：Iris 只把原版管线映射到 shader pack 的 `gbuffers_*`（其 `ShaderKey` 枚举中可见 `ENTITIES_SOLID`、`TERRAIN_SOLID`、`TEXTURED` 等对应项），自定义着色器 ID 不在映射表内，开启光影且禁用未知着色器时整块被丢弃。
>
> 改用 `entitySolid` 后映射到 `ENTITIES_SOLID` → shader pack 的 `gbuffers_entity_solid`，原版与光影下均有输出。
>
> **已知代价**：原版 `end_portal` 着色器在片元里做多层视差采样，形成随视角滑动的星空隧道；标准管线只有一次采样，观感退化为按世界坐标连续平铺的静态星空贴图（无视差纵深）。此外传送门会接受 shader pack 对 `gbuffers_entity_solid` 的光照/PBR/阴影处理。这两点是获得光影可见性的必然取舍，已由实机确认可接受。

## 四、群系构成：原版群系剔除 + BWG 接管

这是天灾维度设计中最需要理解的一环。

### 4.1 目标状态

| 维度 | 群系构成 |
|---|---|
| 主世界 `minecraft:overworld` | **纯净原版**群系，BWG 完全不介入 |
| 天灾 `beloong:disaster` | **BWG 群系 + 21 个白名单原版群系**，其余 32 个原版群系被剔除 |

**21 个白名单原版群系**（刻意保留，判据见 4.6）：

| 类别 | 数量 | 群系 |
|---|---|---|
| 海洋 | 9 | `frozen_ocean` `deep_frozen_ocean` `cold_ocean` `deep_cold_ocean` `ocean` `deep_ocean` `lukewarm_ocean` `deep_lukewarm_ocean` `warm_ocean` |
| 河流 | 2 | `river` `frozen_river` |
| 洞穴 | 3 | `lush_caves` `dripstone_caves` `deep_dark` |
| 碎裂地形 | 3 | `windswept_hills` `windswept_gravelly_hills` `windswept_forest` |
| 暖带裸岩峰 | 1 | `stony_peaks` |
| 冰海滩 | 1 | `snowy_beach` |
| 其他硬编码位置 | 2 | `stony_shore` `windswept_savanna` |

被剔除的 32 个原版群系（`plains` / `forest` / `desert` / `badlands` / `mushroom_fields` …）
会被替换为气候最接近的 **25 个 BWG 群系**。

> **参数点账目**（`7593` 个原版参数点）：`替换 6782 + 白名单保留 811 = 7593`。
> 白名单 21 项里，前 14 项只占 41 点，后 7 项占 770 点（`windswept_savanna` 一项就有 216 点）。

**两个层面的目标必须同时达成：**

1. **生成层** —— 这些群系不再在天灾维度生成
2. **查询层** —— 它们从 `BiomeSource.possibleBiomes()` 中消失，因此 `/locate biome` 搜不到、
   自然罗盘只把它们显示在主世界

> 这两层是**独立的两条路径**，必须分别处理。这是本功能实现过程中最大的坑，详见
> `docs/天灾维度群系剔除-两次尝试复盘.md`。

> **⚠️ 本功能没有任何配置项。** 白名单与映射表都是硬编码的结构性决策。
> 早期版本曾有 `[disaster_biomes]` 配置节（`enabled` 开关 + `fallbackBiome` 兜底群系），
> 已按设计决定**整体移除**——详见 4.4 与第八节决策 19。

### 4.2 实现机制：精准排除主世界

`data/terrablender/tags/dimension_type/overworld_regions.json`：

```json
{
  "replace": true,
  "values": [
    "beloong:disaster"
  ]
}
```

TerraBlender 通过 `LevelUtils.getRegionTypeForDimension()` 查询维度类型 tag `terrablender:overworld_regions`，命中才返回 `RegionType.OVERWORLD` 并执行群系注入。TerraBlender 自带的同名文件是 `replace: false` + `minecraft:overworld`。

**原理**：原版 `TagLoader` 在加载每个数据包的同名 tag 文件时：

```java
TagFile tagfile = TagFile.CODEC.parse(...).getOrThrow();
if (tagfile.replace()) {
    list.clear();          // 清空此前所有数据包累积的条目
}
tagfile.entries().forEach(e -> list.add(new EntryWithSource(e, sourcePackId)));
```

`replace: true` 会**清空列表**，从而抹掉 TerraBlender 自己注入的 `minecraft:overworld`。最终该 tag 只含 `beloong:disaster`：

- 主世界 → `getRegionTypeForDimension()` 返回 `null` → TerraBlender 直接 `return`，不做任何群系注入
- 天灾 → 返回 `RegionType.OVERWORLD` → 正常注入 BWG 群系

> ⚠️ **该文件是「一票否决」式的全局开关，改动它等于同时动两个维度。** 若要恢复主世界的 BWG 群系，需改为 `"replace": false` 并把 `minecraft:overworld` 加回 `values` 数组。

### 4.3 防污染：CloneParameterListMixin

`mixin/CloneParameterListMixin`（`@Pseudo`，目标 `terrablender.util.LevelUtils`）

天灾维度与主世界共用 `minecraft:overworld` 的 `multi_noise` 预设，而 TerraBlender 的 `initializeForTerraBlender` 是**在 `Climate.ParameterList` 实例上原地初始化**的。若不干预，初始化天灾维度会把共享的 `ParameterList` 标记为已完成初始化，导致 BWG 群系**泄漏回主世界**。

Mixin 用 `@Redirect` 拦截 `initializeBiomes` 中对 `IExtendedParameterList.initializeForTerraBlender(...)` 的调用：

```java
Climate.ParameterList cloned = (Climate.ParameterList) receiver.clone();
((IExtendedParameterList) cloned).initializeForTerraBlender(targetRA, regionType, targetSeed);
MultiNoiseBiomeSource biomeSource = (MultiNoiseBiomeSource) chunkGenerator.getBiomeSource();
((MultiNoiseBiomeSourceAccess) biomeSource).setParameters(Either.left(cloned));
```

**先 clone、再初始化、再写回**，使天灾维度持有独立的参数列表副本，主世界的共享实例保持未被污染。

TerraBlender 与 BWG 现为 **required 依赖**（见 `neoforge.mods.toml`），因此本 Mixin 不必再考虑
"TB 缺席"的情形；但仍保留 `@Pseudo` + `remap = false`（目标是 TB 类，TB 的 jar 不带 refmap）。

### 4.4 生成层剔除：在副本上改写群系

`CloneParameterListMixin` 在上述 clone 与 initialize **之间**插入了群系改写：

```
① cloned = receiver.clone()
② 先把 cloned.values 换成一个新列表        ← 断开与共享原件的 List 引用
③ 逐行改写：非 minecraft: 命名空间 → 保留
             命中白名单 21 项       → 保留
             其余 32 项             → 查 DisasterBiomeMapping 换成 BWG 群系
             映射不可用             → 保留原版群系 + 记 ERROR（无兜底群系）
④ cloned.initializeForTerraBlender(...)   ← index 0 兜底树此时才建立，读到的是改写后的行
⑤ biomeSource.setParameters(Either.left(cloned))
```

**为什么必须换新列表（②）**：`ParameterList.clone()` 是浅拷贝，副本与原件**共享同一个
`values` 对象**（TerraBlender 的 `MixinParameterList` 只把 `clone()` 重写为 `super.clone()`）。
原地改行会连主世界一起改。`values` 声明为 `private final`，故用
`@Mutable @Accessor`（`mixin/ParameterListAccessor`）整体替换——TerraBlender 自己改
`MultiNoiseBiomeSource.parameters` 这个 final 字段也是同样手法。

**为什么时机必须在 initialize 之前（④）**：TerraBlender 的 `MixinParameterList` 内部以
`Climate.RTree.create(this.values)` 构建 index 0 兜底树，而 region 树命中
`Region.DEFERRED_PLACEHOLDER` 时会回退到这棵树。晚于此处的任何修改都不会影响兜底树。

**维度守卫**：该改写点对**所有**被 TerraBlender 判定为 `RegionType.OVERWORLD` 的维度都会触发。
实测 `minecraft:the_nether` 也会命中（TerraBlender 按维度类型 tag 而非维度身份分支），
若不限定维度，下界 5 个群系会被换成本不应该出现的 BWG 地表群系。
故 `DisasterBiomeSubstitution.isTargetDimension(levelKey)` 只放行 `beloong:disaster`。

主世界不需要在此排除：**本模组用自己的 datapack** 以 `"replace": true` 覆盖了
`terrablender:overworld_regions`（见 4.2），主世界因此不在该 tag 内，
`LevelUtils.getRegionTypeForDimension()` 返回 `null`，`initializeBiomes` 在到达改写点**之前就已 return**。

> ⚠️ **不要把这个保护当成平台固有属性。** TerraBlender 自带的该 tag 内容是
> `{"replace": false, "values": ["minecraft:overworld"]}`——主世界被排除**完全是本模组覆盖的结果**。
> 任何在该 tag 里放回 `minecraft:overworld` 的数据包，都会让主世界也进入 `appendDeferredBiomesList`，
> 从而被查询层的过滤器命中（见 4.5 的判据说明）。

**降级保护（无兜底群系）**：改写前会校验目标群系「已注册」且「未被 BWG 配置禁用」
（BWG 的 `BWGTerraBlenderRegion` 会把被禁用的群系改写成 `DEFERRED_PLACEHOLDER`，
说明 BWG 自己都回避它们）。任一校验失败则**保留原版群系并记 ERROR**——
不使用兜底群系，因为"什么都不做"比"换成一个语义不搭的群系"更安全。

**异常安全**：替换段整体包在 `try/catch` 中。**本功能没有配置开关，没有逃生舱**，
所以失败时必须继续执行原有的 `initializeForTerraBlender` + `setParameters`（退化为 TB 原行为），
而不是让异常穿透 `LevelUtils.initializeOnServerStart` 的 level stem 循环——
那会导致该维度之后的所有 level stem 全部不再初始化。

### 4.5 查询层剔除：让 possibleBiomes 也干净

**这是与生成层完全独立的一条路径。** `/locate biome`、自然罗盘、地图读的都是
`BiomeSource.possibleBiomes()`。实测天灾维度关卡实际持有的 `BiomeSource` 是**另一个实例**
（其 `parameters()` 返回的 `ParameterList` 与 4.4 写入的 clone 不是同一个），
该实例的 `values` 从未被替换，因此 `possibleBiomes()` 曾报 **109** 个群系
（53 原版 + 56 BWG），其中 32 个是待剔除的。

**实现**：`mixin/PossibleBiomesFilterMixin`（目标 `BiomeSource`）——
原版构造器已把 `possibleBiomes` 字段包成 `Suppliers.memoize`，TerraBlender 的
`MixinBiomeSource.appendDeferredBiomesList` 又会把它整体替换为一个**新的缓存闭包**。
因此过滤必须发生在这个**缓存被建立的那一点**：在该方法 HEAD 处 `cancellable` 注入，
自行合并「现有集合 + 本次追加列表」、剔除黑名单、重设 supplier，然后 `ci.cancel()`。

> 反例记录：先尝试注入 `MultiNoiseBiomeSource.collectPossibleBiomes()` 的 RETURN 点，
> 日志确认注入触发、判据正确，但**完全无效**——缓存闭包建立后，`possibleBiomes()`
> 直接读缓存，不再经过被过滤的方法。

**维度识别用「生成层是否真的生效」标志**：读
`DisasterBiomeSubstitution.isSubstitutionApplied()`——由 4.4 在真的替换成功时置位。
时序上安全：实测 `filter()` 比天灾的 `appendDeferredBiomesList` 早 **426 ms**。

> **为什么不用"追加列表里是否含 BWG 群系"这个判据**（早期实现）：该列表来自**全局** region 表，
> 与"当前是哪个维度"无关。任何进入 `overworld_regions` tag 的维度其追加列表都含 BWG，判据恒真。
> 主世界当时之所以安全，靠的是本模组覆盖 tag（见 4.4 的警告），而不是该判据本身。

**保序要求**：写入的新 supplier 必须**保序**，因为 `possibleBiomes()` 的迭代顺序会进入
`ChunkGenerator` 的 `FeatureSorter.buildFeaturesPerStep`，决定 `PlacedFeature` 的全局编号，
进而影响 `setFeatureSeed` 与地物放置顺序。原版用 Guava `ImmutableSet`、TerraBlender 用
`ObjectLinkedOpenHashSet`，两者都保序；而 `Set.copyOf` 返回的 `ImmutableCollections$SetN`
其迭代顺序由每次 JVM 启动随机化的 `SALT32L` 决定，**不保序**。故用 `ImmutableSet.copyOf`
并**一次算好快照返回常量**（同时满足保序与记忆化）。

> **已知局限（刻意不修）**：该标志由服务端初始化时置位，因此**专用服务器的客户端不成立**，
> 那里会回退为修复前的行为（自然罗盘的列表会显示原版群系在天灾维度）。
> 生成与 `/locate`（服务端）不受影响。


### 4.6 为什么必须保留那 21 个原版群系

判据统一为「**BWG 在结构上不覆盖该参数区**」：

| 类别 | 数量 | 原因 |
|---|---|---|
| **海洋** | 9 | BWG 只在暖/热两列填了 `LUSH_STACKS` / `DEAD_SEA`，寒/冷/中性三列（占海洋 60%）主动留空 |
| **河流** | 2 | BWG **完全没有河流群系**——其全部源码内 `river` 零命中，也不声明 `minecraft:is_river` 标签。原版在 `EROSION[6] + coastContinentalness` 上独立注册 |
| **洞穴** | 3 | 原版洞穴群系占 `depth ≥ 0.2` 的参数区域，而**所有 BWG 群系（及所有地表群系）的 `depth` 都是 0**。用地表群系去填这些点，会导致地下直接生成地表群系 |
| **碎裂地形** | 3 | BWG 的 `SHATTERED_BIOMES_BWG` 与 `SHATTERED_BIOMES_TERRABLENDER` 两个数组 **25 格全空**——BWG 明确把碎裂地形留给原版。原版这三个群系的侵蚀维固定在 `[4500,5500]`，正是碎裂地形的签名 |
| **暖带裸岩峰** | 1 | BWG 的 `PEAK_BIOMES_BWG` 对 WARM 带最干旱两格主动 `DEFERRED` 回原版 |
| **冰海滩** | 1 | BWG 的 `BEACH_BIOMES_BWG` ICY 行全 `DEFERRED`——BWG 没有冰海滩 |
| **其他硬编码位置** | 2 | `stony_shore` / `windswept_savanna` 由 `OverworldBiomeBuilder` 中**未被 TerraBlender 覆写**的私有方法产生（`addMidSlice` / `addLowSlice` / `maybePickWindsweptSavannaBiome`），BWG 在这两处从不放置自己的群系 |

**这 21 个是当前阶段的已知缺口，不是最终状态。** 后续计划用 `beloong:` 命名空间的
自制群系接管它们，见第十节。

> 判据的一致性说明：`stony_shore` 与 `windswept_savanna` 确实有"尚可的替身"
> （`basalt_barrera` 带 `beach`+`wasteland` tag；`firecracker_chaparral` 与 `araucaria_savanna` 同格），
> 把它们收进白名单是**刻意选择保守**——宁可暂时保留原版，也不接受语义不搭的替代。


### 4.7 表面规则与结构

- **表面规则**：TerraBlender 的 `NamespacedSurfaceRuleSource` 按群系命名空间分发规则。
  它是**两段式**而非二选一——BWG 规则返回 `null` 时才落到原版规则。
  因此 `biomeswevegone:*` 走 BWG 规则，白名单里的 `minecraft:*` 走原版规则，行为一致。
  这一机制也为后续自制群系自带地表规则留了口子（见第十节）。
- **结构**：BWG 结构经由 `NoiseGeneratorSettings` 的 structure settings 生效，
  与主世界共享 `settings: minecraft:overworld`，行为一致。
- **群系筛选**：BWG 配置文件中被禁用的群系在天灾维度**不会被选为目标**
  （`DisasterBiomeSubstitution` 会检测到并**保留原版群系 + 记 ERROR**，无兜底群系）。
  注意：被禁用的 BWG 群系在 BWG 侧会被改写成 `DEFERRED_PLACEHOLDER`，
  即**退回原版兜底树**——在剔除生效后，兜底树里已是 BWG 群系，不再产出原版群系。
- **映射表回避 BWG 默认禁用的群系**：BWG 在 `BWGWorldGenConfig.getDefaultBiomes()` 里
  **硬编码禁用** `biomeswevegone:eroded_borealis`。若映射表的某个目标指向它，那么在未手工改过
  BWG 配置的环境上该映射会静默失效。因此映射表**刻意不使用它**——
  `grove` 改映射到默认启用的 `frosted_taiga`。**新增映射条目时必须核对目标的默认启用状态。**

### 4.8 实测确认

**生成层**——关卡实际持有的参数列表（反射读取 `biomeSource.parameters()` 的 `values`）：

```
关卡 biomeSource = MultiNoiseBiomeSource, parameters = Left(ParameterList)
关卡参数列表：共 7593 条，其中 BWG 6782 条、黑名单 0 条
```

**替换账目**（启动日志）：

```
[BeLoong] 天灾维度群系替换：参数点 7593 个 = 替换 6782 + 白名单保留 811 + 未能求解 0（替换生效）
```

`7593 = 6782 + 811`，逐点闭合。白名单 21 项占 811 点（前 14 项 41 点 + 后 7 项 770 点）。

**查询层**（服务端启动后逐维度打印 `possibleBiomes()`）：

| 维度 | 白名单原版 | 待剔除残留 | BWG | 判定 |
|---|---|---|---|---|
| `minecraft:overworld` | 21 | 32 | 0 | ✅ 正确（主世界保留了全部 53 个原版群系） |
| `beloong:disaster` | **21** | **0** | 55 | ✅ 目标达成 |
| `minecraft:the_nether` | 0 | 5 | 0 | ✅ 未受污染 |
| `minecraft:the_end` | 0 | 5 | 0 | ✅ 未受污染 |
| `beloong:loong_palace` | 0 | 0 | 0 | ✅ 未受污染 |

> 主世界那一行的"21 + 32"只是把 53 个原版群系按本模组的白名单口径分了类，
> **不代表主世界被改动**——主世界仍是完整的 53 个原版群系（BWG = 0）。

TerraBlender 仅为下界与天灾打印初始化行，主世界**从不出现**——与设计意图一致。

> ⚠️ **验证方法警告（两条）**
> 1. `tools/scan-biomes.js`（区块 NBT 扫描）**读数失真**：会把未生成群系的区块
>    （`Status=minecraft:structure_starts`）也算进去，且统计的是 palette 出现次数而非群系体积。
>    **不得用于"某群系是否生成"的判定。** 验证一律以**游戏内存**为准：
>    `ServerLevel.getBiome(pos)` 或 `chunk.getSection(i).getBiomes().get(x,y,z)`，
>    或反射调用游戏自己的 `ChunkSerializer.write` 后读 palette。
> 2. **旧区块的群系固化在 NBT 里、不会回填。** 用旧存档扫描必然得到假阳性——
>    加载旧区块还会刷新它的 `LastUpdate`，所以连"最后更新时间"都不能用来区分新旧。
>    **判据必须是"在从未探索过的区域新生成的区块"。**
> 详见 `docs/天灾维度群系剔除-两次尝试复盘.md` 第 3.4 节。

## 五、结构效果与禁空联动

天灾维度承载 Cataclysm 与 FDBosses 的高难度结构。进入这些结构范围时对玩家施加**禁空**效果，限制龙类飞行能力。

数据文件：`data/beloong/beloong/structure_effects/disaster.json`

| 结构 | 效果 | amplifier | duration |
|---|---|---|---|
| `cataclysm:acropolis` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:ancient_factory` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:burning_arena` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:cursed_pyramid` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:frosted_prison` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:ruined_citadel` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:soul_black_smith` | `beloong:flight_ban` | 5 | 100t |
| `cataclysm:sunken_city` | `beloong:flight_ban` | 5 | 100t |
| `fdbosses:chesed_arena` | `beloong:flight_ban` | 6 | 100t |
| `fdbosses:geburah_arena` | `beloong:flight_ban` | 6 | 100t |
| `fdbosses:malkuth_arena` | `beloong:flight_ban` | 6 | 100t |

**注意：该文件按结构 ID 匹配，不含维度限定条件。** 文件名 `disaster.json` 只是归类约定；若同 ID 结构出现在其他维度，效果同样生效。目前这些结构仅生成于天灾维度，因此实际作用范围等价。

### 配套实现

- `structure/StructureEffectLoader` — Codec 驱动的 `SimpleJsonResourceReloadListener`，扫描 `beloong/structure_effects/*.json`，解析为 `Map<ResourceKey<Structure>, List<EffectEntry>>`
- `structure/StructureEffectHandler` — 触发时机：
  - `ServerTickEvent.Post`：仅在玩家**所在区块坐标变化**时检测（避免每 tick 全量扫描）
  - `PlayerChangedDimensionEvent` / `PlayerRespawnEvent` / `PlayerLoggedInEvent`：清缓存并立即检测
  - `MobEffectEvent.Expired` / `Remove`：对 `Config.StructureEffects.watchedEffects` 中的效果，过期或被牛奶/指令移除时重检，若仍应生效则取消移除（防闪烁）
  - 命中判定：玩家 AABB 与结构 `StructureStart` 包围盒求交
  - 支持可选的 `advancement` 条件（进度已完成则跳过该效果）

### 效果本体

`registry/FlightBanEffect` — 每级降低 1 点 `dragonsurvival:flight_level`：

- 属性修饰符由 `ModMobEffects` 注册时通过 `addAttributeModifier` 挂到该属性上，原版按 `amount × (amplifier + 1)` 自动缩放
- `onEffectStarted()` 在修饰符生效后检查：若飞行等级 `< 0` 且玩家正在展翅，**强制收翅**并向所有追踪该玩家的客户端同步 `SyncWingsSpread`，同时发送 `message.beloong.flight_banned`
- 效果结束后**不自动恢复飞行**，玩家需手动按 G 键重新展翅
- 与 `BROKEN_WINGS` 的区别：`BROKEN_WINGS` 无条件收翅；禁空仅在等级降至负数时才收翅，保留了「低等级禁空只削弱悬停、不阻止飞行」的梯度

> ⚠️ **待复核项**：`flight_ban` 的等级 5/6 对应 `-6 / -7` 飞行等级。请对照《飞行等级系统》确认 DS 侧 `flight_level` 的实际量程——若上限远低于此，则该效果的梯度差异在实际游戏中不可观测，只剩下「强制收翅」这一行为。

## 八、设计决策记录

1. **纯数据包维度，无自定义 Java 维度类** — 复用原版主世界生成规则的最短路径，升级维护成本最低。
2. **`effects: minecraft:overworld`** — 天灾不需要自定义天空。把天空系统的影响范围严格限制在龙宫，避免两套维度机制相互干扰。
3. **用 `replace: true` 排除主世界而非 Mixin** — 在 tag 层做取舍是纯数据驱动方案，不引入对 TerraBlender 内部实现的耦合，也不需要 Mixin 即可达成「主世界退回原版」。
4. **`CloneParameterListMixin` 必须存在** — 主世界与天灾共用同一个 `multi_noise` 预设，TerraBlender 的原地初始化会跨维度泄漏。clone 是保证隔离的最小改动。
5. **数字槽位而非语义化眼球键** — 早期用 `"cataclysm:mech_eye"` 等短键导致枚举与硬编码 Map 绑定、配置形同虚设。数字槽位让配置列表与纹理解耦，任意物品 ID 均可工作。
6. **multipart 而非 variants** — variants 需穷举 104 种排列，multipart 靠条件匹配天然忽略非法组合。
7. **重实现渲染器而非继承 `TheEndPortalRenderer`/`TheEndPortalBlock`** — 原版渲染器在字节码层把 BlockEntity 硬转型为 `TheEndPortalBlockEntity`，无法子类化复用，只能重实现。（注：此处只说"必须自己写渲染器"，**不代表必须自研着色器**——用哪条管线是独立决策，见第 11 条。）
8. **上下行判断用「当前维度是否为天灾」** — 而不是判断「是否为配置的源维度」。这让任意维度（不只主世界）进入传送门都能去天灾，且下行逻辑无需区分来源。
9. **冷却写入玩家持久化 NBT** — 跨维度、跨重登保持，避免玩家在传送门两侧反复弹跳。
10. **框架破坏时用 `level.destroyBlock`** — 直接复用原版破碎音效与粒子，无需自行实现特效。
11. **渲染改用标准实体管线（Iris 兼容），代价是放弃视差隧道** — 最初实现为自研 `ShaderInstance`（`beloong:rendertype_disaster_portal`，`.vsh`/`.fsh` 照搬原版 `rendertype_end_portal`），在 Iris 光影下**完全不渲染**：Iris 只把原版管线映射到 shader pack 的 `gbuffers_*`，自定义着色器 ID 不在其映射表内，开启光影且禁用未知着色器时整块丢弃。改为 `RenderType.entitySolid()` 后映射到 `ENTITIES_SOLID`，原版与光影下均可见。
    - **代价**：原版 `end_portal` 着色器的多层视差采样（随视角滑动的星空隧道）无法在标准管线中复现，观感退化为按世界坐标连续平铺的静态星空贴图；且传送门会接受 shader pack 对 `gbuffers_entity_solid` 的光照/PBR/阴影处理。已由实机测试确认可接受。
    - **随之删除的死代码**：`BeLoongCoreClient.disasterPortalShader` 字段、`onRegisterShaders` 事件处理器、`assets/beloong/shaders/core/rendertype_disaster_portal.{json,vsh,fsh}`。改造后它们已无任何消费方。
    - **不引入 Iris 依赖**：全程只用原版 `RenderType`，因此不需要 `compileOnly`/`localRuntime` 任何光影模组，也不需要 `ModList.isLoaded` 守卫。
12. **在 TerraBlender「复印参数列表」的时机改写群系，而不是从源头重建** — 曾有一条更激进的路线
    （见 `disaster_test` 分支）试图在原版生成 `multi_noise` 对照表的 preset 阶段直接重建，
    用 7 个 Mixin 注入点全部失败。根因是该时机**极早**：早于任何维度上下文（判断不了维度身份）、
    早于 Forge 配置加载（读配置直接 NPE），且 `PUTFIELD` / `INVOKEDYNAMIC` 不是合法的注入点说明符。
    改为在 `LevelUtils.initializeBiomes` 复印副本的瞬间改写后，维度身份、注册表、配置全部就绪，
    且操作对象是副本，主世界天然隔离。完整复盘见 `docs/天灾维度群系剔除-两次尝试复盘.md`。
13. **生成层与查询层必须分别处理** — 两者是独立路径：生成走 `getNoiseBiome → findValuePositional`
    （用 region 树 + 兜底树），查询走 `possibleBiomes()`（由 `values()` 现算）。
    只修生成层时，区块生成已干净，但 `/locate biome` 与自然罗盘仍能搜到原版群系。
14. **查询层的过滤必须发生在「缓存闭包被建立」的那一点** — TerraBlender 的
    `appendDeferredBiomesList` 会把 `possibleBiomes` 换成一个缓存闭包，闭包在替换那一刻固化集合。
    过滤注入到 `collectPossibleBiomes()` 是无效的（该方法是缓存建立时调用一次，之后不再经过）。
15. **维度识别用语义判据而非对象身份** — 关卡实际持有的 `BiomeSource` 与 TerraBlender
    初始化时拿到的不是同一个实例（实测 `parameters()` 返回的 `ParameterList` 不同），
    因此按实例登记不可靠。最初改用「参数列表里是否含 `biomeswevegone:` 群系」这一语义判据。
    **该判据已废弃**（它依赖"主世界不含 BWG 群系"这一前提，且真正兜住它的是数据包 tag 覆盖），
    现行做法见决策 21。
16. **必须保留 21 个原版群系（分阶段完成）** — 判据是「BWG 在结构上不覆盖该参数区」：
    洞穴占 `depth ≥ 0.2` 而 BWG 群系全为 `depth = 0`；BWG 完全没有河流群系；
    海洋的寒/冷/中性三列 BWG 主动留空；`SHATTERED_BIOMES_*` 两个数组 25 格全空；
    `PEAK_BIOMES_BWG` 对 WARM 带、`BEACH_BIOMES_BWG` 对 ICY 带主动 defer；
    `stony_shore`/`windswept_savanna` 位于未被 TB 覆写的私有方法中。
    这 21 个留待后续用 `beloong:` 自制群系接管，见第十节。
17. **验证必须读游戏内存，不能依赖 NBT 扫描工具** — 本项目的 `tools/scan-biomes.js`
    会把尚未生成群系的区块（`Status=minecraft:structure_starts`）计入统计，且量纲为
    palette 出现次数而非群系体积，读数显著失真。曾因此一度误判实现失败。
    验证一律用 `ServerLevel.getBiome()` 或 `chunk.getSection(i).getBiomes()`；
    或反射调用游戏自己的 `ChunkSerializer.write` 读 palette。
    **且必须用"从未探索过的新区域"**——旧区块的群系固化在 NBT 里、不回填。
18. **BWG 配置读取用反射而非直接 import** — 直接引用使其方法在**类校验期**就解析 BWG 类，
    BWG 缺席时抛 `NoClassDefFoundError`——该错误发生在进入方法体之前，外层 `try/catch` 捕获不到，
    会导致 Mixin 应用失败。故改用 `Class.forName` + `ModList` 守卫，BWG 因此不需要 `compileOnly`。
19. **本功能不提供任何配置项** — 白名单与映射表是硬编码的结构性决策。移除早期
    `[disaster_biomes]` 配置节的直接原因：`enabled` 开关**只覆盖生成层、覆盖不到查询层**，
    导致"关闭"不仅没回到旧行为，反而制造出「群系照常生成、但 `/locate` 搜不到、
    结构集与地物被静默剔除」的第三种状态（因为过滤后的 `possibleBiomes` 会进入
    `ChunkGeneratorStructureState.hasBiomesForStructureSet` 与 `ChunkGenerator.applyBiomeDecoration`
    的 `retainAll`）。移除 `fallbackBiome` 的原因：它可按配置指向任意群系（包括黑名单里的原版群系），
    等于给"绕过白名单"开了后门；改为**不可用时保留原版并记 ERROR**，更安全也更简单。
20. **TerraBlender 与 BWG 改为 required 依赖** — 本功能的生成与查询两层都建立在
    TerraBlender 的注入之上（查询层的注入目标 `appendDeferredBiomesList` **只由 TB 提供**，
    原版 `BiomeSource` 没有这个方法），而全部映射目标都来自 BWG。
    在 `optional` 声明下，卸掉 TB 会从"功能失效"变成**启动崩溃**（`defaultRequire: 1`）。
    改为 required 与实际依赖关系一致，也顺带保证了 mixin 的应用顺序（两者都已有 `ordering="AFTER"`）。
21. **查询层与生成层共用「是否真的生效」标志** — `PossibleBiomesFilterMixin` 读
    `DisasterBiomeSubstitution.isSubstitutionApplied()`，而不是自己做维度判定。
    这样两层天然一致：替换没发生，查询层就不过滤。时序上安全——
    实测 `filter()` 比天灾的 `appendDeferredBiomesList` 早 426 ms。
22. **写入的新 supplier 必须保序且记忆化** — `possibleBiomes()` 的迭代顺序会进入
    `FeatureSorter.buildFeaturesPerStep`，决定 `PlacedFeature` 的全局编号，进而影响
    `setFeatureSeed` 与地物放置顺序。原版用 Guava `ImmutableSet`、TB 用 `ObjectLinkedOpenHashSet`，
    两者都保序；`Set.copyOf` 返回的 `ImmutableCollections$SetN` 其迭代顺序由每次 JVM 启动
    随机化的 `SALT32L` 决定，**不保序**。同时原版用 `Suppliers.memoize` 包裹该字段，
    重建缓存时若不重新包裹就丢失了记忆化。故用 `ImmutableSet.copyOf` 并一次算好快照返回常量。
23. **无配置项 ⇒ 异常安全是必需而非可选项** — 没有 `enabled` 开关意味着没有逃生舱，
    所以 `cloneBeforeInit` 的替换段必须 `try/catch`，失败时**继续**执行原有的
    `initializeForTerraBlender` + `setParameters`（退化为 TB 原行为）。
    若不捕获，异常会穿透 `LevelUtils.initializeOnServerStart` 的 level stem 循环，
    导致该维度之后的所有 level stem 全部不再初始化。

## 十、后续计划：用自制群系接管白名单 21 项（第二阶段）

**第一阶段已完成**：天灾维度的 53 个原版主世界群系中，32 个已被替换为 BWG 群系，
黑名单残留为 0；查询层（`possibleBiomes()`）同步干净，`/locate` 查不到黑名单群系。
**第二阶段目标**：把仍保留的 21 个白名单原版群系换成 `beloong:` 命名空间的自制群系，
使天灾维度**不含任何 `minecraft:` 群系**。

### 10.1 这 21 项为什么只能靠自制群系

见 4.6 节。13 项是**参数空间上的结构缺口**（BWG 根本没往那里放群系），
另有 2 项是**代码路径缺口**，还有 6 项是**刻意保守**（有替身但语义不搭，暂不收）：

| 类别 | 数量 | 缺口性质 | 自制群系的改造点 |
|---|---|---|---|
| 海洋 | 9 | BWG 只填暖/热两列，寒/冷/中性三列留空 | 需照顾结冰语义（`frozen_ocean` / `deep_frozen_ocean` 会结冰、有冰山） |
| 河流 | 2 | BWG 完全没有河流群系（源码内 `river` 零命中） | 需具备水体生成语义（原版河流群系触发水体/河床生成） |
| 洞穴 | 3 | BWG 无任何 `depth > 0` 的群系 | 需正确处理 `depth` 参数；地表规则可用命名空间隔离（见 10.2） |
| 碎裂地形 | 3 | BWG 的 `SHATTERED_BIOMES_*` 两数组 25 格全空 | 侵蚀维固定 `[4500,5500]`，需配套专属地表表现 |
| 暖带裸岩峰 | 1 | BWG 对 WARM 带最干旱两格主动 `DEFERRED` | — |
| 冰海滩 | 1 | BWG 的 ICY 海滩行全 `DEFERRED` | — |
| 其他硬编码位置 | 2 | `stony_shore` / `windswept_savanna` 由 TerraBlender **未覆写**的私有方法产生 | — |

### 10.2 关键手段：命名空间地表规则

`NamespacedSurfaceRuleSource` 是**两段式**而非二选一（`TerraBlender/.../surface/NamespacedSurfaceRuleSource.java:56-68`）：

```java
if (biome.is(key -> this.rules.containsKey(key.location().getNamespace())))
    state = this.rules.get(...getNamespace()).tryApply(x, y, z);
if (state == null)                     // ← 只有在上面返回 null 时才落到原版规则
    state = this.baseRule.tryApply(x, y, z);
```

`SurfaceRuleManager.addSurfaceRules(OVERWORLD, namespace, rules)` 接受任意命名空间。
**因此自制洞穴群系可以自带专属地表规则**，不必迁就原版——
这正是"必须保留原版洞穴群系"这一约束的解除路径。

### 10.3 迁移路径（改动面很小）

两条注入路径（`CloneParameterListMixin` 生成层 / `PossibleBiomesFilterMixin` 查询层）
**无需任何改动**——它们只认 `WHITELIST` 与 `DisasterBiomeMapping` 两个抽象：

1. 新建 `beloong:` 命名空间的群系（海洋 / 河流 / 洞穴可分批）并注册
2. 在 `DisasterBiomeMapping` 中把原版群系的对应项直接指向 `beloong:` 群系
   （注意 `isUsable` 是 `registry.getHolder(key).isEmpty()`，自制群系必须在**该注册表冻结前**注册好）
3. 从 `DisasterBiomeSubstitution.WHITELIST` 中**逐项移除**已接管的白名单条目
   （移除一项 ⇒ 该项从"白名单保留"转入"替换"，账目里的 `811` 会变小、`6782` 会变大）
4. 如需专属地表表现，注册 `beloong` 命名空间的 surface rule

每接管一项都要重跑 4.8 的两条验证（关卡参数列表 + 日志账目），确保
`替换 + 白名单保留 + 未能求解 = 参数点` 仍然逐点闭合，且 **`未能求解 = 0`**。

### 10.4 前置调研项（进入第二阶段前须先验证）

1. **自制群系的注册时机**——`filter()` 在 `LevelUtils.initializeOnServerStart` 期间执行，
   必须确认此时 `beloong:` 群系已可被 `registry.getHolder(key)` 解析，否则会走"保留原版 + 记 ERROR"
2. **水体语义**——自制河流/海洋群系是否会自动获得水体生成（是否需要在 `BiomeSpecialEffects`
   或维度层的 `NoiseGeneratorSettings` 侧配合），原版是靠群系 tags + `BiomeGenerationSettings` 驱动的
3. **结冰语义**——`frozen_ocean` 的结冰是硬编码在群系 temperature 上的行为，需确认自制海洋群系的温度设置
4. **碎裂地形的侵蚀维**——自制群系在 `[4500,5500]` 侵蚀区是否需要不同的噪声设置
5. **结构联动**——`structure_effects/disaster.json` 按**结构 ID** 匹配，与群系无关，
   预期不受影响；但结构自身的 `biomes` 生成条件（如 BWG 结构只生成在 BWG 群系里）需实测确认
6. **游标成本**——白名单缩小意味着 `filter()` 的替换分支执行次数上升，需复测启动耗时
   （当前 `filter()` 实测约 426 ms）

### 10.5 明确不要做的事

- **不要**为了"填满参数空间"而把语义不搭的 BWG 群系塞进白名单位置
  （见 4.6 末尾的一致性说明：`stony_shore` / `windswept_savanna` 是刻意保守）
- **不要**新增 `eroded_borealis` 这类目标——BWG 默认禁用，干净部署上会静默失效
- **不要**重新引入 `[disaster_biomes]` 配置项（决策 17：全部硬编码，无逃生舱）
- **不要**调整 `data/terrablender/tags/dimension_type/overworld_regions.json`——
  它是主世界/天灾共享的一票否决开关，改动等于同时动两个维度
