# 天灾维度群系剔除 —— 两次尝试的经验与教训

**Date:** 2026-09-11
**Status:** 定稿（第一阶段已完成并验收；第二阶段的规划见 [`docs/天灾维度总设计.md`](天灾维度总设计.md) 第十节）
**适用分支:** `disaster_test`（已废弃）、`disaster2`（现行）

> 本文不是设计文档，而是**复盘**。现行实现见 `docs/天灾维度总设计.md` 第四节；
> 第一阶段的施工依据见 `docs/plans/2026-09-11-disaster-vanilla-biome-removal-design.md`。
> 本文记录的是"为什么这样做／为什么不那样做"，供后续会话避免重复踩坑。

> （+3 碎裂地形、`stony_peaks`、`snowy_beach`、`stony_shore`、`windswept_savanna`），
> 相应地从"39 个替换"变为"32 个替换"。下文出现的 14 / 39 均按当时的中间状态理解。

## 一、目标与背景

天灾维度与主世界共用 `minecraft:overworld` 的 `multi_noise` 预设，因此它的群系对照表
就是原版主世界那份（7593 行）。TerraBlender（BWG 的前置）把 BWG 群系**叠加**在这张表上：
BWG 填了的地方用 BWG，留空的地方**退回原版**。

结果是"**原版打底 + BWG 叠加**"，实测原版群系仍占约 65%（`plains` 一项就占 65%）。

目标是：让天灾维度不再出现不需要的原版群系，只保留结构上必需的
（9 海洋 + 2 河流 + 3 洞穴，后扩为 21 项），其余换成 BWG 群系；并且这些群系要从
`BiomeSource.possibleBiomes()` 里消失，使 `/locate biome` 搜不到、自然罗盘只显示在主世界。

## 二、`disaster_test`：想从源头重建

### 2.1 思路

不去改叠加层，而是**从源头把整张表重建**——让天灾维度的参数列表里根本不含原版群系。
要重建，就得在原版**生成这张表的那一刻**插手，也就是
`MultiNoiseBiomeSourceParameterList` 的 preset 构建路径。

这条路线的目标比现在更激进：**彻底无原版群系**，连海洋、河流、洞穴都要换成 BWG 或自制群系。

### 2.2 结果：12 个提交、7 个注入点，全部失败

代码最终整体撤销，分支停在"恢复可运行状态"。失败原因见下节。

### 2.3 失败原因（技术死路 —— 这些是真的走不通）

| # | 尝试 | 报错原文 / 现象 | 性质 |
|---|---|---|---|
| 1 | `@Inject` 到 `Preset$SourceProvider.apply`，接收者写 `Object` | `Found unexpected argument type java.lang.Object at index 0` | 该接口是包私有，源码无法引用 |
| 2 | `@At("PUTFIELD")` 改写 `parameters` | `PUTFIELD is not a valid injection point specifier` | **注入点说明符本身非法** |
| 3 | `@At("INVOKEDYNAMIC")` 拦截合成 Consumer | `INVOKEDYNAMIC is not a valid injection point specifier` | **注入点说明符本身非法** |
| 4 | 改写 `OverworldBiomeBuilder.addBiomes` + `@Invoker` 回调原生实现 | `StackOverflowError` | `@Invoker` 仍会调回被改写的方法，必然递归 |
| 5 | 同 4 但去掉配置读取 | NPE：该时机早于 Forge 配置加载 | 时机太早，`Config` 尚未初始化 |
| 6 | `@Redirect ImmutableList$Builder.build()`，按方法名匹配 | `could not find any targets matching 'generateOverworldBiomes'` | 未命中 |
| 7 | 同 6，改用完整描述符 | 仍未命中 | 描述符与 Mixin 期望不符 |

**归纳：**

- 前两条说明 **Mixin 的 `@At` 只接受有限几种位置说明符**，`PUTFIELD` / `INVOKEDYNAMIC`
  不在其中。这两条不是"没找对写法"，而是**语法层面就不成立**。
- `@Invoker` 的语义是"生成一个调用原方法的桥"，**不能**用于"改写方法体后再回调自己"。
- preset 展开发生在 `Bootstrap` 阶段，**早于任何世界/维度上下文，也早于 Forge 配置加载**。
  那个位置既判断不了维度，也读不了配置。

### 2.4 失败原因（方法论 —— 这些本可避免）

| # | 教训 | 具体表现 |
|---|---|---|
| **M1** | **不得把"代码执行了"当成"结果被使用了"** | 前 6 次尝试的日志都显示"替换成功"，但世界照旧。因为诊断跑在**初始化期**，而被观察的对象是一份**没人读的副本**。唯一有效的证据来自"在区块生成那一刻读取 biomeSource 实际持有的对象" |
| **M2** | **Mixin 的注入点在应用期才校验，构建期不校验** | `gradlew build` 成功、`require = 1` 通过，**都不能作为注入点可用的证据**。必须实际启动游戏看日志。注入失败会在 `Bootstrap` 阶段崩溃 |
| **M3** | **不得用常量池字符串搜索推断注解里写了哪个类** | `@Mixin` 的 value 是 `Class` 字面量，编译后只留字段描述符，**类名字符串不会进常量池**。据此误判过一次目标类 |
| **M4** | **参考源码必须与运行时工件版本一致** | 排查初期参考的是 TerraBlender `26.1.2` 分支（对应 MC 26.1.2），而项目用的是 1.21.1。结论全错。**应以 `javap` 反编译运行时实际加载的 jar 为准** |
| **M5** | **误判根因会掩盖真根因** | 见下节 |

### 2.5 关键教训：一次被误导的"根因修复"

提交 `21fc73b`（标题："修复群系接管失效的根因：TerraBlender 回退到固化索引"）
判定根因是 `initialized` 标志未置位，修复手段是反射写入 `initialized = true`。

**这个修复是多余的。** TerraBlender 的 `MixinParameterList.initializeForTerraBlender`
结尾本来就有：

```java
this.treesPopulated = true;
this.initialized = true;      // 它自己会置位
```

反射写进去的值，和已经在里面的值一模一样——**没有改变任何行为**。

而该提交信息自己就记载了否证：

> 诊断①：替换后参数列表中已是 [deep_dark, dripstone_caves, lush_caves]，原版 53 种里其余 50 种已不存在
> 诊断②：写回 biomeSource 生效（identity 一致）
> **但存档扫描显示天灾维度仍在生成 minecraft:plains / river / stony_shore**

**"诊断显示干净"与"世界仍生成原版群系"是同时成立的。** 这就是 M1 的又一个实例。

后果：真根因（替换没有落到"生成时实际使用的那个参数列表"上）被这个假根因掩盖，
随后转去攻 preset 路线（7 个注入点全灭），最后连**已经做对的那部分**也一起撤掉了。

> **如果当时停下来、用"读区块内存群系"这种消费端证据确认一次，就不会走这段弯路。**
> 这也是 `disaster2` 之所以能成的直接原因——它把 M1 当成硬约束来执行。

### 2.6 最终为何"变回原版 + BWG"

撤销提交 `306b4b1` 本身只是**从 `beloong.mixins.json` 移除 `PresetBiomeTakeoverMixin` 的注册**，
是纯机械操作。但此时接管逻辑已经**搬过一次家**：

```
第一阶段：接管逻辑写在 CloneParameterListMixin 里        ← 21fc73b 属此阶段
第二阶段：逻辑搬到 PresetBiomeTakeoverMixin，
          CloneParameterListMixin 被还原成"只做隔离"     ← 5156ff9 起
第三阶段：PresetBiomeTakeoverMixin 注入点全被否决，
          从 mixins.json 移除注册                        ← 306b4b1
```

到第三阶段，`CloneParameterListMixin` 已退回纯隔离职责（其类文档明确写着
"**群系替换不在本类**"），而 `PresetBiomeTakeoverMixin` 又被摘掉注册——
**两份代码加起来一行群系替换都不剩**，因此生成结果自然回到"原版打底 + BWG 叠加"。

### 2.7 遗留的可用资产

| 资产 | 状态 |
|---|---|
| `worldgen/DisasterBiomeMapping`（原版 → BWG 气候对照表） | **可用**，已被 `disaster2` 沿用并修正 |
| `mixin/CloneParameterListMixin`（参数列表隔离） | **可用**，独立职责，`disaster2` 继续使用 |
| `tools/scan-biomes.js`（区块 NBT 扫描） | **读数失真**，见 3.4 节，仅可用于粗粒度观察 |
| `docs/plans/...-handover.md`（交接文档） | 保留，其"教训"章节价值很高 |

## 三、`disaster2`：在"复印"的那一刻改写

### 3.1 思路

不去重建那张表，而是**在 TerraBlender 已经为每个维度复制出一份副本的时机，把副本上的行改写掉**。

`LevelUtils.initializeBiomes` 里本来就有这一步：

```java
Climate.ParameterList cloned = (Climate.ParameterList) receiver.clone();   // 复印
((IExtendedParameterList) cloned).initializeForTerraBlender(...);           // 在副本上建索引
((MultiNoiseBiomeSourceAccess) biomeSource).setParameters(Either.left(cloned));
```

我们的改动就插在"复印"和"建索引"之间：**复印 → 改写副本上的群系 → 建索引 → 交给这个维度用**。

**为什么这个时机好：**

- 此时**维度身份已知**（`levelKey` 参数直接给出），能判断是不是天灾维度
- 此时**注册表已就绪**（`targetRA`），能查群系、能读 BWG 配置
- 此时**配置已加载**——不像 preset 阶段那样会 NPE
- 操作对象是**副本**，主世界的共享原件天然不受影响

### 3.2 具体做法

```
① cloned = receiver.clone()
② cloned.values = 一个新列表（先断开与原件共享的那个 List）
③ 逐行改写：非 minecraft: 命名空间 → 不动
             命中白名单 14 项        → 不动
             其余 39 项              → 查对照表换成 BWG 群系
④ cloned.initializeForTerraBlender(...)   ← 兜底树此时才建立，读到的是改写后的行
⑤ biomeSource.setParameters(Either.left(cloned))
```

**②为什么必须换新列表**：`clone()` 是浅拷贝，副本与原件**共享同一个 `values` 对象**。
直接改行会连主世界一起改。`values` 是 `final`，所以用 `@Mutable @Accessor`（`ParameterListAccessor`）
整体换掉——这也是 TerraBlender 自己改 final 字段的手法。

**③的实测数字**：`7593` 行中改写 `7552` 行、保留 `41` 行。41 恰好等于白名单 14 个群系占的行数，
两个数精确吻合，这是"改写逻辑正确"的第一个硬证据。

**维度守卫**：这个改写点对**所有**被 TerraBlender 判定为 `RegionType.OVERWORLD` 的维度都会触发。
实测 `minecraft:the_nether` 也会命中——下界 5 个群系会被换成草原、针叶林。
因此加了 `isTargetDimension(levelKey)`，只对 `beloong:disaster` 动手。

**主世界为何天然安全**：主世界不在 `overworld_regions` tag 里，
`LevelUtils.getRegionTypeForDimension()` 返回 `null`，`initializeBiomes` 在到达改写点**之前就已 return**。

### 3.3 中途的失败：只修了一条路

**第一版落地后实测失败**——天灾维度仍生成黑名单原版群系，`/locate` 仍能搜到。

根因：天灾维度有**两条彼此独立**的路径，第一版只修了其中一条。

| 路径 | 数据源 | 修复 |
|---|---|---|
| **生成路径** `getNoiseBiome → findValuePositional` | 被改写过的副本的 `values` | `CloneParameterListMixin` |
| **查询路径** `/locate biome`、自然罗盘、地图 → `possibleBiomes()` | **关卡实际持有**的那份 `parameters().values()` | `PossibleBiomesFilterMixin` |

**第一条补丁打在了错的位置**：注入 `MultiNoiseBiomeSource.collectPossibleBiomes()`，
日志确认**注入确实触发、判据也正确**，但仍无效果。

原因：`possibleBiomes()` 的实现是 `possibleBiomes.get()`——读一个 supplier 字段，
而 TerraBlender 的 `MixinBiomeSource.appendDeferredBiomesList` 把这个字段**整体换成了一个缓存闭包**：

```java
this.possibleBiomes = () -> new ObjectLinkedOpenHashSet<>(possibleBiomes.stream().distinct()...);
```

闭包在**替换那一刻**就把集合固化了。`collectPossibleBiomes` 只在缓存建立时被调用一次，
之后 `possibleBiomes()` 直接读缓存，**不再经过被过滤的方法**。

**正确做法**：注入到 `appendDeferredBiomesList` 的 HEAD，在那一点就让并入缓存的内容干净，
然后 `ci.cancel()` 跳过 TerraBlender 的原逻辑。

**如何识别天灾维度**：用**语义判据**——TerraBlender 传进来的追加列表里若含非 `minecraft:`
命名空间的群系（即 BWG 的），就是天灾维度。实测五个维度中只有天灾维度满足
（主世界 53 个全原版、下界 5 个全原版、末地走 `TheEndBiomeSource`、龙宫走 `FixedBiomeSource`）。

> ⚠️ **该判据的适用边界**：若将来主世界恢复 BWG 群系，此判据会同时命中主世界。
> 届时必须改为按维度身份打标记，不能只靠语义判据。

**结果**：天灾维度 `possibleBiomes` 从 **109 → 70**（14 白名单原版 + 55 BWG），黑名单 **0**。

### 3.4 第二个中途失败：被自己的验证工具误导

排查过程中，`tools/scan-biomes.js` 报出天灾维度含大量黑名单群系
（`plains 15840`、`ocean 5216` 等），与实机结论矛盾。

用**两种互相独立**的方式读同一批全新生成的区块，才发现是工具失真：

| 读数方式 | 结果 |
|---|---|
| **A. 内存**：`chunk.getSection(i).getBiomes().get(x,y,z)` | 种数 2，黑名单 **0**：`temperate_grove=30034`, `lush_caves=2734` |
| **B. 游戏自己的序列化器**：反射调用 `ChunkSerializer.write` 后读 palette | 种数 2，黑名单 **0**：`temperate_grove=490`, `lush_caves=53` |

按区块 `Status` 拆解暴露了工具的问题：

| Status | 区块数 | 含黑名单 | 比例 |
|---|---|---|---|
| `minecraft:structure_starts` | 2513 | 2513 | **100.0%** |
| `minecraft:full` | 2449 | 728 | 29.7% |

`structure_starts` 阶段的区块**根本还没生成群系**，却 100% 命中——说明脚本在读不属于它的字节。
且它统计的是"palette 出现次数"而非"群系实际占用体积"，量纲本身就不对。

**后续约定**：

- `scan-biomes.js` **不得再用于"某群系是否生成"的判定**，只可用于粗粒度分布观察，
  且结论必须用内存读数复核。
- 验证一律以**游戏内存**为准：`ServerLevel.getBiome(pos)` 或
  `chunk.getSection(i).getBiomes().get(x,y,z)`。
- 旧区块的群系固化在 NBT 里、不回填，**用旧存档验证必然得到假阳性**。

## 四、成与败的对照

| | `disaster_test` | `disaster2` |
|---|---|---|
| 切入点 | 原版生成对照表的过程（preset 构建） | TerraBlender 为维度复印表的时刻 |
| 手段 | 填满 BWG 数组的空格子 | 改写副本上的行 |
| 时机质量 | 极早：无维度上下文、配置未加载 | 很好：维度身份、注册表、配置全部就绪 |
| 与 BWG 的耦合 | 强（要动 BWG 内部结构） | 无（只读 BWG 的配置） |
| 影响面 | 若成功会覆盖所有实例 | 只影响副本，主世界天然隔离 |
| 结果 | 12 提交 / 7 注入点全部失败，代码已撤销 | 已落地并验证通过 |
| 失败模式 | 改错对象 + 误判根因 + 方法论文档缺失 | 漏掉第二条路径 + 验证工具失真 |

### 一句话总结

> `disaster_test` 想**从源头重建**那张对照表，卡在原版的构建时机与 Mixin 的能力边界上；
> `disaster2` 改为**在复印的瞬间改写副本**——时机更晚、信息更全、耦合更浅。
> 而"`/locate` 仍能搜到"的问题，是因为查询走的是另一条路（`possibleBiomes`），
> 补上第二个注入点即完整。

## 五、可以带走的规则（建议后续会话遵守）

1. **消费端取证**。只验证"代码执行了"是无效的。必须在**数据被真正使用的那一点**读结果。
2. **构建成功 ≠ 注入可用**。Mixin 注入点在应用期才校验，必须实机启动验证。
3. **先查清"有几个实例、有几条路径"**再动手。本项目两次翻车都源于只看到一个实例/一条路径。
4. **优先用 `@Accessor` 而非反射**改 final 字段。反射在部分构建配置下可能静默失败，
   而 `@Accessor` 在编译期就会报错。
5. **不要相信单一验证工具**。至少用两种互相独立的方式交叉验证关键结论。
6. **误判根因比不修更糟**——它会把后续排查引向错误方向，并可能让人撤掉已经做对的部分。
   判定根因前，先找一个能**否证**它的观测。
7. **参考源码必须与运行时工件版本一致**，以 `javap` 反编译实际加载的 jar 为准。

## 六、第二阶段：替换为自制群系（未开始）

> 本节是**当时的规划草案**。现行为准的版本见
> [`docs/天灾维度总设计.md`](天灾维度总设计.md) 第十节与
> `docs/plans/2026-09-11-disaster-phase2-handover.md`（第二阶段交接文档）。

第一阶段的结果是：天灾维度只保留 **21 个原版群系**（9 海洋 + 2 河流 + 3 洞穴 +
3 碎裂地形 + `stony_peaks` + `snowy_beach` + `stony_shore` + `windswept_savanna`），
其余全部为 BWG 群系。**这些是刻意保留的**，因为它们在参数空间中占据的位置
在 BWG 里没有对应物：

| 类别 | 为什么 BWG 替代不了 |
|---|---|
| **洞穴（3）** | 原版洞穴群系占 `depth ≥ 0.2` 的参数区域，而**所有 BWG 群系（及所有地表群系）的 `depth` 都是 0**。用地表群系填这些点，会导致地下直接生成地表群系 |
| **河流（2）** | BWG **完全没有河流群系**（其源码内 `river` 零命中，也不声明 `minecraft:is_river` 标签）。原版在 `EROSION[6] + coastContinentalness` 上独立注册 |
| **海洋（9）** | BWG 只在暖/热两列填了 `LUSH_STACKS` / `DEAD_SEA`，寒/冷/中性三列（占海洋 60%）主动留空 |
| **碎裂地形（3）** | BWG 的 `SHATTERED_BIOMES_BWG` 与 `SHATTERED_BIOMES_TERRABLENDER` 两个数组 **25 格全空** |
| **其余 4 项** | `stony_peaks`（BWG 对 WARM 带 defer）、`snowy_beach`（BWG 的 ICY 海滩行全 defer）、`stony_shore` / `windswept_savanna`（由 TB 未覆写的私有方法产生）——均属**刻意保守**，宁可暂留原版也不接受语义不搭的替代 |

**第二阶段的目标**：用 `beloong:` 命名空间的自制群系接管这些位置。

**关键手段**：`NamespacedSurfaceRuleSource` 提供了按命名空间分发地表规则的能力
（`TerraBlender/.../surface/NamespacedSurfaceRuleSource.java:56-68`），且是**两段式**而非二选一：

```java
if (biome.is(key -> this.rules.containsKey(key.location().getNamespace())))
    state = this.rules.get(...getNamespace()).tryApply(x, y, z);
if (state == null)                     // ← 只有在上面返回 null 时才落到原版
    state = this.baseRule.tryApply(x, y, z);
```

`SurfaceRuleManager.addSurfaceRules(OVERWORLD, namespace, rules)` 接受任意命名空间。
**因此自制洞穴群系可以自带专属的地表规则**，不必迁就原版规则——
这正是第一阶段"必须保留原版洞穴群系"这个约束的解除路径。

**前置调研建议**：

1. 自制群系需要处理 `depth` 参数（洞穴群系用 `depth` 区分，见上表）
2. 河流群系需要能生成水体语义（原版河流群系会触发水体生成）
3. 海洋群系需要照顾结冰语义（`frozen_ocean` 会结冰）
4. 确认替换后 `flight_ban` 等既有的结构联动不受影响（结构效果按结构 ID 匹配，与群系无关，应该不影响）
5. **自制群系的注册时机**——`filter()` 在 `LevelUtils.initializeOnServerStart` 期间执行，
   必须确认此时 `beloong:` 群系已能被 `registry.getHolder(key)` 解析

**迁移路径**：第二阶段只需修改
`worldgen/DisasterBiomeMapping`（或改为查 `beloong:` 命名空间）与
`DisasterBiomeSubstitution.WHITELIST`（白名单逐步清空），
生成/查询两条注入路径**无需改动**——它们只认"白名单"与"对照表"两个抽象。

每接管一项都要重跑验证（关卡参数列表 + 启动日志账目），确保
`替换 + 白名单保留 + 未能求解 = 参数点` 逐点闭合且 **`未能求解 = 0`**，
并且必须在**从未探索过的新区域**里实测生成。
