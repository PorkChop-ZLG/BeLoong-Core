# 自制龙之生存技能总设计

> **文档性质：** 本模组自己实现并注册进 Dragon Survival（下称 DS）的 **3 个龙技能**的总体设计说明。
> **事实口径：** 凡是「代码事实」都以当前工作区的 `文件:行号` 为准；凡引用设计文档的地方会标明该文档可能已过时。
> **更新日期：** 2026-09-18（含命名空间迁移后的状态）

## 一、范围与边界

### 1.1 本文覆盖

| 技能 ID | 中文名 | 英文名 | 一句话 |
|---|---|---|---|
| `beloong:air_strike` | 龙击长空 | Air Strike | 滑翔中撞到生物造成按速度缩放的高额伤害 |
| `beloong:tornado` | 龙卷风 | Tornado | 发射一个持续吸引并伤害周围敌人的自定义实体 |

- **整合包侧的分配与获取途径**。见 §3.5。
- DS 自身的技能框架（`DragonAbility` / `MagicData` / 施法流程）——只在解释自制技能行为时引用必要部分。

## 三、共同架构

### 3.1 三层结构

```
数据包层（JSON，可被整合包覆盖）
  data/beloong/dragonsurvival/dragon_ability/<id>.json
        │  声明 activation / actions / effect_type / icon / upgrade
        ▼
效果实现层（Java，注册进 DS 的 AbilityEntityEffect 注册表）
  com.zonlong.beloong.ability.<X>Effect
        │  apply(ServerPlayer dragon, DragonAbilityInstance ability, Entity target)
        ▼
世界表现层（按需）
  自定义实体 / 渲染器 / 伤害类型 / 粒子音效
```

**分层边界**：JSON 负责「数值、动画、音效、冷却、升级曲线」；Java 负责「行为、公式、伤害归因、失败提示」。伤害公式、伤害类型与参与属性**刻意写死在 Java 里**，JSON 不暴露——`AirStrikeEffect` 与 `TornadoEffect` 的字段表（§4.1 / §5.1）里没有任何公式相关字段，正是这个取舍的体现。

### 3.2 效果类型注册链

唯一注册点：`AbilityEffectRegistry.java:16-27`，在 `RegisterEvent` 上按 `event.getRegistry() == AbilityEntityEffect.REGISTRY` 判断后注册三个效果：

| 注册键 | 实现 | 提供方 |
|---|---|---|
| `beloong:tp_loong_palace` | `TpLoongPalaceEffect.CODEC` | `:19-20` |
| `beloong:air_strike` | `AirStrikeEffect.CODEC` | `:21-23` |
| `beloong:tornado` | `TornadoEffect.CODEC` | `:24-26` |

注册类用 `@EventBusSubscriber(modid = BeLoongCore.MODID)`（`:10`），因此走 mod 总线，无需在 `BeLoongCore` 构造函数里手工登记。

**JSON 里的 `effect_type` 必须与这里的注册键逐字一致**（`air_strike.json:8`、`tornado.json:8`、`tp_loong_palace.json:8`）——写错会得到「未知效果类型」的加载错误，不会静默生效。

### 3.3 数据驱动契约

三个 JSON 共用同一套 DS schema，字段由 DS 反序列化类决定（本模组不扩展 schema）：

| 段 | 必需性 | 作用 | 出处 |
|---|---|---|---|
| `actions[].target_selection` | 必需 | 选择目标的类型（`target_type`），如 `dragonsurvival:self` | `ActionContainer.java:14` |
| `actions[].target_selection.applied_effects.entity_effect` | 必需 | 效果列表，每项含 `effect_type` 与自定义字段 | `AbilityTargeting.java:87` |
| `actions[].target_selection.applied_effects.targeting_mode` | **必需** | 目标过滤口径（见 §7.5，对 `self` 目标实为声明性字段） | `AbilityTargeting.java:88` |
| `actions[].trigger_point` | 可选（默认 `default`） | 行动触发点 | `ActionContainer.java:15` |
| `actions[].trigger_rate` | 可选（默认 `1`） | **tick 间隔**：`actualTick % rate != 0` 则跳过 | `ActionContainer.java:16,21-25` |
| `activation` | 必需 | 激活方式（`simple` / `passive` / …） | `DragonAbility.java:56` |
| `icon.texture_entries` | **必需** | 等级 → 图标资源，无匹配时回退到首项 | `DragonAbility.java:61`、`LevelBasedResource.java:24-33` |
| `upgrade` | 可选 | 升级类型与上限；**缺失即按满级授予** | `DragonAbility.java:57`、`MagicData.java:503-508` |

**自定义字段的容错写法**：`AirStrikeEffect` 与 `TornadoEffect` 都用 `FLEXIBLE_LBV`（`Codec.either(LevelBasedValue.CODEC, Codec.DOUBLE)`）让同一个字段既能写纯数字也能写 `LevelBasedValue` 对象（`AirStrikeEffect.java:46-52`、`TornadoEffect.java:49-55`）。`TpLoongPalaceEffect` 无参，用 `MapCodec.unit`（`TpLoongPalaceEffect.java:43`）。

### 3.4 命名空间约定

**2026-09-18 起，三个技能全部位于 `beloong` 命名空间。** 这是从 `dragonsurvival` 迁移过来的。

规则（都经源码验证）：

- **能力注册项的命名空间由目录决定**：`data/<ns>/dragonsurvival/dragon_ability/<id>.json` ⇒ 能力 ID `<ns>:<id>`。所以文件必须放在 `data/beloong/dragonsurvival/dragon_ability/`。
- **能力名/描述的语言键由能力 ID 推导**：`Translation.Type.ABILITY` 的前缀是 `"dragon_ability.dragonsurvival."`，而 `wrap(ResourceLocation)` 执行 `prefix.replace(DragonSurvival.MODID, location.getNamespace())`（`Translation.java:83,144-150`）⇒ `beloong:tornado` 的键是 `dragon_ability.beloong.tornado`。调用点仅两处：`DragonAbilityInstance.java:360`（名字）、`AbilityAndPenaltyTooltipRenderer.java:240`（描述）。
- **图标可以从任意命名空间解析**：图标走原版 GUI 精灵图集（`net.minecraft.client.gui.GuiSpriteManager`，图集 `minecraft:gui`），而原版 `assets/minecraft/atlases/gui.json` 用的是**目录源**（`{"type":"directory","source":"gui/sprites","prefix":""}`）。目录源遍历**所有命名空间**，因此 `assets/beloong/textures/gui/sprites/abilities/*.png` 会自动进图集，**不需要额外的 atlas JSON**。
- **标签文件是例外**：标签的命名空间同样由目录决定。若要向 DS 的标签追加内容（例如 `#dragonsurvival:order` 或龙种标签），文件**必须**放在 `data/dragonsurvival/tags/...` 且带 `"replace": false`，放进 `data/beloong/` 只会定义出一个新标签。

> **参考模组的做法与本设计不同（记录以免误解）**：闭源模组「星辰龙」把技能注册项与图标都留在 `dragonsurvival` 命名空间（`data/dragonsurvival/dragonsurvival/dragon_ability/star_laser.json`、`assets/dragonsurvival/textures/gui/sprites/abilities/star/`），只把 `effect_type`、函数与语言文件放在自己的 `star_dragon` 下。**本模组选择全部迁入 `beloong`**，依据是上面三条源码事实，而不是照抄该模组。

### 3.5 「只出技能本体，不分配龙种」的边界

三个技能的获取途径**都不在本模组内**：

- 本仓库 `data/` 下没有任何把技能关联到龙种的标签（现有标签只有 `block` / `damage_type` / `item` / `dimension_type`）。
- 因此必须由整合包侧通过 `/dragon-ability add`、任务奖励、或 `data/dragonsurvival/tags/dragonsurvival/dragon_ability/<species>.json` 来分配。
- 这条边界在三个技能的设计里都被明确写成决策（§9.2「明确不做」的第一条）。

**⇒ 能力 ID 是对外契约**：任何外部授予点都必须跟着 ID 走。本次迁移已导致整合包侧 9 处引用失效，见 §12.2。

### 4.1 数据定义

| `speed_factor` | `lookup` `[1.0,1.2,1.4,1.6,1.8]`，fallback `linear 1.0 +0.2/级` | `:24-38` |
| `min_speed` | `0.8`（常数） | `:39` |

**`trigger_rate: 0.5` 的实际含义**：判定是 `rate > 0 && actualTick % rate != 0`（`ActionContainer.java:23`）。由于任何整数对 `0.5` 取模都是 `0`，该条件**恒不成立** ⇒ **每个 tick 都执行一次**。也就是说它表达的是「尽可能频繁地检测碰撞」，而不是「半速」。

### 4.2 效果实现与伤害公式

`AirStrikeEffect`（`ability/AirStrikeEffect.java`，158 行）是 `record(baseDamage, speedFactor, collisionSize, minSpeed)`（`:33-38`），因而是**被动、无状态**的：每次 `apply` 都重新读参数、重新算伤害。

`apply`（`:62-138`）的完整流程：

1. `target` 必须是 `ServerPlayer`，否则返回（`:63-65`）。
2. 施法者必须**正在滑翔**（`ServerFlightHandler.isGliding`），否则返回（`:67-69`）。
3. 取当前速度 `speed = player.getDeltaMovement().length()`（格/刻）；小于 `minSpeed` 则返回（`:72-76`）。
4. **武器伤害**：累加**主手**与**副手**物品上 `ATTACK_DAMAGE` 属性的 modifier 值（`:80-96`）。
5. **伤害公式**（`:98-100`）：

   ```
   伤害 = ( base_damage + 主手武器伤害 + 副手武器伤害 )
        × 当前速度(格/刻)
        × speed_factor
        × dragonsurvival:dragon_ability_damage 属性值
   ```

6. **actionbar 反馈**（每 5 刻一次，`:103-109`）：显示 `速度 × 20 × 3.6`（换算成 km/h）与本次伤害值。
7. **碰撞扫描**（`:111-116`）：取施法者碰撞箱**膨胀 `collision_size` 格**内的所有 `LivingEntity`，排除自己、排除已死与不可选中的。
8. 若一个都没扫到 → **直接返回，不折翼**（`:118-120`）。
9. 对每个目标用 `new DamageSource(damageType, dragon)` 结算（`:122-131`）——**直接实体与归因实体都是施法者**（二参构造器委派为 `this(type, entity, entity)`，`DamageSource.java:52-54`），因此击杀归因、进度与掉落都正常计入玩家。
10. 只要**至少一个**目标真的受到了伤害（`hurt` 返回 true），就把 `FlightData.areWingsSpread` 置 false 并同步给追踪者（`:133-137`）⇒ **强制收翅、结束滑翔**。

> **描述与实现的落差（须知）**：技能描述写「碰撞后**暂时无法飞行**」，但代码**没有**施加任何 `MobEffect`——`beloong:flight_ban` 效果（`ModMobEffects.java:65-75`，`FlightBanEffect extends MobEffect`，每级 −1 `dragonsurvival:flight_level`）**在本技能里没有任何调用点**，它是由结构效果数据包施加的（`data/beloong/beloong/structure_effects/disaster.json`）。本技能的实际做法是**收翅**：DS 的滑翔需要展翅，收翅即中断滑翔。

### 4.5 设计理由与历史

- 该技能经历过一次系统性改造：碰撞箱数据驱动、武器伤害叠加、乘以 `DRAGON_ABILITY_DAMAGE`、引入自定义伤害类型与死亡消息。**公式、伤害类型与参与属性三者刻意写死在代码里**，JSON 不暴露（§3.1）。
- 设计演变中值得记住的两处**方案变更**（早期计划里的写法均已被推翻）：
  1. 武器伤害最初计划取自 **SWORD 爪牙槽**（`ClawInventoryData.getData(player).getSword()`），**最终实现读的是主手 + 副手物品**（`AirStrikeEffect.java:80-96`）。
  2. `collision_size` 的 `per_level_above_first` 最初计划为 **0.0**，最终为 **0.5**（`air_strike.json:43`）。
- 关于「打到所有人、只排除自己」：这是**有意设计**，并在 2026-08-14 的裁定里被保留，同时把 `targeting_mode` 改为 `all_except_self` 以与声明一致（`memory/decisions-log.md:1225,1233`）。注意该字段实际不参与运行期过滤（§7.5）。

### 5.2 效果实现（发射）

`TornadoEffect`（`ability/TornadoEffect.java`，141 行）同样是 `record`，六个字段全是 `LevelBasedValue`。

`apply`（`:66-91`）：

1. 读等级，算出 6 个数值：伤害（**在这里就乘上 `DRAGON_ABILITY_DAMAGE`**，实体本身不碰属性系统）、寿命、吸引半径、伤害半径、吸力、飞行速度（`:68-76`）。
2. 取施法者准星方向 `dragon.getLookAngle()`（`:78`）。
3. 生成点 = `(x + look.x, getEyeY() − 0.5, z + look.z)`——**刻意照抄灾变（Cataclysm）原版的发射高度**，但不复刻它「生成点偏到侧面」的 bug（`:79-83`）。
4. 构造 `TornadoEntity`，`setPos`，把速度设为 `look × speed`，加入世界（`:85-90`）。

**调用契约（重要）**：`apply` **故意忽略 `Entity target` 参数**——龙卷风总是从施法者自身位置与准星方向生成。因此**必须**配合单目标行动 `dragonsurvival:self` 使用；若数据包把它换到 `area` / `disc` 等多目标行动下，每个匹配实体都会调一次 `apply`，一次施法就会放出 N 个龙卷风。代码里**不做拦截**（加运行时守卫会让单目标复用也付出代价），这写在类的 javadoc 里（`:29-37`）。

### 5.3 实体 `TornadoEntity`

`entity/TornadoEntity.java`（419 行），`extends Projectile`。

**注册**：`ModEntities.java:42-49` —— `sized(2.8F, 3.3F)`、`clientTrackingRange(10)`、`updateInterval(1)`、`fireImmune()`，`build("beloong:tornado")`。

- **碰撞箱**刻意取 3x 模型的视觉包围盒；`updateInterval(1)` 让服务端**每 tick** 下发位置包，因为 `Projectile` 在客户端侧的 `lerpTo` 是硬吸附——客户端在两次吸附之间用同步下来的速度自行外推一 tick，并同样做方块碰撞（`ModEntities.java:36-40` 的注释）。

**移动**（`advance()`，`:207-231`）：

- 服务端与客户端**都**执行位移，方式是 `this.move(MoverType.SELF, delta)` 后逐轴碰撞检测、把撞到的那一轴速度**取反**（镜面反弹，不衰减、不限次数）。
- **生物可穿透**（否则无法把敌人吸到身上）；**方块不穿透**。

**吸引**（`pull()`，`:294-324`）：

- 朴素「每 tick 朝中心加力」会越吸越快、穿过中心来回抖动，故实现为**阻尼 + 近中心限速**：保留 82% 既有水平速度，再加恒定牵引，最后按 `pull_strength × PULL_SPEED_FACTOR × min(1, 距离/2)` 封顶。
- `pull_strength <= 0` 视为「关闭吸引」（既不拉也不减速）——若没有这道守卫，`maxSpeed <= 0` 会让末尾的 `normalize().scale(maxSpeed)` 把目标水平速度清零甚至反向（`:295-300`）。
- 竖直方向另有 `clamp(current.y * 0.85 + PULL_LIFT, LIFT_MIN, LIFT_MAX)` 的抬升。
- 每次改写目标速度后置 `target.hurtMarked = true`，否则客户端不会应用服务端设的速度（`:322-323`）。

**伤害**（`applyPullAndDamage()`，`:258-285`）：

- 候选盒水平半径取 `max(pullRadius, damageRadius)`；竖直下探固定，**上探取 `max(AREA_UP, radius)`**（半径调大后固定上探会把「水平在范围内但高 5 格以上」的目标排除，`:269-274`）。
- **伤害节奏**：`DAMAGE_INTERVAL_TICKS = 4`，写法是「先自减再判定、命中后重置为完整间隔」（`:262-265`），实际命中于第 1、5、9… 刻 ⇒ 间隔恒为 **4 刻 = 每秒 5 次**。
- **为什么不是每 tick**：`bypasses_cooldown` tag 让每次命中都走全额伤害分支，同时**每次都会播受伤音效并广播伤害事件包**，且没有 tag 能压掉音效 ⇒ 每 tick 结算在 10 只生物时约 200 次/秒。改为分批 + 单次伤害等比例放大后 DPS 不变（`:56-62`、`:94-97`）。
- 吸引仍然是**每 tick**，只有伤害分批。

**目标过滤**（`canAffect()`，`:340-367`）：排除已死/旁观、排除创造模式玩家、排除施法者本人、排除同队（`isAlliedTo`）、排除该施法者的原版宠物（`OwnableEntity.getOwnerUUID`）、排除该施法者的 DS 召唤物。召唤物判定必须用 `getExistingDataOrNull`——`getData` 在附件缺失时会创建并挂上默认 `SummonData`，而它是 `serializable` 的，会给每个被扫到的生物写 NBT（`:363-365`）。

**同步与存档**：

- 玩法字段（伤害/半径/吸力）**不同步**，渲染器不得读取。
- 唯一同步的自定义数据是 `DATA_INITIAL_LIFE`（生成时的初始寿命，一生同步一次，跨区块重载时再同步一次）；客户端用本地 `tickCount` 倒推剩余寿命（`:391-403`）。
- `addAdditionalSaveData` / `readAdditionalSaveData` 存 `DamagePerHit` / `PullRadius` / `DamageRadius` / `PullStrength` / `Life` 五个键（`:370-389`）。

### 5.7 设计理由与历史

该技能从初版设计到当前实现共经历 **8 项返工**（含多轮试玩调参）。这些是最容易在后续改动中被重新踩回去的地方：

1. 伤害字段 `damage_per_tick` → **`damage_per_hit`**，并重标定为 `linear base 2.0 +1.0/级`（现上限 6 级 ⇒ L6 = 7.0，见 §5.5）。
2. 伤害频率由「每 tick」改为「**每 4 刻一次、单次 4 倍**」（用户裁决），DPS 逐级不变。
3. 「客户端平滑由原版 `partialTick` 插值提供」的初版判断**是错的**（位置包是硬吸附，且在 `setOldPosAndRot` 之前被处理）⇒ 改为客户端自行外推 + 服务端每 tick 发速度。
4. `exhaustion` `0.1` → **`0.02`**（按新频率表达「≈0.1/秒」的原意）。
5. `experience_cost.values[0]` `1.0` → **`0.0`**，否则生存模式 0 经验下授予的技能不可用（后来升级方式整体改为 `dragon_growth`，门槛随之变成成长值，见 §7.4）。
6. 初版附带的 6 张图标为占位图，最终只保留 **2 张**（0 级黑白、1–6 级全彩，见 §5.6 与 §12.1）。
7. 移动由「穿透方块」改为**撞方块镜面反弹**（用户试玩反馈），生物仍可穿透。`speed` 与半径经多轮试玩调整：`speed` 0.45→0.30→0.22→**0.15**、`pull_strength` 0.35→**0.45**、`pull_radius` 8→**12**、`damage_radius` 4→**6**。
8. 消散由「凭空消失」改为**最后 20 刻缓慢缩小**（试玩反馈），为此**新增唯一同步字段** `DATA_INITIAL_LIFE`。

当前数值的**唯一权威来源是 `data/beloong/dragonsurvival/dragon_ability/tornado.json`**（纯数据包字段，`/reload` 即可生效）。

### 6.1 数据定义

**`usage_blocked` 的读法**：`inverted(any_of(A, B))` ⇒ **当且仅当玩家位于龙宫或主世界时才允许使用**。该条件由 DS **服务端每 tick 求值**（`DragonAbilityInstance.java:98-110`，上下文取 ORIGIN = 玩家坐标、level = 玩家所在维度），一旦成立就**自动禁用整个技能**（不只是拒绝这一次施法）。这是把「只在两个维度间往返」这条规则**下推到数据包层**的做法，效果层另有一道兜底（`:84-87`）。

### 6.2 效果实现

`TpLoongPalaceEffect`（`ability/TpLoongPalaceEffect.java`，122 行）是**无参 record**，`MapCodec.unit`（`:43`）。

`apply`（`:46-106`）流程：

1. `target` 必须是 `ServerPlayer`，否则返回（`:47-49`）。
2. **冷却检查**：`TeleportCooldown.isOnCooldown(player)` —— 与天灾传送门、龙宫 Y<0 兜底**共用同一份 NBT 冷却**，时长为 **60 刻**。被拦下时给 actionbar 提示（`message.beloong.tp_loong_palace.on_cooldown`），否则玩家只会看到「技能按了没反应」。注意**技能自身的数据冷却（`cooldown: 5.0`，单位是刻 = 5 刻）比 NBT 冷却（60 刻）短得多**，所以实际节流完全由 NBT 冷却决定（`:51-57`）。
3. 按当前维度选方向（`:59-87`）：
   - 主世界 → 龙宫：`TeleportTarget.toLoongPalace(level)`，落点读配置 `[dimension_transport.overworldToLoongPalace]` 的 `targetX / targetZ / fallbackY`（默认 **0.5 / 0.5 / 65.0**）；龙宫是纯虚空维度，高度图必然取不到，实际落点**恒为 fallbackY**，代码不加偏移。目标维度取不到则 warn + 提示 `dimension_not_found`。
   - 龙宫 → 主世界：`new TeleportTarget.Spawn(overworld)`，即**世界出生点（含扩散）**；「优先玩家重生点」的旧行为已由用户裁定删除。
   - 其它维度：**直接返回不放行**（正常情况下数据包的 `usage_blocked` 已挡住，这里是兜底）。
4. 骑乘中先 `stopRiding()`（`:89-92`）。
5. `DimensionTeleport.toTarget(player, destination, postTeleport())` 生成原版 `DimensionTransition`；返回 `null` 表示「既拿不到高度图、又没有兜底 Y」，此时 warn 并放弃（`:94-101`）。
6. `player.changeDimension(transition)`（`:103`）。
7. **传送后收尾**（`:109-116`）：`fallDistance = 0` + `TeleportCooldown.mark(player)` 记一次共用冷却。

### 6.3 与传送系统的接口

本类**只负责**「按当前维度选方向、做冷却检查、给出玩家提示」，落点解析与实际传送全部交给 `com.zonlong.beloong.teleport` 包（与天灾传送门同一套 API）：

| 职责 | 承担者 |
|---|---|
| 目标定义（去龙宫 / 回出生点） | `TeleportTarget.toLoongPalace` / `TeleportTarget.Spawn` |
| 维度常量收口 | `TeleportTarget.LOONG_PALACE_LEVEL`（原先多处各写一份） |
| 落点解析（高度图 / 兜底 Y） | `CoordinateLanding` / `LandingY` |
| 跨维度执行 | `DimensionTeleport.toTarget` + 原版 `changeDimension` |
| 共用冷却 | `TeleportCooldown` |

**⚠️ 类 javadoc 里记着一处已知缺陷（`:33-35`，勿当成设计）**：龙宫侧落点 `(targetX, ?, targetZ)` 处没有方块 ⇒ 总是走 `fallbackY`，玩家落在空中。龙宫实际可站立面（水体区域）在 `x[-54,8] y[68,77] z[-312,-272]`，与默认 `z = 0.5` 完全不相交。

### 7.1 伤害类型与标签

| 文件 | 内容 |
|---|---|
| `data/beloong/damage_type/air_strike.json` | `message_id beloong.air_strike`、`exhaustion 0.1`、`scaling when_caused_by_living_non_player`、`effects hurt`、`death_message_type default` |

**两个原版标签为什么必须放在 `minecraft:` 命名空间**：原版直接判 `minecraft:` 的这两个标签（`LivingEntity.java:1190` 判 `BYPASSES_COOLDOWN`、`:1241` 判 `NO_KNOCKBACK`），模组自建标签无法间接塞进原版判定，只能向 `minecraft:` 的标签**追加**。

**追加语义**：这两个文件省略了 `"replace"` ⇒ 缺省为 `false`（`TagFile.java:12`），而 `TagLoader` 遍历的是**资源栈**、只在 `replace == true` 时 `clear()`（`TagLoader.java:49-55`）⇒ 结果是**原版内容与本模组条目的并集**，不会清空原版。仓库同类文件习惯显式写出 `"replace": false`。

**死亡消息只用基键**：两个伤害类型的 `.player` 变体从未被使用，已删除（语言键 210 → 208）。原因：`.player` 只在直接实体与归因实体**都为 null** 时才启用（`DamageSource.java:80-85`），而两个技能构造伤害源时都带了实体，该条件恒不成立。

### 7.2 语言键规则

| 键类别 | 生成方式 | 谁负责 |
|---|---|---|
| `dragon_ability.beloong.<id>` | **DS 由能力 ID 自动推导**（§3.4） | DS |
| `dragon_ability.beloong.<id>.desc` | 同上 + `.desc` | DS |
| `dragon_ability.beloong.<id>.dynamic_desc` | **本模组自建的约定**，键名硬编码在各自 `getDescription` 里 | 本模组 |
| `death.attack.beloong.<id>` | 由伤害类型的 `message_id` 推导 | 原版 |
| `entity.beloong.tornado`、`message.beloong.*` | 本模组自建 | 本模组 |

**两条必须知道的约束**：

1. **`dynamic_desc` 的数值参数颜色无法由语言文件控制**。`Component.translatable` 会把每个 `%s` 参数作为**独立子组件**渲染（非组件参数被包成 `Component.literal(字符串)`，样式为空），而 `§` 颜色码由 `StringDecomposer` **逐叶子文本**解析、**不跨组件边界传递** ⇒ 写在 `%s` **之前**的 `§a` 后面没有文本可作用，参数只能继承上层样式（DS 工具提示的灰）。**当前三个技能统一接受这个灰色**，不在代码里硬编码颜色，以保证观感一致（`TornadoEffect.java:100-110` 的 javadoc 记录了这个决定）。
2. **未学习（等级 0）时计算描述数值必须钳制等级下限为 1**。`LevelBasedValue.Lookup.calculate` 是 `values.get(level - 1)`（`LevelBasedValue.java:166-167`），传 0 会索引 `-1` 崩溃。我们的 `getDescription` 自己钳制（`AirStrikeEffect.java:149`、`TornadoEffect.java:102`）；DS 自己的部分效果靠本模组的 `DamageEffectMixin` / `ModifierMixin` 修（见 §7.6）。

### 7.3 图标规范

- 位置：`assets/beloong/textures/gui/sprites/abilities/<name>_<n>.png`，**32×32 RGBA**。
- 引用形式：JSON 写 `"texture_resource": "beloong:abilities/<name>_<n>"`（不含 `textures/gui/sprites` 前缀与 `.png` 后缀——DS 在解析时补）。
- 解析链路：`LevelBasedResource.get(level)` 按 `from_level` **降序**取第一个 `fromLevel <= level` 的项，无匹配则回退首项（`LevelBasedResource.java:17-33`）。因此 `from_level` 只需覆盖实际等级区间；`tornado` 用 7 条 `from_level` 指向 2 个文件是合法且刻意的（0 级黑白、1 级以上全彩）。
- 图集：走原版 GUI 精灵图集，**目录源跨所有命名空间**，无需额外 atlas JSON（§3.4）。

### 7.4 等级与升级机制

**三个技能刻意采用三种不同的获取/升级模型**，这是本设计里最容易踩坑的地方：

| | `air_strike` | `tornado` | `tp_loong_palace` |
|---|---|---|---|
| 有 `upgrade` 段 | 有 | 有 | **无** |
| 授予时的等级 | 0（`MIN_LEVEL`） | 0 | **满级 1** |
| 何时可用 | 升到 ≥1 后 | 升到 ≥1 后 | **立即** |
| 首个门槛 | 经验 1 | **成长值 20** | — |
| 上限 | 5 | 6 | 1 |

机制依据：`MagicData.java:503-508` —— **无 `upgrade` 段时按 `getMaxLevel()` 建实例**（⇒ 立即可用），**有 `upgrade` 段时按 `MIN_LEVEL = 0` 建实例**再尝试升级。而可用性要求 `level > 0`（`DragonAbilityInstance.isUsable()`）。

- `air_strike` 的 `experience_cost.values[0] = 1.0` ⇒ **不会**自动升到 1 级，玩家须支付 1 点经验。
- `tornado` 的 `growth_requirement.values[0] = 20.0` ⇒ 龙的成长值到 **20** 之前不可用。这与 `air_strike` 的差异是 **tornado 有意为之**：其 spec 勘误第 5 条记录了「`values[0]` 必须为 `0.0` 否则授予后不可用」的教训；改用 `dragon_growth` 后门槛变成了成长值，语义随之变化。

`LevelBasedValue` 的算式（`LevelBasedValue.java`）：`Linear` = `base + per_level_above_first × (level − 1)`（`:146-147`）；`Lookup` = 命中则 `values[level − 1]`，否则 `fallback.calculate(level)`（`:166-167`）。

### 7.5 `targeting_mode` 的真实语义

三个 JSON 都写了 `targeting_mode`，但**在 `target_type: dragonsurvival:self` 下它是声明性字段，不参与运行期过滤**：

- `isEntityRelevant`（即 `targeting_mode` 的判定函数）**只被** `AreaTarget:41`、`DiscTarget:61`、`DragonBreathTarget:48`、`LookingAtTarget:48` 调用。
- `SelfTarget.apply` **只检查** `entityTarget.matches(...)`（该方法仅判 `target_conditions`，见 `AbilityTargeting.java:92-94`），**完全不看 `targeting_mode`**（`SelfTarget.java:27-29`）。
- 该字段在 codec 里是**必需**的（`AbilityTargeting.java:88` 用 `fieldOf` 而非 `optionalFieldOf`），所以不能省略。

因此：

- `air_strike` = `all_except_self`：声明「打到所有人、只排除自己」，与效果内部 AoE 的行为一致（`AirStrikeEffect.java:115` 排除自己）。
- `tornado` = `all`：`TargetingMode.ALL` 恒为 true，等于不做声明性过滤；**真正的过滤在 `TornadoEntity.canAffect` 里**。
- `tp_loong_palace` = `allies_and_self`：同上，仅为声明。

**⇒ 真正的目标过滤都必须写在效果 Java 里**，改 `targeting_mode` 不会改变行为。这也是 `air_strike` 那条历史裁定（`memory/decisions-log.md:1225`）的实际含义：它对齐的是**声明与实现**，不是运行期行为。

## 八、关键设计约束（实现期已验证的底层事实）

这些事实是三个技能（尤其龙卷风）设计时逐条从源码读出来并落成实现的依据，也是改动时最容易踩空的地方。**来源**：原版/NeoForge 反编译源 `build/review-src/neoforge-21.1.236/`；DS 官方源码参考树 `D:\Minecraft\开源模组参考文件\DragonSurvival`（早期文档记的 `…\dabrdragonsurvivalcompat\前置源代码\…` 路径在本机不存在，已作废）。

| 事实 | 证据 |

| `bypasses_cooldown` 让每次命中都走全额伤害分支 | `LivingEntity.hurt`：`if (invulnerableTime > 10.0F && !source.is(BYPASSES_COOLDOWN))` 走差额分支，否则调 `actuallyHurt` |

## 九、边界行为与明确不做

### 9.1 龙卷风的边界行为

| 情况 | 处理 |
|---|---|
| 飞进未加载区块 | 实体随区块卸载；`readAdditionalSaveData` 恢复数值，`life` 继续走 |
| 施法者死亡 / 登出 | `getOwner()` 返回 null → `canAffect` 与 `DamageSource` 均判空；`new DamageSource(type, this, null)` 合法 |
| 目标在吸引过程中死亡 | `isAlive()` 已过滤，下一 tick 自然移除 |
| 掉进虚空 | `getY() < getMinBuildHeight() − 8` → discard |
| 连续放两个 | 两个独立实体各自结算，伤害叠加（可接受） |
| 末影人瞬移 | 每 tick 重算，会被反复拉回（预期行为） |
| 拉起的实体落地摔伤 | 不特殊处理，属预期副作用 |
| `/summon beloong:tornado`（不给 NBT） | 数值全为 0 → 寿命 0，下一 tick 消散（预期） |

> 注：`/summon` 调试时的 NBT 键是 `DamagePerHit / PullRadius / DamageRadius / PullStrength / Life`（**不是**早期文档里的 `DamagePerTick`，写错会静默得到 0 伤害）。

### 9.2 明确不做（Out of scope）

- **不修改任何 `dragon_species` 或 species ability tag**——技能分配交给整合包数据包（§3.5）。
- **不做自定义网络包**——客户端渲染所需的剩余寿命原版已同步（§5.3）。
- **不做龙卷风对方块的破坏、音效循环、粒子拖尾**。
- **`air_strike` 的敌我不分是有意设计**（打到范围内所有人、只排除自己），不做友军豁免。
- **龙卷风的吸引/伤害 AoE 不做视线检测**——龙卷风本体撞墙会反弹，但墙后的目标照样会被吸（刻意保留）。
- **`tp_loong_palace` 不判玩家是否为龙**——授权口径由整合包决定；效果层只兜底拒绝第三维度。

## 十、验收要点

三技能共用的门禁：

1. `.\gradlew.bat build` 通过。
2. **数据包解析门禁**：跑一次客户端后检查 `run\logs\latest.log` 里 `Failed to parse` 与 `Registry loading errors` **零命中**。
   （早期文档写的是 `run\client\logs\latest.log`，该路径**不存在**——运行目录就是 `run/`，`build.gradle` 未设 `gameDirectory`。）
3. **引用一致性**：三份 `dragon_ability` JSON 的 `effect_type` 与注册键逐字一致；`icon.texture_resource` 指向的文件都存在；能力 ID 与 `data/beloong/dragonsurvival/dragon_ability/<id>.json` 的目录/文件名一致。
4. **语言键**：中英键集合完全一致；`dynamic_desc` 的 `%s` 数量与顺序与各自 `getDescription` 的传参一致。

分技能的实测要点：

| 技能 | 要点 |
|---|---|
| `air_strike` | 滑翔中撞到生物造成伤害；速度低于 `min_speed` 不触发；命中后收翅；actionbar 每 5 刻显示速度/伤害读数；队友/自己的宠物是否命中（当前设计为**会**命中） |
| `tornado` | 向准星飞出、青色、四层差速自转、约 2.8 格宽 × 3.28 格高、悬空；持续把敌人拉向中心；每 4 刻结算一次（血条不是每 0.5 秒一跳）；无击退；友军/宠物/DS 召唤物免疫；创造模式玩家免疫；**撞墙镜面反弹**；寿命最后 20 刻缓慢缩小 |
| `tp_loong_palace` | 主世界↔龙宫双向传送；第三维度技能被 `usage_blocked` 禁用；共用传送冷却生效并给出提示；传送后不摔伤 |

## 十二、已知缺口与后续

### 12.1 功能缺口

1. **龙卷风技能图标只有 2 张**（0 级黑白、1–6 级全彩）。这是用户明确的选择，但与 `air_strike`（逐级一张）不一致；`tornado.json` 的 7 条 `from_level` 指向 2 个文件。
2. **龙宫落点在虚空**（§6.3）——`tp_loong_palace` 会把玩家送到空中，属已知缺陷，待龙宫传送门那一轮解决。
3. **`tools/make_tornado_icons.py` 的覆盖风险**：其产物已从交付删除，但脚本仍在仓库、计划仍引导把它直接写进正式贴图目录，且脚本无备份无存在性检查 ⇒ 重跑会静默覆盖用户的正式美术。详见审查清单第 4 条。
4. **历史设计文档已合并进本文档并删除**（原 3 份 spec + 3 份 plan）。§4.5 / §5.7 / §6.5 保留了它们与当前代码的差异；设计依据并入 §八，边界与取舍并入 §九，验收清单并入 §十。
5. **`tp_loong_palace` 的两条未决问题**（在龙卷风那轮审查里被定为中等）：
   - `cooldown: 5.0` 的单位是 **tick** 而非秒；它与共用 NBT 冷却（60 刻）方向不一致，实际节流完全由后者决定。
   - 改用 `changeDimension` 后**丢失 `POST_TELEPORT` 落点票据**，两个龙宫调用方都没有补 `requestChunk`；而 `DimensionTransportHandler.java:95` 的注释仍写着旧结论。
