## 一、板块范围与边界

### 1.1 属于本板块

| 路径 / 内容 | 说明 |

### 1.2 **不属于**本板块（越界前先问）

- **方块本体**（`registry/ModBlocks`、`block/`）——另一个板块。本板块只提供它们的 **`BlockItem` 包装**（见 §2.3）。
- **mixin**（`mixin/`）、**跨模组兼容层**（`compat/`）、**配置节本体**（`Config`）——各自板块。
- **整合包侧文件**：`D:\BeLoong\.minecraft\versions\BeLoong`、`BeLoong-Server`、`【化龍】服务端` —— **只读，一律不改**（`AGENTS.md` §六）。
- **DS 爪牙（claw sword）系列**：`compat/dragonsurvival/ClawSword*` 是**龙之生存自己的物品**的进度触发器，本模组不新增物品 ⇒ **不属于本板块**（但与本板块有接口，见 §6.6）。

### 1.3 与相邻板块的接缝（改动要两边一起看）

| 接缝 | 谁改 | 风险 |
|---|---|---|
| 方块 ↔ 它的 `BlockItem` | 方块在 `registry/ModBlocks`，**BlockItem 在本板块**（`item/ModItems`） | **同一个方块要改两个文件**；只改一边 = 物品栏里没有它，或注册到不存在的方块 |
| 物品 ↔ 语言文件 | 本板块 | 键缺失只在运行期以原始键形式暴露，构建期不报 |
| 物品 ↔ Curios | 本板块（物品）+ 数据（`data/curios`） | **必选前置**（rev 2 起）；此前的 optional 声明与类加载事实冲突，见 §9.1 |
| 物品 ↔ FDBosses/FDLib | `DawnLightEffect` | 两者在 `mods.toml` 是 `required`，可无条件调用 |
| 物品 ↔ 天灾传送门 | 眼球物品清单在 `Config.DisasterPortal.eyeItems`（**别的板块的配置节**） | 本板块只提供"嵌眼球"的载体（框架方块），清单属配置板块 |

## 二、注册架构

### 2.1 唯一的注册中心

```
BeLoongCore 构造函数 (src/main/java/com/zonlong/beloong/BeLoongCore.java:111)
    └─ ModItems.register(modEventBus)
           └─ DeferredRegister.Items Items = DeferredRegister.createItems(MODID)   // ModItems.java:42
```

- 物品**全部**经 `ModItems.Items.register(...)` 注册，**没有第二处**（全仓 `Items.register(` 只出现在 `ModItems.java`）。
- `DeferredRegister.Items` 是**懒加载**注册：`register(String, Supplier<? extends Item>)` 与
  `register(String, Function<Item.Properties, ? extends Item>)` 两个重载都存在。
  ⇒ 传**实例**编译不过，必须传 `Supplier`（元素魔源的设计文档 §3 / D29 记的就是这个编译错误）。
- 物品 ID 的命名空间恒为 `beloong`。

### 2.2 创造模式页签

`item/ModCreativeModeTabs.java` 注册单个页签 `beloong:beloong_tab`：

- 图标 = `ModItems.BELOONG_LOGO`；标题键 = `itemGroup.beloong_tab`（zh「化龙」/ en「BeLoong」）。
- `displayItems` 里 **19 件逐件 `accept`**，顺序 = 声明顺序的**人工重排**：
  图标 → 放大护符 → 黎明曙光 → 永恒猪排 → **十个魔源（金木水火土 → 风雷冰 → 光暗）** → 天灾框架 → 天灾门方块 → 龙宫门 → 地狱之门 → 红黄板子。
- ⚠️ **元素魔源的顺序有三处真相源，必须同步**：`ModItems` 的声明、本类的 `accept` 调用、
  `tools/verify_essence_lang.py` 的 `ELEMENT_IDS`（设计文档 D20）。
- 新增物品**不要只加注册不加 `accept`** —— 那件物品会从创造页签里消失（`/give` 仍能拿到）。

### 2.3 `BlockItem` 的归属分割（本项目特有，容易踩）

**方块在 `registry/ModBlocks`，它的 `BlockItem` 在 `item/ModItems`，不在 `ModBlocks` 里注册。**
`ModBlocks` 只有 `DeferredRegister.Blocks` 与 `BlockEntityType`，没有 `Items`（`ModBlocks.java:56-61`）。

⇒ 判断"这个方块有没有物品形态"要去 `ModItems` 找，不要在 `ModBlocks` 里找。

## 四、逐件行为规格

### 4.1 `beloong_logo`（无行为）

`new Item(new Item.Properties())`，默认 `COMMON`、堆叠 64。存在意义是**图标资源**：
创造页签图标（`ModCreativeModeTabs.java:35`）与 NPC 进度根节点的图标（`data/beloong/advancement/npc/root.json:44`）。
⇒ **不要删**，删了页签与进度会失去图标。

### 4.2 `eternal_porkchop`（`item/effect/EternalPorkchopEffect.java`）

| 项 | 值 | 位置 |
|---|---|---|
| 食物数值 | `nutrition(8)` / `saturationModifier(0.8f)`（= 熟猪排） | `:24-27` |
| 进食时长 | **32 tick** | `:29`、`:46-48` |
| 冷却 | **600 tick**（30 s） | `:30`、`:86` |
| 动画 / 音效 | `UseAnim.EAT` / `SoundEvents.GENERIC_EAT` | `:41-43`、`:51-53` |
| **不消耗** | 覆写 `finishUsingItem` 并 `return stack`（原版食物会 `shrink`） | `:62`、`:88` |

流程：`use` 走原版 `Item.use` 的食物分支 → `startUsingItem` → 32 tick 后 `finishUsingItem`：
① 若在冷却中**直接 `return stack`**（不进食、不发音、不计数）；② 否则 `FoodData.eat(...)` + 吞咽音 + `awardStat`
+ `CriteriaTriggers.CONSUME_ITEM` + 上冷却。

⚠️ **已知观感（§9.3）**：冷却判定只在 `finishUsingItem` 里，而原版 `Item.use`（`Item.java:165-176`）**不查冷却**
⇒ 冷却期间玩家仍能啃满 32 tick 然后**什么也没发生**（无任何提示）。热键栏有冷却转圈，故影响有限。

### 4.3 `amplification_charm`（`item/effect/AmplificationCharmEffect.java`）

`implements ICurioItem`（Curios）。装饰器 ID 固定 `beloong:amplification_charm`：

```java
mods.put(Attributes.SCALE, new AttributeModifier(MODIFIER_ID, 1.0, Operation.ADD_MULTIPLIED_TOTAL));
```

⇒ **体型放大至 200%**（`ADD_MULTIPLIED_TOTAL` 的 1.0 = 在基值上再乘 1.0）。`canEquipFromUse = true` ⇒ 右键即可装备。

⚠️ 该类**直接实现 Curios 的接口**。**rev 2 起 `mods.toml` 已把 `curios` 声明为 `required`**
（此前的 `optional` 与类加载事实冲突）⇒ 见 **§9.1**。

### 4.4 `dawn_light`（`item/effect/DawnLightEffect.java`）

| 常量 | 值 | 位置 |
|---|---|---|
| 扫描半径 | 32 格（`AABB(player.blockPosition()).inflate(32)`） | `:31` |
| 冷却 | 1200 tick（60 s） | `:32` |
| 耐久消耗 | 每次使用 **1 点**（总耐久 10 ⇒ 共 10 次） | `:41`、`:73` |
| 白屏特效 | `FDLibCalls.sendScreenEffect(..., SCREEN_COLOR, 白, 5, 0, 5)` | `:91-98` |

对三种 Boss 各削 **1 层**，三种机制**互不相同**（`MalkuthEntityAccessor` 是 mixin，属别的板块）：

| Boss | 削法 | 位置 |
|---|---|---|
| `ChesedEntity` | `decreaseHitCount(1)`（复用第三方自己的量） | `:78` |
| `MalkuthEntity` | 读 `getCurrentHits()` − 1 → 经 `MalkuthEntityAccessor#setHits` 写回；**减到 0 时手动 `kill()`** | `:80-84` |
| `GeburahEntity` | `setSinnedTimes(getSinnedTimes() + 1)` | `:86` |

- **无 Boss 时**：只给一条 `item.beloong.dawn_light.no_boss` 的 actionbar 提示，**不耗耐久、不上冷却**（`:63-68`）。
- **客户端**：`use` 在 `level.isClientSide` 直接 `return success`（`:48-50`）⇒ 判定完全由服务端做。
- 贴图是**全板块唯一带动画的物品**：`dawn_light.png` 16×144（9 帧 16×16）+ `dawn_light.png.mcmeta`（`frametime 8`、`interpolate true`）。
  ⚠️ **静态贴图不得有 `.mcmeta`**（会被当帧条解析并误算帧尺寸）——十个魔源贴图因此都没有 `.mcmeta`。

### 4.5 元素魔源 ×10（`ModItems.java:67-120`）

**十件共用一个匿名 `Item` 子类**：私有工厂 `essenceSupplier(String tooltipKey)` 返回
`Supplier<Item>`，唯一差异是 tooltip 翻译键（`:112-120`）。jar 里只有 `ModItems$1.class` 一份字节码。

- 属性：`new Item.Properties().rarity(Rarity.UNCOMMON)`，`stacksTo` **保持默认 64**。
- tooltip：**每件一条完整句子**（`item.beloong.<元素>_essence.tooltip`），
  **没有 `%s`、没有共享模板、没有元素代入词**（设计文档 D26）。
  ⚠️ 用 `%s` + 代入词会踩"中文模板里 `%s` 位置与参数顺序错配"（渲染出「自然界的**金魔源**元素凝聚成的魔源」），
  这个失败模式**只在用真实语言文件重演展开时暴露**。
- **顺序**（金木水火土 → 风雷冰 → 光暗）三处必须同步，见 §2.2。
- **不做**：不给任何效果、不加配方、不做数据驱动、不加配置项（设计文档 §8 Non-Goals）——**这是刻意的**，不是待办。

### 4.7 `hell_gate` 的动态 tooltip（本板块唯一"读数据包"的物品）

`item/HellGateBlockItem.java`：在 tooltip 里**逐行列出当前能开这扇门的钥匙的物品名**。

- 数据源 = 物品 tag `#beloong:hell_gate_keys`（`ModItemTags.HELL_GATE_KEYS`），默认只含 `irons_spellbooks:bone_key`。
- **为什么列名字而不是列 tag 名**：玩家要的是「拿什么去开门」；tag 名是给整合包作者看的。
- 用 `ItemStack#getHoverName()` ⇒ **钥匙自带的自定义译名会跟着显示**。
- **空 tag 的失败面**：tag 被清空/删掉时输出 `item.beloong.hell_gate.no_key`（据实说明"没有钥匙能开"），
  与加载期告警 `HellGateKeyWatcher`（`block/HellGateKeyWatcher.java`，在 `BeLoongCore.java:137` 注册）构成可排查组合。
- ⚠️ `TooltipContext#registries()` **可为空**（如 `TooltipContext.EMPTY`）⇒ 代码先判空再查（`:43-46`）。
- **推断方向**：整合包要**追加**钥匙，文件必须写在 **`beloong` 命名空间**下（tag 文件的命名空间 = tag ID 的命名空间），
  用 `"replace": false` 合并（`ModItemTags` 的 javadoc 有完整说明）。

### 5.3 语言键（`assets/beloong/lang/{zh_cn,en_us}.json`，各 331 键）

**键命名规则（本板块）：**

| 物品类型 | 名字键 | tooltip 键 |
|---|---|---|
| 普通 `Item` | `item.beloong.<id>` | `item.beloong.<id>.tooltip` |
| **`BlockItem`** | **不写 `item.*`** —— 用 `block.beloong.<id>` | 视需要（`hell_gate` 用 `item.beloong.hell_gate.key` / `.no_key`） |
| 创造页签 | `itemGroup.beloong_tab` | — |

⚠️ **`BlockItem` 不写 `item.*` 键是正确做法，不是漏写**：`BlockItem#getDescriptionId()`（`BlockItem.java:189-190`）
返回 `this.getBlock().getDescriptionId()`，即 `block.beloong.<id>`。
（现场核对：五个 BlockItem 的 `item.beloong.*` 键**都不存在**，只有 `block.beloong.*`。）

**硬约束**：中英键集必须一致；`%s` 个数与代码传参个数一致；`§x` 颜色码两端一致；字面 `%` 写成 `%%`。

## 七、新增 / 修改一件物品的清单

**按顺序做完，缺一项就是一个只在运行期暴露的缺陷：**

1. **注册**：`item/ModItems.java` 加一个 `DeferredItem<...>`（有行为的类放 `item/effect/`，否则就地匿名/裸 `Item`）。
2. **页签**：`item/ModCreativeModeTabs.java` 的 `displayItems` 里加 `accept`，并放到**用户要的位置**。
3. **模型**：`assets/beloong/models/item/<id>.json`（默认 `minecraft:item/generated` + `layer0`）。
4. **贴图**：`assets/beloong/textures/item/<id>.png`。**静态图不得带 `.mcmeta`**；动画图必须带。
5. **语言**：`item.beloong.<id>`（`BlockItem` 除外，走 `block.beloong.<id>`）+ tooltip，**中英同步**。
6. **属性约定**：默认不写 `stacksTo`（= 64）；珍贵品用 `stacksTo(1)`；主题品加 `fireResistant`；
   稀有度按 §三 既有取值，**不要为了"金色"去改 `Rarity` 枚举**（1.21.1 原版四个稀有度没有金色，见元素魔源设计文档 §2.2）。
7. **可选模组 API**：**必须**先确认该模组在 `mods.toml` 是 `required`；若是 `optional`，
   **绝不能**让恒被加载的类（`ModItems`）直接引用它的 API —— 见 §9.1。
8. **客户端专属类**：**不得被公共类引用**（专用服务端会在常量池里撞见 ⇒ `NoClassDefFoundError`，`try/catch` 抓不到，`AGENTS.md` §七）。
9. **配置项**：**默认不加**。要加先拿用户点头，并连带补 `beloong.configuration.*` 的中英翻译键。
10. **临时探针**：为验证临时加的东西一律用 `*_test` 命名，收尾**删除并验证 jar 内无残留**（它们会随 jar 发布）。

### 严重 / 重要

#### 9.1 ✅ 已修复：`amplification_charm` 与「curios 声明为 optional」直接冲突（rev 2 按方案 A 修复）

> **本条不是本轮首次发现**：`docs/reviews/2026-09-18-post-0.9.3-bug-list.md:115-120`（编号 **13**）
> 与 `docs/reviews/2026-09-18-post-0.9.3-code-review.md:1220-1224`（**L7-S3-2**）早已登记过同一问题，
> 当时的裁定是「**当前不可触发** ⇒ 属『**借来的安全**』，**不升 S1**」——因为
> `lendercataclysm-551586-8095590.jar!/META-INF/neoforge.mods.toml:91` 把 curios 声明为 **required**，
> FML 强制校验，所以整合包里 Curios 必然在场。
> **本轮的增量**是：独立复现了机制（最小 JVM 实验）、并把「借来的安全」换成**自己声明的安全**。
> 上一轮给的修法就是「补 `isLoaded("curios")` 守卫，**或把 curios 声明补正**」——用户 2026-10-15 选了后者。

**事实链**（修复前的状态）：

1. `mods.toml`：`modId="curios"` + **`type="optional"`**；`build.gradle` 当时也是 `compileOnly` + `localRuntime` + 注释「Curios — 可选依赖」。
2. `item/effect/AmplificationCharmEffect.java:20`：`extends Item implements ICurioItem`（**Curios 的接口**）。
3. `item/ModItems.java:54-55`：`Items.register("amplification_charm", AmplificationCharmEffect::new)`
   —— 这个**构造器方法引用写在 `ModItems` 的静态初始化器里**，而 `ModItems` 在 `BeLoongCore.java:111` **恒被加载**。

**机制（实测，不是推断）**：用一个最小 JDK 21 实验复现了同形结构（接口 `I`、实现类 `A implements I`、
持有 `Supplier<A> ITEM = A::new` 的 `B`、只触碰 `B`）：

```
基线（I.class 存在）: B.ITEM = B$$Lambda/0x000001f1...@77459877        exit 0
删掉 I.class 后      : Exception in thread "main" java.lang.NoClassDefFoundError: I
                          at B.<clinit>(B.java:5)
                       Caused by: java.lang.ClassNotFoundException: I   exit 1
```

⇒ **只要 `ModItems` 被加载（必然），构造器方法引用的 indy 链接就会加载 `AmplificationCharmEffect`，
进而要求解析 `ICurioItem`。Curios 缺席时在 `<clinit>` 抛 `NoClassDefFoundError` ⇒ 模组构造失败 ⇒ 启动期硬崩。**
（注意：**没有任何路径需要真的实例化该物品**就已经崩了。）

**当时的爆炸半径**：正式整合包装了 Curios，dev 侧靠 `localRuntime` 也在 classpath 上
⇒ **实机不会崩**。但 **manifest 声称 optional 与事实不符**：任何"没装 Curios"的整合包都会起不来，
而这正是 `optional` 声明存在的意义。

**修法（三选一）——已采纳 A**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（✅ 已采纳，rev 2）** | `mods.toml` 把 `curios` 改 `required`，`build.gradle` 的 `compileOnly` 升 `implementation` | 一句话；代价是"没 Curios 就装不了"，但这本来就是事实 |
| B | 保持 optional：把护符拆成「无 Curios 时的降级 `Item`」+「有 Curios 时注册 `ICurioItem` 能力」，用 `ModList.get().isLoaded("curios")` 守卫类加载 | 结构变复杂，且**物品 ID 与属性要在两条路径下保持一致** |
| C | 保持 optional 且不给降级：用 `RegisterClientExtensionsEvent` 类似思路把 Curios 交互挪到守卫后的注册处 | Curios 的物品能力没有等价的"延迟绑定"入口，实操上等同 B |

⚠️ 与 `AGENTS.md` §四「三段（Gradle 依赖 / toml 声明 / mixin 注解）缺一，兼容都不完整」
是**同一类错误**，只是这里缺的是「代码对反向依赖的守卫」。
⚠️ **本条仍未做运行时验证**（没有真的把 Curios 从运行环境摘掉跑 `runClient`）——
已证实的是 JVM 机制与代码结构，不是"这个整合包会崩"。
✅ **修复后已重新通过构建**（`--rerun-tasks`，exit 0），且 `curios` 现在由本模组自己声明为 required
⇒ 即使 Cataclysm 将来撤掉它那条 required，本模块也不会因此变得不可加载。

### 可选

#### 9.2 `dawn_light` 在客户端无条件返回 `success`

`DawnLightEffect.java:48-50`：客户端 `return InteractionResultHolder.success(stack)`，
而服务端在"未检测到 Boss"时返回 `fail`（`:67`）。
⇒ 客户端会**先**播放一次挥手/使用动作，服务端随后回绝。

`EternalPorkchopEffect.java:67-69` 把冷却判定放在 `finishUsingItem`，

**修法（若在意）**：覆写 `use`，冷却中直接 `return InteractionResultHolder.fail(stack)`。
**代价**：无。**收益**：省掉一次"白啃 32 tick"。
