## 2. 设计

### 2.1 缺陷 1：龙门的来源必须与 DS 同源

**决策 D1** — 门的判定用 `DragonStateProvider.isDragon(player)`（等价于 `getOptional(player).map(h -> h.isDragon()).orElse(false)`），
即与 `ClientFlightHandler.java:343` 的 `if (handler.isDragon())` **同一语义**。

- **作用位置：两处都要。** HEAD（`:278`）目前是 `beloong$setZeroGravity(player, isGliding(player))` ⇒ 改为
  **"是龙 **且** `isGliding`"** 才挂零重力；TAIL 的滑翔分流（`:309`）同样先要求是龙。
  理由：零重力本身就是"飞行权"的一部分，只门控 TAIL 会留下"人类不掉落"这一半症状。
- **禁止的替代判据**：不能用"有 `FlightData`"、"有飞行能力 `hasFlight`"、"翅膀展开"来代替——这三者对人类同样为真（诊断 §1 证据 ②③④）。
- **不改变非滑翔分支的语义**：`beloong$isEligible`（`:392`）本来就有 `isDragon` 检查，悬停/非稳定模拟对人类的空操作行为保持不变。
- **已知副作用（可接受）**：人类恢复原版重力与坠落伤害；DS 自身那两条**没有**龙分流的处理器
  （`handleEarlyFlightLogic:173-190`、`handleWallCollisionsWhenFlying:192-214`）仍会把人类当滑翔者记账
  —— 那是 DS 既有行为，不在本次范围。

### 2.2 缺陷 2：撤掉"大常数"，改为补回重力原本间接提供的那部分

**核心认识**：DS 原版的滑翔速度谱**依赖重力**。平视时 DS 会缓沉（终端约 0.79 格/tick），而那个下坠经
`:410-413` 的 `downwardMomentum` 换成前向速度（平视约 `0.079`/tick）；低头时 `:408` 与 `:410-413` 共同给出
1.6 格/tick 量级的俯冲。**本模组把重力归零，等于同时切断了 DS 的整条"下坠 → 速度"链路**——这才是
rev 1 之后不得不由我们补能量的根本原因，也说明"贴合原版速度"**不能靠调常数**，而要**把重力原本的那部分补回来**。

**决策 D2** — 用"**重力等效下压**"替代"沿视线的加速"：

```
当 look.y <= 0（平视或低头）时：
    竖直补入  A(θ) = g_base · (2 − 0.75·vd)        // vd = cos²θ（DS 的 verticalDelta）
当 look.y > 0（抬头）时：
    完全不介入（DS 自己的 ay / 3.2·delta 负责）
```

- `A(θ)` 的来源：重力时代的下压是**两条之和** —— DS `:408` 的 `g·(−1 + 0.75·vd)` 与原版
  `LivingEntity.travel:2331` 的 `−g`。两者相加即上式（平视 0.110、45° 0.143、竖直 0.176，`g=0.088`）。
- **不做正反馈、不设上限、不乘 `FS`**：这几个量本身就是 DS/原版自己的数，再加系数就是双重计入。
- **必须使用"未被我们归零"的重力值** ⚠️ 这是本设计最容易错的一点：`Attributes.GRAVITY` 在 HEAD 已被乘 0，
  TAIL 读它只会得到 0。取法：**HEAD 在挂修饰符之前读一次 `gravity.getValue()` 并缓存**（每 tick 覆盖），
  TAIL 用缓存值。这样它天然包含 DS 体型对重力的 `+10%/+20%` 修正，无需我们自己复刻体型表。

**决策 D3** — 平视**保持不缓沉**（延续 rev 1 的需求），代价由"前向等效"承担：

| 方案 | 平视行为 | 与目标 A 的关系 | 取舍 |
|---|---|---|---|
| **(a) 推荐** | 不缓沉；改为给一个与重力时代 `dM` 等效的前向推力（平视约 `0.079/tick`） | 平视**速度**谱与 DS 一致（终端 ≈0.79 格/tick），但不缓沉 | 保住 rev 1 的"不受重力影响"；与 `dM` 数值对齐，不是新发明的量 |
| (b) 被否 | 平视也补下压 ⇒ 缓沉 0.79 格/tick | 字面上完全复刻 DS | **与 rev 1 需求"滑翔不受重力影响"直接冲突**，用户当时明确要求不因重力下坠 |

⇒ 采用 (a)。注意 (a) 的 `0.079` 不是随手取的：它等于重力时代平视稳态下坠 `0.79` 经
`:410-413` 换算出的前向推力（`0.1 · vd · FS · |y|`，平视 `vd=1`）。

**决策 D4** — 补入必须有**爬升**（这是"没有缓缓加速"的直接修复）：

- 竖直补入天然有爬升：它是对速度的持续注入，速度从当前值积分上去，时间常数与重力时代一致（约 7 tick）。
- 平视的前向等效项**必须复刻 DS 的线性累加器**（`+0.004·FS/tick`，约 20 tick 爬到 0.079），
  **而不是常数、也不是指数缓动**——理由：与 DS 同构才能保证观感一致，并且它在俯角切换处**连续**
  （累加器天然如此，这正是 rev 4 修掉"阶跃"所用的同一条道理）。

**决策 D5** — 删除 rev 3/4 引入的三个量：

| 删除 | 原用途 | 为何现在必须删 |
|---|---|---|
| `GLIDE_BASE_ACCEL = 0.25` | 竖直基准 + 平视常开底座 | 是"过快 + 阶跃"的直接来源；其职责由 D2/D3 接管 |
| `GLIDE_FEEDBACK = 0.128` | 正反馈（对齐 DS 抬头强度） | 它把 DS **抬头专属**的量级搬到平视/低头；在 D2 下 DS 自己的 `dM`/`ax/az` 已承担该职责。**另有一个 rev 5 未覆盖的隐患**：源封顶只在 `h > 1` 后生效，`h < 1` 区间的环增益随 `FS` **平方**增长（45° ≈ `0.51·FS²`），`FS ≈ 1.4` 即达临界 ⇒ 删掉它同时消除该发散路径（诊断报告附 B） |
| `GLIDE_FEEDBACK_MAX_SPEED = 1.0` | 反馈源封顶 | 随反馈项一起删除 |

**保留**：`GLIDE_TURN = 0.10`（方向插值，只改方向不改大小；需求 3 要"飞往视角朝向"）、
`NORMALIZE_EPSILON`、`look.y <= 0` 的叠加式门、`isSpin` 跳过、HEAD 的"每 tick 必有一次写"不变式、
rev 5 的暂停守卫。

### 6.2 实现期的两处设计细化

1. **`levelness` 的连续混合**（设计只写了"随俯角连续衰减到 0"，未给机制）：
   `levelness = clamp(1 − |look.y| / GLIDE_LEVEL_BAND, 0, 1)`；
   下压乘 `(1 − levelness)`、前向乘 `levelness`。两项互补 ⇒ 带边界处前向速度连续
   （带外由 DS 的 `dM` 给 ≈0.08，带内由目标 0.079 给），也就不会复发 rev 4 的"阶跃"。
2. **HEAD 的写序固定为「先摘除 → 读重力基准 → 按需挂」**：因为修饰符会跨 tick 存活，
   若直接读 `getValue()`，滑翔中永远读到 0 ⇒ 重力等效下压会静默退化成 0（R1 的具体形态）。

### 6.3 顺带核实/更正

- **R2 已核实**：`vd = 1 − look.y²` 即 `cos²θ`；原版 `getLookAngle()` 恒为单位向量，
  故 DS 的 `verticalDelta` 中 `min(1, lookMagnitude/0.4)` 因子恒为 1。
- **诊断附 A 的结论已回填本节 D2 的刹车率前提**：DS 的滑翔**不**走原版 `isFallFlying()` 分支
  （DS 全源码无 `setSharedFlag`/`startFallFlying`，而 `isFallFlying()` = `getSharedFlag(7)`），
  所以 `f3 = 0.91` 与 `-g` 都照常生效，`A(θ) = g·(2 − 0.75·vd)` 的两项来源成立。

### 6.4 修订：平视悬崖（结构修复，源自 rev 5 的教训）

**症状（实机）**：完全平视时"几乎没有任何动力"。

**根因**：6.1 的实现把**前向等效项放回了 `if (look.y <= 0.0)` 的俯仰符号门内**（因为它当时与
`levelness` 同块计算）。而 `look.y = -sin(xRot)`，"完全平视"恰好落在门的边界上：摄像机高出一丝
（`xRot = -0.0001°` ⇒ `look.y = +1.7e-6`）整块被跳过 ⇒ 前向推力**从满值直接掉到 0**。
更糟的是平视时竖直也是零（2a 有意不缓沉、且 `dM` 因无下坠而失效）⇒ **两条前向能源同时消失**，
只剩原版 WASD 推力，速度按 `0.9009^n` 衰减（**1 秒掉到 ~1/8**）。

| 姿态（同一"平视"） | 前向输入 | 终端 |
|---|---|---|
| `look.y <= 0`（门通过） | 0.079 + WASD | ≈1.0 格/tick（≈21 格/秒） |
| `look.y > 0`（高一丝） | 仅 WASD | ≈0.26 格/tick（≈5 格/秒） |

**这是 rev 4 已修过、rev 6 又复发的同一类缺陷**——rev 5（提交 `63fcc6f`）的注释甚至原文预言过它：
"若挂在 `look.y <= 0` 之后……表现为'完全平视时没有任何动力'"。rev 5 唯一做对的一点正是
**把水平项放在符号门之外**。

**修复（借 rev 5 的结构 + 保留 rev 6 的量级与爬升）**：

```java
// 权重只看 |look.y| —— 以 0 为中心的对称带，与符号无关
double levelness = 1.0 - Math.abs(look.y) / beloong$GLIDE_LEVEL_BAND;
if (levelness < 0.0) levelness = 0.0;

// 前向等效：放在任何符号门之外（rev 5 的做法），保留 DS 式线性爬升
if (levelness > 0.0) acc = Math.min(acc + RAMP*FS, TARGET*FS); else acc *= 0.98;
Vec3 lookH = new Vec3(look.x, 0.0, look.z);
if (acc * levelness > 0.0 && lookH.length() > NORMALIZE_EPSILON)
    result = result.add(lookH.normalize().scale(acc * levelness));

// 重力等效下压：仍只在"非抬头"施加（它在 look.y = 0 两侧本就连续：levelness→1 时该项→0）
if (look.y <= 0.0) {
    double vd = 1.0 - look.y*look.y;
    result = result.add(0.0, -g_baseline * (2.0 - 0.75*vd) * (1.0 - levelness), 0.0);
}
```

**连续性核对**：`look.y = 0` 处前向为满值、下压为 0；`|look.y| = 0.2` 处前向连续归零（带外由 DS 的
`dM`/`ax/az` 接管）；抬头 `look.y > 0.2` 时前向为 0（代价是带的上半仍按 `levelness` 给少量前推力，
这是为消除悬崖有意让出的对称性，已在方法 javadoc 记为取舍）。

**量级未变**（用户裁定）：`TARGET = 0.079`（DS 原版档）、`RAMP = 0.004`（≈20 tick 到顶）。
