# 对账机制部分重写 + 性能优化 设计文档（2026-10-14）

**起因**：实机反馈 + 日志实证 —— 未完成流程离开龙宫后，进度**15 秒内被撤回且无任何提示**，
而私有分身**没被销毁**（区块卸载时只是被存档），导致**进度与实体分家**；回到龙宫后玩家被送回原点、
CG 却播在旧分身上 ⇒ 不同步。
（日志：`run/logs/latest.log` 里 `has the start advancement but no double` ×6、`reason: outside_dimension` ×0
⇒ 是 **D21** 撤的，而"离开维度"那条分支从未执行。）

## 二、新对账器的形状

| 判定 | 处置 |
|---|---|
| 重复分身（同一 owner 多只）| 保留最新（`bornAt` 新者优先，并列取离玩家近者），其余删除 ✓ **不撤** |
| 孤儿（有分身 ∧ 玩家未开始）| 删除分身 ✓ **不撤** |
| 通关（`finished`）| `keep_after_finish=false` ⇒ 删除 ✓ **不撤** |
| **租约到期**（`hasExpired`）| 删除分身 + **撤回整条链** ✓ ← 保留的两条之一 |
| ~~离开维度~~ | **删除**（连同提醒）|
| ~~扫不到分身~~（D21）| **删除**（连同 `searchTrustworthy` / `addMiss` / `missesOf` / `clearMiss` / `missingCounts` / `MISSES_BEFORE_RESET`）|
| ~~离线结算~~（`settleOffline` / `skipOfflineSettlement`）| **删除**（D6：离线一律不动）|

⇒ **对账器只处理"主人此刻在线"的分身** ✓（离线主人 ⇒ 不删、不撤、不判 ✓）。
⇒ ⇒ **"撤回进度"与"删除分身"此后永远成对** ✓ —— 这是本设计的中心不变量。

## 三、D6 为什么选"纯乙"，以及它的边界

离线到期时**删得掉、撤不了**（`PlayerAdvancements` 只存在于在线玩家上）⇒ 若强删，该玩家下次登录会停在
"有 `root`、无分身、锚点又永不显示"的**卡死**态 —— 这正是被删掉的 D21 存在的唯一理由。
自洽的解法要么留一张服务器级待撤回表 ✗，要么**干脆不删** ✓。用户裁定：**接受不删**，换取**零新状态**。

**能力边界（已知取舍，必须写清）**：
- 过期分身**只有主人看得见**（私有可见性）⇒ 它长期留存**对其他玩家不存在**，也不会渲染、不会被交互；
- 它所在区块**一旦被加载**（别人走剧情、路过、主人在线回来）⇒ 若主人**此刻在线** ⇒ 当场"删 + 撤"（成对 ✓）；
  若主人**仍离线** ⇒ 继续不动（纯乙 ✓）；
- ⇒ 因此"玩家永不再上线 ⇒ 分身永久残留"**在极端情况下仍会发生** ✗（一条实体 + 它的 NBT）；
  用户明确接受这一取舍（要消除它就必须恢复待撤回表 ✓ 已否 ✗）。人工兜底：管理员可 `/kill` 该实体。

## 四、租约的时间基准（已查证）

- `MinecraftServer.tickChildren` 遍历**所有维度**并逐个 `serverlevel.tick(...)`，
  **没有"空维度不 tick"的闸门**（`MinecraftServer.java:1039-1052`）；
- `ServerLevel.tickTime()` 只在 `this.tickTime` 为真时推进 `gameTime`，**不看玩家**（`ServerLevel.java:444-450`）；
- `beloong:loong_palace` 的维度类型是 `"natural": true`。
⇒ **玩家离开龙宫后，龙宫的 `gameTime` 照常推进 ⇒ 租约照常计时** ✓（D5 成立）。
**检查时机**：租约判定需要**扫到分身**（区块加载）⇒ 玩家离开期间扫不到 ⇒ 租约会**在下次扫到它时立刻判超期** ⇒
"删 + 撤"在同一刻完成 ✓ ⇒ 语义仍是"到期即重置"，只是执行被推迟到可执行的那一刻 ✓。

## 五、性能优化（S1 · S2 · A1）

审计口径：**调用频率 × 单次成本**（⚠️ 无 profiler 实测，结论由代码形状推出；实施后可加临时计时验证）。

### S1 ★ 实体注册表（替换 `level.getAllEntities()` 全实体扫描）

**问题**：`NpcStoryHandler.reconcileStory` 每个 sweep（默认 100 tick）对每条剧情**遍历该维度全部已加载实体**
（`ServerLevel.getAllEntities()` ⇒ `getEntities().getAll()`）—— 含掉落物、弹射物、成群怪物，而我们只要其中几只
`NpcEntity`。

**方案**：新增注册表（`npcstory/LoadedNpcIndex`），由 NeoForge 事件维护：
- `EntityJoinLevelEvent` ⇒ 记录（**已查实**：`PersistentEntitySectionManager:78-81` 的 `addEntity` 一定派发它，
  而**全仓唯一的 `addNewEntityWithoutEvent` 调用在 `ServerLevel:932`，只用于玩家** ⇒ 存档恢复**也会**触发 ✓）；
- `EntityLeaveLevelEvent` ⇒ **只作加速**，不作为正确性依赖（见下）；
- **正确性由读取时过滤保证**：卸载路径是 `unloadEntity` → `setRemoved(RemovalReason.UNLOADED_TO_CHUNK)`
  （`PersistentEntitySectionManager:234-236`）⇒ 读取时丢掉 `isRemoved()` 的条目即可，**leave 事件不触发也不会错** ✓；
- ⚠️ **死锁红线**：`EntityJoinLevelEvent` 的 javadoc 明确警告"可能早于 `ChunkStatus#FULL`，
  与世界交互会导致区块加载死锁" ⇒ **处理器里只许读写内存表**（不得访问 level/chunk/blockState/实体查询）✓；
  需要判到期/删除的动作一律放到 **tick 阶段** ✓。

**收益**：对账从"全维度实体"降到"个位数 NPC"；**A1（同维度重复扫描）被它吞掉**（不再有按维度扫描这一步）。

**回退**：极少数必须**精确**的路径（`ensureDouble` 找锚点）若注册表没给出候选 ⇒ **回退到一次全量扫描** ✓
（罕见 ⇒ 成本可接受；宁可慢也不能漏锚点）。

### S2 ★ 进度查询缓存（`NpcDialogueStage.isEarned` 收口）

**问题**：`NpcEntity#broadcastToPlayer` → `visibleTo` 在**每个追踪周期 × 范围内每个玩家**都会跑
（`NpcEntity.java:139-140`、`:1288`），其中 `NpcDialogueStage.isEarned` 会 `getOrStartProgress(...)`
——不只查询，**没记录时还会懒建一条** ✗（守卫注释里已点过）。

**方案**：在 `NpcDialogueStage.isEarned` 内加**短 TTL + 事件失效**的缓存（唯一的收口点 ⇒ `visibleTo` / 对账器 /
对话全部受益）：
- 失效点：`AdvancementEarnEvent`（置真）· 我们自己撤回（`revokeStory` / `revokeWholeAdvancement`）·
  `CgCompletionHandler` 授予 · 玩家登录/登出（清该玩家）· **TTL 兜底**（外部命令如 `/advancement revoke` 改动的可见性误差被限制在 TTL 内）；
- 另：把 `NpcStory` 缓存在 `NpcEntity` 上（瞬时字段），`NpcStoryLoader.reloadStamp()` 变化即失效。

**风险**：缓存过期窗口内可能给出**短暂的**错误可见性（有界，靠 TTL）；**不改变任何持久状态**。

### A1 同维度重复扫描 ⇒ 被 S1 取代 ✓
### A2 寻路"放弃后不重试" ⇒ **不做**（用户：那是设计目的）

## 六、租约续约（D10 / D11）

### 目的
**缺省的**一小时租约对**长剧情**太短（实际时长由该剧情 JSON 的 `lease.ticks` 决定） ⇒ 玩家**积极推进**时必须续约，避免剧情过半被重置；
同时它天然区分"**正常过剧情的玩家**"与"**跳过/不做剧情的玩家**"（后者不续约 ⇒ 租约自然到期 ⇒ 删 + 撤）。

### 规则
- **触发**：`AdvancementEarnEvent`（`NpcStoryHandler` 已在监听）；
- **认哪些进度**：只认**剧情链上 `start` 与 `end` 之间**的进度 ⇒ 端点（`root` / `5_1`）**不**续约，
  中间的一切（含 `1_0`「末的登场」）**都**续约；
- **续约时长 = 该剧情 JSON 里配置的租约时长**（**缺省** 1 小时，**不是硬编码**）：
  实现上就是 `setLease(now, story.expiryAt(now))` —— `expiryAt(now)` 用的是该剧情自己的
  `ticks` 配置 ⇒ 配置改成多少，续约就续多少 ✓（本仓库不出现"一小时"这个字面量 ✓）；
- **动作**：把**该玩家该剧情的分身**的租约 `setLease(now, story.expiryAt(now))` ⇒ 重新从当下起算**该剧情配置的**一整段租约时长（缺省 1 小时）；
- **开关**：`lease.renewal`（`lease{}` 组内的布尔，**缺省 true**）；模组侧 `mo.json` **显式写** `"renewal": true`；
- **显式列表**：可选数组 `lease.renew_advancements`（给了就**覆盖**缺省规则）；
- **日志**：每次续约打一条 INFO（旧到期 → 新到期），排查"某人为什么没被清"时是决定性证据。

### 实现要点
1. **缺省列表惰性解析一次**：要沿 `parent()` 上溯（**复用 `revokeStory` 那个链遍历器**），
   而进度管理器在数据包加载后才就绪 ⇒ 沿用既有 `checkStoryIdsOnce` + reload stamp 模式，重载后失效；
2. **校验**：列表里每个 id **必须真在链上**（否则链外进度就能续约）⇒ 解析时校验，违规记 WARN 并忽略该条；
3. **只续该剧情那只分身**（不得"给该玩家所有分身续约"——那会掩盖其它剧情的超期）；
4. **够不到分身时**：注册表未命中 ⇒ **回退一次全量扫描**（只扫该剧情维度，罕见）⇒ 仍找不到记 WARN（不静默）；
5. **不动"完成"路径**：已完成的剧情直接跳过续约（不报错）。

### 它顺带解开的张力
```
在龙宫内积极推进 ⇒ 每次里程碑续约 ⇒ 永不被误清 ✓
离开龙宫 / 在龙宫内发呆 ⇒ 没有里程碑 ⇒ 租约照常计时（D5）自然到期 ⇒ 删 + 撤 ✓
```
⇒ "跳过剧情的会被清掉"不再需要任何激进逻辑（"离开即重置"），它就是"**不续约就会到期**"的自然结果。

### ⚠️ 明确写出的连带语义（有破坏性，用户已接受）
租约到期是"**删分身 + 撤进度**"⇒ 所以**积极推进才保住进度**，而**长时间不推进的玩家会丢掉剧情进度**。
这正是"区分"的目的，但它确实是破坏性的 ⇒ 此处记录在案。

## 七、序章的两处修正（与重写配套）

### C. 从头开场时，先清掉孤儿分身，再传送、再新建
对账器每 100 tick 扫一次，而序章每 20 tick 一次 ⇒ **撤进度后序章可能先于对账器的孤儿清理跑起来** ⇒
它会 `ensureDoubleFor` **扫到旧分身并复用** ⇒ "玩家在原点、CG 拍在旧分身" ⇒ 又不同步。
故"从头开场"分支必须：**若存在 `owner == 我` 的分身（此时玩家没有 `root` ⇒ 它必然是上一轮的孤儿）
⇒ 先 `discard()` ⇒ 再传送 ⇒ 再确保分身（此时必然是全新的、在锚点）⇒ 再授予 `root` ⇒ 再播 CG。**

### D. 恢复分支（`root ∧ ¬1_0` ⇒ 补授 `1_0`）不得在 CG 播放期间触发
日志实测：它在 **CG 开始后 1 秒**就补授了 `1_0`（5 次）。改法：补授前先问 `CgCompletionHandler`
**是否存在该玩家的待授予项** ⇒ 有则**不补**（`1_0` 由 CG 按时长授予）。

## 八、语义变化（明确）

| 之前 | 现在 |
|---|---|
| 离开龙宫 = **跳过**剧情（重置 + 回来重新开场 + 送回原点）| 离开龙宫 = **暂停**（进度与分身都保留；回来接着走，`root` 还在 ⇒ 序章不介入）|
| "从头开场"由"离开维度"或"扫不到分身"触发 | 只由 **租约到期** 或 **手动撤进度** 触发 |

## 九、保留风险（已知取舍）

1. **分身被外部删掉**（`/kill`、世界数据损坏）⇒ 无自动恢复 ⇒ 玩家停在"有 `root`、无分身"的卡死态。
   用户裁定**暂不加手动重置命令** ⇒ 真出现时人工处理（`/advancement revoke` 后重进龙宫即可）。
   缓解：分身**无敌**且**不可被玩家移动/牵引/传送**（前几轮的工作）。
2. **永不上线的玩家其过期分身可能永久残留**（§三，用户接受）。
