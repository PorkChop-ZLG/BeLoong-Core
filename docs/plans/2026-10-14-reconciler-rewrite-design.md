# 对账机制部分重写 设计文档（2026-10-14）

**起因**：实机反馈 + 日志实证 —— 未完成流程离开龙宫后，进度**15 秒内被撤回且无任何提示**，
而私有分身**没被销毁**（它在区块卸载时只是被存档），导致**进度与实体分家**；
回到龙宫后玩家被送回原点、CG 却播在旧分身上 ⇒ 不同步。
（日志：`run/logs/latest.log` 里 `has the start advancement but no double` ×6、
`reason: outside_dimension` ×0 ⇒ 是 **D21** 撤的，而"离开维度"那条分支从未执行。）

## 决策（用户 2026-10-14 裁定）

| # | 决定 |
|---|---|
| D1 | **删除**"玩家离开剧情维度 ⇒ 重置 + 销毁"这个功能（含它的提醒）|
| D2 | **删除**"找不到该玩家的私有 NPC ⇒ 重置 + 销毁"这个功能（即 D21 及其 miss 计数机制）|
| D3 | **只保留两条清理**：① 配置时间内**未完成** ⇒ 删 + 撤（租约）；② **剧情完成** ⇒ 删（`keep_after_finish` 例外）|
| D4 | 删除 D21 后应当**直接修掉**本 BUG |
| D5 | **离开龙宫维度后，租约照常计算**，到期即"重置进度 + 销毁 NPC"（不再有"离开=跳过"的即时清理）|
| D6 | **离线**到期 ⇒ 先把分身删掉、**留下"待撤回"标记**，玩家**重登时**撤回（离线读不到玩家进度，这是既有事实）|
| D7 | **暂不**提供手动重置命令 |
| D8 | `npc_story` 的 `dimension{}` 组：**选甲 —— 删掉失去消费者的字段**（保留 `host`）；**只改模组自带的数据文件**（整合包尚未使用新格式 ⇒ 无需考虑旧存档）|

## 为什么 D4 成立

D21 是唯一"**手里没有实体却要撤进度**"的路径 ⇒ 它撤销时**无法删除分身** ⇒ 必然分家。
删掉它之后，剩下两条清理都**只在自己删掉分身的那一刻**才撤进度 ⇒
**"撤回进度"与"删除分身"永远成对** ⇒ 分家不可能再发生。

## 新对账器的形状

| 判定 | 处置 |
|---|---|
| 重复分身（同一 owner 多只）| 保留最新（出生时刻新、并列时取离玩家近的），其余删除 ✓ **不撤** |
| 孤儿（有分身 ∧ 玩家未开始）| 删除分身 ✓ **不撤** |
| 通关（`finished`）| `keep_after_finish=false` ⇒ 删除 ✓ **不撤** |
| **租约到期**（`hasExpired`）| 删除分身 + **撤回整条链** ✓ ← 保留的两条之一 |
| 离线租约到期 | 删除分身 + 在玩家持久数据里写**待撤回**标记 ✓ ⇒ 重登时撤回 |
| ~~离开维度~~ | **删除**（连同提醒）|
| ~~扫不到分身~~ | **删除**（连同 `searchTrustworthy` / `addMiss` / `missesOf` / `clearMiss` / `missingCounts` / `MISSES_BEFORE_RESET`）|

## 租约的时间基准（已查证）

- `MinecraftServer.tickChildren` 遍历**所有维度**并逐个 `serverlevel.tick(...)`，
  **没有"空维度不 tick"的闸门**（`MinecraftServer.java:1039-1052`）；
- `ServerLevel.tickTime()` 只在 `this.tickTime` 为真时推进 `gameTime`，**不看玩家**
  （`ServerLevel.java:444-450`）；该标志来自维度类型，而 `beloong:loong_palace` 是 `"natural": true`。
⇒ **结论**：玩家离开龙宫后，龙宫的 `gameTime` **照常推进** ⇒ **租约照常计时** ✓（D5 成立）。
> 待办：把 `tickTime ⇐ natural()` 这一行调用点在实施时确认一次（高置信，但本设计不靠它成立——
> 即便它不成立，租约也仍以**该维度自己的时间**计算，语义一致）。

**检查时机**：租约判定需要**扫到分身**（区块加载）⇒ 玩家离开期间扫不到 ⇒ 租约会**在下次扫到它时立刻判超期** ⇒
"删 + 撤"在同一刻完成 ✓ ⇒ 语义上仍是"到期即重置"，只是执行被推迟到可执行的那一刻 ✓。

## 序章的两处修正（与对账器重写配套）

### C. 从头开场时，先清掉孤儿分身，再传送、再新建

对账器每 100 tick 扫一次，而序章每 20 tick 一次 ⇒ **手动/租约撤进度后，序章可能先于对账器的孤儿清理跑起来**
⇒ 它会 `ensureDoubleFor` **扫到旧分身并复用** ⇒ 于是"玩家在原点、CG 拍在旧分身"又不同步。
故序章的"从头开场"分支必须：**若存在 `owner == 我` 的分身（此时玩家没有 `root` ⇒ 它必然是上一轮的孤儿）
⇒ 先 `discard()` 掉 ⇒ 再传送 ⇒ 再确保分身（这时必然是全新的、生成在锚点）⇒ 再授予 `root` ⇒ 再播 CG。**

### D. 恢复分支（`root ∧ ¬1_0` ⇒ 补授 `1_0`）不得在 CG 播放期间触发

日志实测：它在 **CG 开始后 1 秒**就补授了 `1_0`（5 次）。该分支本意是"CG 被服务器关停打断"的兜底。
改法：补授前先问 `CgCompletionHandler` **是否存在该玩家的待授予项** ⇒ 有 ⇒ **不补**（`1_0` 会由 CG 按时长授予）。

## 语义变化（必须明确）

| 之前 | 现在 |
|---|---|
| 离开龙宫 = **跳过**剧情（重置 + 回来重新开场 + 送回原点）| 离开龙宫 = **暂停**（进度与分身都保留；回来接着走，`root` 还在 ⇒ 序章不介入）|
| "从头开场"由"离开维度"触发 | "从头开场"只由 **租约到期** 或 **手动撤进度** 触发（那两条例外合理：前者是配置时间到，后者是人主动）|

## 保留下来的风险（已知取舍）

- **分身被外部删掉**（`/kill`、世界数据损坏）⇒ 不再有自动恢复 ⇒ 玩家会停在"有 `root`、无分身、锚点永不显示"的卡死态。
  用户裁定 **暂不加手动重置命令** ⇒ 真出现时人工处理（`/advancement revoke` + 让它重新开场即可）。
  缓解：分身本身**无敌**、**不可被玩家移动/牵引/传送**（前几轮的工作）⇒ "外部删掉"只剩管理员命令与世界损坏两条路。
