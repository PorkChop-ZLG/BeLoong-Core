# NPC 一次性表情的"播完即清"设计文档

**Date:** 2026-10-13
**Status:** Approved（三节逐节确认通过）
**Approach:** 客户端回报长度 + 服务端定时清除（表情层通用修复）

---

## 一、问题陈述

**症状**（用户实测）：玩家获得触发 CG 的进度（`beloong:npc/root`）后，**每次离开末一定距离（~100 格）
再走回来，末都会重播一遍登场动画**（`descend`）——**只有动作，没有运镜**。

**影响面**：任何**一次性（`PLAY_ONCE`）**表情都受影响，不只 CG：

| 场景 | 机制 | 修前 |
|---|---|---|
| **走远再回来**（用户报告） | 超出追踪半径 ⇒ 客户端销毁并**重建实体实例** | 重播 |
| 同会话内换维度 / 传送后回来 | 同上 | 重播 |
| 断线重连 | 客户端无任何记忆 | 重播 |
| 别人中途加入 | 新客户端没有"播过了"的记忆 | 重播（**09-29 就已明确接受**） |

**根因不在 CG 层，也不在"距离"上** —— 而是**表情系统缺少"一次性表情的生命周期"**。
CG 只是**第一个使用"很长的一次性表情"的用户**，于是把一个一直存在、但没人注意的缺陷放大成了显眼的 bug。

## 二、已核实的既有事实（全部附行号）

### 2.1 缺陷链（四环，每环都已核到源码）

1. **CG 播动画 = 写一个同步字段。** `CgAnimation.play` → `npc.setEmote("descend")`
   → `NpcEntity:848` 写 `DATA_EMOTE`（`:378` 定义、`:502` 默认 `""`）。
2. **"播完了没有"只记在客户端本地字段。** 控制器 `NpcEntity:1705-1747` 播满长度后
   只做 `npc.emoteDone = true`（`:1743`）；`emoteDone`（`:1635`）、`emoteSeen`、`emoteStartTick`
   **都是客户端瞬态，不同步**。`:1622` 的既有注释自己写明了：
   *"服务端只知道 `DATA_EMOTE`（那个名字），'播完了没有'只有客户端能判断"*。
3. **没有任何"时间到了/播完了"的清理。** 全仓 `clearEmote()` 的调用点**全是事件驱动**
   （`state` / `move` / `attack` / `reset` / `play stop` / 对话 `stop_emote`）
   ⇒ **播完之后 `DATA_EMOTE` 永久停在 `"descend"`。**
4. **重新追踪 ⇒ 客户端重建实例 ⇒ 从头再播。** `beloong:mo` 注册为 `.clientTrackingRange(10)`
   （`ModEntities.java:105`）= 10 区块 = **160 格**。玩家走出该半径 ⇒ 客户端销毁该实体；
   走回 ⇒ 客户端**新建实例**并收到生成包 + 全部非默认同步字段（含 `DATA_EMOTE="descend"`）。
   新实例的 `emoteSeen=""` / `emoteDone=false` / `emoteStartTick=0` ⇒ 控制器判定"换了一条表情"
   （`:1715-1720`）⇒ **从第 0 tick 重播**。

**并且这条链在代码注释里已经写死了**（`NpcEntity:855-856`）：
> 客户端会**无条件**收到通知（`SyncedEntityData.assignValues` 对每个条目都调本方法、不比较新旧值）
> ⇒ 下一个谓词帧就会重新走一遍"换名"分支、重新钉计时起点。

### 2.2 日志证据：重播**完全没走服务端**

- 复现实例（旧版 `beloong-core`，NeoForge 21.1.248）的 `latest.log`，会话 22:08–22:35（**27 分钟**）
  里 `[BeLoong] cg 'mo_entrance' playing` **只有 2 条**（22:15:37 / 22:16:45）。
- 而"每次走远回来都会重播"在 27 分钟里发生了很多次 ⇒ **它们一条日志都没有**。
- 交叉核对：`BeLoong-Core-NPC/run/logs/` 下**全部 79 个日志文件（含 `.gz` 轮转）共 83 条命中**里，
  **`failed to send the cutscene` 与 `aborted:` 一条都没有** ⇒ 服务端每次发包都是成功的。
- `descend` 这个动画名**在所有数据文件里都不出现**（唯一的路线表情是 `end_emote: "sit"`）
  ⇒ 它只可能由 `CgAnimation.play` 设置 ⇒ 而它没走服务端 ⇒ **⇒ 只能是客户端拿旧字段自己重播。**

### 2.3 系统自己已经区分了"姿态"与"一次性"（本方案的地基）

判据是资产的 `loop` 字段，控制器 `:1727` 就按它分支：

| 动画 | `loop` | `LoopType` | 语义 | 走远再回来应该怎样 |
|---|---|---|---|---|
| **`descend`** | 缺失 | **`PLAY_ONCE`** | 一次性演出 | **绝不重播** ← 本 bug |
| `sit` | `true` | `LOOP` | 姿态 | **应当保持**（"它坐在那里"是刻意设计，`keep_after_finish=true`） |
| `dance` | `true` | `LOOP` | 姿态 | 同上 |

⇒ **任何"播完就清"的方案都必须只作用于一次性表情**，否则会打断"坐下"这个刻意设计。

### 2.4 一条**范围被低估**的既有取舍（不是判断错误）

`docs/plans/2026-09-29-npc-emote-system-design.md:214`：

> \| 中途加入的观察者 \| 同步字段里若留着一次性表情名，他会**从头再播一遍**（**已接受**；与 DS 同性质）\|

**当时"已接受"的适用范围是"中途加入的观察者"**（别人走进视野，罕见），
**没有考虑到"你自己走开再回来"** —— 同一机制，但把一次性演出变成了**可无限重播**的东西。
本次修复把这一整类（含那条已接受项）一起收掉。

### 2.5 两处对方案形状有决定作用的代码事实

- **`setEmote` 用 `force = true`**（`:843-848`），注释写明：*"再播一次同一条一次性表情**正是值没变**的情形"*
  ⇒ **每次 `setEmote` 都是一次"要求重播"**，哪怕同名。⇒ 服务端可以自己记"最后一次要求播它的时刻"，
  **不需要客户端带 nonce / 不需要新增同步字段**。
- **`onSyncedDataUpdated` 不依赖渲染**（`:855`），但**控制器只在渲染时跑**
  ⇒ 决定了申报点的选择（见 D3）。

## 三、设计

### 3.1 架构（核心机制）

**让"这个一次性表情已经播完了"从"客户端内存"变成"服务端知道的事实"。**

```
服务端 setEmote("descend")  ──force 发包──►  客户端控制器首次起表（find 成功）
                                                  │ · LOOP           ⇒ 不申报（姿态）
                                                  │ · 其它（PLAY_ONCE）⇒ 发 C1：名字 + 长度
                                                  ▼
服务端 handleServer ──校验（实体 + 名字）──► 记计划 deadline = npc.emoteSetAt + duration
                                                  │
                             NpcEmoteExpiryHandler 每 tick 检查（与区块加载无关）
                                                  ▼
                          到点 且 npc.emote() 仍 == 计划里的名字 ⇒ npc.clearEmote()
                                                     （DATA_EMOTE 回 ""，同步给所有人）
```

**四条性质**：

| 性质 | 为什么成立 |
|---|---|
| **姿态不受影响** | 申报的唯一入口是"客户端解析出 `PLAY_ONCE`"；`sit`/`dance` 是 `LOOP` ⇒ 根本不上报 ⇒ 服务端永远没有它们的计划 |
| **不依赖视线/距离** | 申报由"控制器起表"触发；CG 期间相机锁在末身上、且 `nullifyInput` 锁输入 ⇒ 末一定被渲染、玩家也走不掉 |
| **四行场景全修** | 服务端到点把字段清回 `""` ⇒ 此后**任何**客户端重建实例看到的都是 `""` ⇒ 不播 |
| **同名二次点播仍能播** | 字段已被清回 `""`，"再播一次"永远是 `"" → 名字` 的变化；再加上 `force=true` 兜底 ⇒ 一定能重播 |

### 3.2 组件（2 新 3 改）

| # | 位置 | 类型 | 职责 |
|---|---|---|---|
| **C1** | `NpcEmoteDurationPayload`（与 `NpcDialogueReplyPayload` 同处） | 新 | C→S：`(entityId, emoteName, durationTicks)`。照既有形状：`record` + `Type` + `StreamCodec.composite` + `handleServer`（模板：`NpcDialogueReplyPayload:42-67`） |
| **C2** | `BeLoongCore.registerPayloads` | 改 | 加一条 `registrar.playToServer(...)`（先例：`:163-177`） |
| **C3** | `NpcEntity.setEmote` + 2 个普通字段 | 改 | ① `emoteSetAt = gameTime`（**每次调用都刷新**）；② 作废该实体的待清计划 |
| **C4** | `NpcEntity` 表情控制器的"起表"分支（`:1715-1720` 附近） | 改 | 客户端申报入口（**在 `EmoteAnimationLookup.find` 成功之后**） |
| **C5** | `NpcEmoteExpiryHandler` | 新 | `ServerTickEvent.Post`：驱动到期清除 |

### 3.3 数据流与四条不变量

| 不变量 | 内容 | 为什么必须 |
|---|---|---|
| **I1** | **重复申报幂等** —— 到期用 `emoteSetAt + duration`，**不是** `now + duration` | 重新追踪时客户端会**再申报一次**。若用 `now`，玩家在末旁边来回走就会把清除**无限推后** ⇒ 永远清不掉。用 `emoteSetAt` 则同一轮申报结果恒等 |
| **I2** | `setEmote` **每次都刷新** `emoteSetAt` 并作废旧计划 | `force=true` 的语义就是"再播一次" ⇒ 同名二次点播必须得到新到期时刻；同时保证旧计划不会把**新**表情清掉 |
| **I3** | 到期时**名字必须仍然一致**才清 | 用户裁定的校验口径；也防"计划还在、表情已被换掉" |
| **I4** | **`LOOP` 姿态永不上报** | 保护 `sit`/`dance` 与 `keep_after_finish` 的刻意设计 |

### 3.4 为什么定时器必须与区块加载无关（硬约束，不是偏好）

玩家走远 ⇒ 那个区块**不再 tick**；而**恰恰是这段时间需要把字段清掉**（否则玩家回来时字段还在）。
⇒ 挂在 `NpcEntity.tick()` 上**必然失效**；必须挂在一个每 tick 都跑的服务端处理器上。

计划表 `实体 → (名字, 到期时刻)`：

- **天然有界**：每个实体最多一条（`setEmote` 覆盖）
- **无泄漏**：到点、或实体已被移除就删；以实体引用作键（`NpcEntity` 未重写 `equals` ⇒ 身份语义）

## 四、错误处理

| 情况 | 行为 | 理由 |
|---|---|---|
| 客户端**不上报**（资产查不到 / 是 LOOP） | 服务端无计划 ⇒ 字段留着 | **降级为现状，不是新故障**。查不到 ⇒ 本来也不播；LOOP ⇒ 本来就不该清 |
| **没人渲染过**这条一次性表情 | 字段留着 ⇒ 下次有人靠近时**重播一次**，同时起表申报 ⇒ 随后被清 | **自愈，但有一次代价。** 唯一残留；对 CG 不成立（见 3.1） |
| `durationTicks <= 0` | **忽略该申报**（不建计划） | ⚠️ **这不是防伪栅栏** —— 资产里最短动画也是 1 tick，"长度 0"是**无效输入**。防伪按 D6 不做 |
| `durationTicks` 极大 | 计划≈永不到期 ⇒ 字段不清 | 属 D6 已接受的"谎报长度"风险面。**只防溢出、不防伪造**：`Math.addExact` 或夹到安全上限，**绝不让它抛异常或变负数** |
| 申报时名字已不匹配 | 忽略 | I3 |
| 实体在到期前 `discard()` | sweep 发现已移除 ⇒ **只丢计划，不动任何东西** | 防泄漏；不能对已移除实体动手 |
| 区块卸载后到期 | **照样清** | 正是设计目的；实体仍在，只是没人看 ⇒ 字段已清 ⇒ 玩家回来时是空的 |
| 到期时名字又被换了 | 只丢计划，不动字段 | I2 已让 `setEmote` 作废旧计划，这是第二道；绝不误清新表情 |
| `clearEmote()` 自身会刷新 `emoteSetAt` | 遍历时**先收集到期项**再逐个处理（或用迭代器 `remove`） | 避免 `ConcurrentModificationException` |
| 专用服务器无任何客户端 | 无申报 ⇒ 无计划 ⇒ 不清 | 无害（没人在看）；**服务端不需要知道资产** |

**刻意不做**：不新增防伪校验（D6）；不给忽略路径加 WARN（"名字不匹配"是正常竞态）；
不改任何既有 `clearEmote()` 调用点；不新增同步字段。

## 六、决策与非目标

### 6.1 决策

| # | 决策 | 理由 |
|---|---|---|
| **D1** | **修在表情层，不修在 CG 层**（用户裁定） | 根因是"一次性表情没有生命周期"；CG 只是第一个用户；且必须保护姿态 |
| **D2** | **让服务端知道"已播完"**，四行场景全修（用户裁定） | 代价是 1 个 C→S 包；换来 `DATA_EMOTE` 回归本义"**当前**表情" |
| **D3** | **申报点 = 控制器首次起表且 `find` 成功之后**（不是 `onSyncedDataUpdated`） | 保证拿到资产（否则会静默永不申报）；语义就是"我正准备播它"；自愈性继承自 `:1724` 的"不做负缓存" |
| **D4** | **服务端不做资产解析** | 长度是客户端上报的**结论**，不违反 `:1704`"长度是客户端资产数据、判断全放客户端"的既有原则 |
| **D5** | **到期用 `emoteSetAt + duration`** | 重复申报幂等的唯一来源（I1） |
| **D6** | **任何 `NpcEntity` 都受理，仅校验"实体 + 名字"**（用户裁定） | 公共锚点上的一次性表情也一并修好、无特例。已接受：改装客户端可谎报长度提前清掉共享 NPC 的表情（纯观感） |
| **D7** | **定时器与区块加载无关** | 硬约束，见 3.4 |
| **D8** | **`LOOP` 姿态完全不上报** | 保护 `sit` 与 `keep_after_finish=true` 的刻意设计 |

### 6.2 非目标

- **不新增同步字段**（不需要 nonce，因为 `force=true` 已经提供了"重播意图"的判据）
- **不动任何既有 `clearEmote()` 调用点**（语义不变）
- **不给"忽略申报"的路径加 WARN**（正常竞态，报了就是噪声）
- **不做防伪**（D6 已接受；只做"无效输入不产生行为"）
- ~~**相关但不在本次范围**~~ → **已在本次修复（T5，用户裁定"改代码让行为符合注释"）**：
  `NpcStoryHandler` 的注释写着 *"幂等：已经有自己的分身了，复用它（不重复生成、**不重播 CG**）"*，
  但调用方原先在返回**既有**分身时也会无条件 `cg.play` ⇒ 一旦 `root` 被重新获得而分身还在，
  CG 会完整重播（带运镜）。现 `ensureDouble` 改为返回 `Ensured(npc, spawned)`，
  调用方**只在 `spawned` 时**才播 CG。
  （它原本记在这里是因为"路径难以到达、且症状与本次不同"；用户 2026-10-13 裁定顺手修掉。）
