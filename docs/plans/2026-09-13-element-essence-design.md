## 1. 需求

为 BeLoong-Core 添加「元素魔源」系列基础物品。

**初版需求（2026-09-13）**：8 件，对应五行（金木水火土）加冰风雷：

1. 8 个物品，中文名「X魔源」，无任何额外效果；
2. 每个物品有**动态贴图**（12 帧），贴图由本项目自行绘制；
3. 每个物品有 tooltip，文本格式为「自然界的X元素凝聚成的魔源，可以为龙的成长提供魔力。」；
4. 物品 ID 与英文名需与用户共同讨论定案。

**后续增补（同日晚）**：追加**光**与**暗**两种元素，共 10 件：

5. 光与暗按与其他八件完全相同的方式注册（同样的类、属性、tooltip 模板），**顺序排在雷之后**；
6. 光与暗的**贴图暂不准备**，直接留空 → 见 §6.6 的"留空"具体含义与后果；
7. 用户明确**雷的贴图不再改动**。

**需求变更记录**：第 2 条（动态贴图）已被用户否决，改为静态图，见 §4。

### 2.1 「金」的两处命名依据

- **ID/英文名用 `metal` 而非 `gold`**：金是五行之"金"（金属），不是黄金这一具体材质。
- **tooltip 里「金」代入「金属」而非「金」**：中文「金元素」会被读成"金钱"的金，且与「金属」不是同一个词；「金属元素」才是中文的正确说法。其余七项保持单字（木/水/火/土/冰/风/雷），因为「木元素」「火元素」本身就是中文通用说法。

### 2.2 稀有度取值的由来（重要，勿改回）

用户最初要求"原版金色对应的稀有度"。**1.21.1 原版四个稀有度没有任何一个是金色**（`Rarity.java:16-19`）：

| 稀有度 | 显示色 | 色值 |
|---|---|---|
| `COMMON` | 白 | `#FFFFFF` |
| `UNCOMMON` | 黄 | `#FFFF55` |
| `RARE` | 青 | `#55FFFF` |
| `EPIC` | 品红 | `#FF55FF` |

而 `ChatFormatting.GOLD` 是 `#FFAA00`（`ChatFormatting.java:23`）——**金色是原版颜色常量，但原版稀有度没有谁用它**。这个印象很可能来自 1.12 及以前（1.13 扁平化重排了稀有度语义）。

用户最终选择 **`Rarity.UNCOMMON`**，因为它是原版四个中最接近"金"的观感（黄色），且零额外代码。也评估过用 FML 的 `RuntimeEnumExtender` 给 `Rarity` 注入一个金色常量（技术上可行：`Rarity` 声明了 `@IndexedEnum`/`@NamedEnum(1)`/`@NetworkedEnum(BIDIRECTIONAL)` 并实现 `IExtensibleEnum`，是官方支持的扩展点），但因代价超出 8 个基础物品的收益而未采用。

## 3. 架构

**十件物品就地写在 `ModItems` 里，不建类、不建枚举、不建基类。**

**2026-09-13 两次回退记录**（用户连续两次指出抽象过度，最终形态如下）：

| 版本 | 结构 | 结局 |
|---|---|---|
| V1 | 一个参数化物品类 + `ElementType` 枚举 + 语言文件「共享模板 + 元素代入词」 | 用户否决："为了写 tooltip 专门写一个类保存各种元素，没有必要" |
| V2 | 每件物品一个子类，tooltip 各写各的（10 个类文件 + 1 个只放属性的基类） | 用户否决："只是简单注册物品，可以直接在 ModItems 里面写，没必要额外写十个类" |
| **V3（最终）** | **全部写在 `ModItems` 里**：一个私有工厂返回匿名 `Item` 子类，tooltip 键作为参数传入 | — |

```java
/** 元素魔源（金）。 */
public static final DeferredItem<Item> METAL_ESSENCE =
        Items.register("metal_essence", essenceSupplier("item.beloong.metal_essence.tooltip"));
// …另外 9 件同形，仅 tooltip 键不同

/**
 * 构造一件元素魔源：唯一的行为变化是 tooltip，文案在语言文件里。
 */
private static Supplier<Item> essenceSupplier(String tooltipKey) {
    return () -> new Item(new Item.Properties().rarity(Rarity.UNCOMMON)) {
        @Override
        public void appendHoverText(ItemStack stack, TooltipContext context,
                                    List<Component> tooltipComponents, TooltipFlag tooltipFlag) {
            tooltipComponents.add(Component.translatable(tooltipKey));
        }
    };
}
```

**为什么工厂返回 `Supplier` 而不是 `Item`**：`DeferredRegister.Items.register` 是**懒加载**注册（要的是 `Supplier<Item>`），直接传实例编译不过。这是本次实测踩到的编译错误。

**匿名子类只有一个类文件**：jar 里只有 `ModItems$1.class`，10 件物品共用同一份类字节码，只是各自持有不同的 `tooltipKey`。

**语言文件**：每件一条完整句子（共 10 条），没有 `%s`、没有共享模板、没有元素代入词。

| 键 | 值 |
|---|---|
| `item.beloong.metal_essence.tooltip` | 自然界的**金属**元素凝聚成的魔源，可以为龙的成长提供魔力。 |
| `item.beloong.light_essence.tooltip` | 自然界的光元素凝聚成的魔源，可以为龙的成长提供魔力。 |
| …（其余 8 条同理） | |

**被回退方案留下的技术结论（仍有价值）**：`%s` 按出现顺序取参（`TranslatableContents.decomposeTemplate`：无显式序号时 `i++` 递增取 `args[i]`）。曾经因为传了「物品名 + 元素词」两个参数，中文模板的第一个 `%s` 位于「自然界的…元素」中间而取到物品名，渲染出「自然界的**金魔源**元素凝聚成的魔源」——这类位置错配只有在**用真实语言文件重演展开**时才会暴露（见 §9）。现在改成每件一条完整句子后，这个失败模式不再存在。

## 4. 贴图规格（已从 12 帧动态改为静态单帧）

**2026-09-13 修订**：初版要求"动态贴图"，实现为 12 帧 16×192 竖排帧条 + `.mcmeta`（`frametime 1`、不插值，规格取自 NeoForge 源码 `SpriteContents` / `AnimationMetadataSection`）。三批成品出来后**用户判定该美术方向失败**，同时改变要求：

1. **不再需要动态贴图，全部使用静态图**；
2. 由用户直接提供五行（金木水火土）的成品贴图，由我参照其画风补上冰、风、雷三张。

因此本节的动画规格（帧数、`frametime`、`interpolate`、帧条布局）**全部作废**，8 个 `.mcmeta` 已从资源目录移除。保留的技术结论仅两条：

- 纹理为 **16×16 RGBA**；静态贴图**不得存在** `.mcmeta`，否则 Minecraft 会把该 sprite 当作动画帧条解析并误算帧尺寸。
- 物品模型仍为 `minecraft:item/generated` + 单层 `layer0`，与是否动画无关。

## 5. 美术设计（手绘静态图标）

### 5.1 画风基线（由用户提供的五张量测得出）

用户提供的五张位于 `preview/新建文件夹`：`{gold,wood,water,fire,soil}element.png`。实测特征：

| 特征 | 实测值 |
|---|---|
| 尺寸/格式 | 全部 16×16、32bpp ARGB |
| 颜色数 | 每张 ~100 种（142 不透明像素里有 136 种色）⇒ **逐像素渐变/噪声，不是小调色板像素画** |
| 轮廓 | **无描边**，形完全由内部明暗承担 |
| 光源 | 顶部/左上；最亮的格在高处与中部 |
| 剪影 | 有机不规则，且**允许分离的散点**（火有脱离主体的火星像素） |
| 不透明像素数 | 103–142 |

色带层次（粗量化 32 级后）举例：土为 `#FFE1BC` 亮奶油心 → `#A08040` → `#402000` 棕边；水为 `#AAFDFE` 高光 → `#00C0E0` → `#0040A0` 深蓝；火为 `#600000` 暗红边 → `#C00000` → `#FF9D44` 亮橙心。剪影：金=矿块、木=斜向叶、水=水滴、火=火苗、土=**完美圆形卵石**（带中心十字高光）。

### 5.3 冰 / 风 / 雷的来源与做法

| 元素 | 来源 | 做法 |
|---|---|---|
| 冰 | 用户用 AI 生成的 1254×1254 雪花图（`preview/ChatGPT Image 2026年9月13日 19_43_05.png`） | `tools/convert_element_sources.py` 转成 16×16 |
| 风 | 用户用 AI 生成的 1254×1254 气旋图（`preview/ChatGPT Image 2026年9月13日 19_43_22.png`） | 同上 |
| 雷 | 用户用 AI 生成的 1254×1254 闪电图（`preview/ChatGPT Image 2026年9月14日 13_19_39.png`） | 同上，**高度上限 14** |

**三张 AI 图的转换（`convert_element_sources.py`）**：源图是**平滑渲染图，没有可还原的像素格**——实测完全不透明连续段长度为 745 / 201 / 164 / 260… 完全无周期，所以脚本不假装能对齐网格，而是按内容区缩放。三条关键决定，每条都来自前一次尝试的实测失败：

1. **内容区取自 alpha 通道**，而不是"判断是否白色"。该图背景是**透明**的，而全透明像素的 RGB 是**黑色**（四角采样 `(0,0,0)`）——按颜色判背景会把整张画布都算成内容，于是精灵被缩放到了整图上。
2. **输出 alpha 二值化**（覆盖率 ≥0.45 即全实、否则全空）。保留面积平均出的半透明覆盖率会在边缘留下一圈半透明格，在 16×16 下读作**发虚的边**而不是像素画的硬边。
3. **内部颜色按格中心取样，不做面积平均**。16 像素的精灵每格对应源图约 60×60 像素，直接平均会把作者的明暗全部摊平成泥；改为取每格中心小窗口的平均，保住原有色。缩放前做**预乘 alpha**（透明区的黑不得参与平均，否则边缘会被拉白）。

另加一道清理：**孤立过暗格**（比八个邻格都暗 60 以上）用邻格均值替换——缩放柔和剪影时偶尔会在边缘落下一个很暗的格（冰曾出现 1 个黑点）。该判据要求"比所有邻格都暗"，因此不会误删渐变内部正常的暗部（如气旋的涡心）。

**雷（`generate_thunder_sprite.py`）**：第一版雷是细长斜线，**70 像素 / 13 色**，而其余七张是 103–142 像素 / 99–136 色，摆在一起明显更小、更稀、更硬。故改为与其余七张同构：**实心团块 + 径向渐变 + 硬边**，形状改为偏竖直、闪电贯穿其中、另加 3 个分离火星。紫色 `#E4D0FF`→`#250D50` 八级色带插值，电弧用金色。剪影半径经两轮收紧（第一次 234 像素太大、第二次铺宽到 14×15 仍偏大），最终 **10×13 / 101 像素 / 54 色**。

### 5.4 三处为贴合画风而做的实测修正

| 问题 | 现象 | 处理 |
|---|---|---|
| 颜色数不足 | 初版每张仅 5–8 种色，用户的是 ~100 种 | 色带**插值成连续渐变**（64 级）后按分数级取样 |
| 抖动污染雷的配色 | 雷出现褐色杂点 | 金→紫的色带过渡会经过褐色，抖动一旦跨带就污染 ⇒ 抖动幅度压到 **1/3 级以内** |
| 整体偏浅发白 | 并排比较后，冰与风在用户的浓烈贴图旁像"泡泡" | 色带整体加深，剪影里中暗色占比提高 |

### 5.5 前两版失败方案的记录（避免重复踩）

**V1「共用基座 + 元素动效」**：八件共用一套棱面宝石外形，差异只来自色板与动效。被用户否决——"只像同款珠子换颜色"。

**V2「八种独立外形 + 12 帧动画」**：改为八种独立外形（金=晶簇、木=叶芽、水=水滴、火=火苗、土=岩块、冰=雪花、风=气旋、雷=闪电），自检全部通过，但用户判定更糟并改为静态图 + 自绘。**本版作废，其结论仍可供将来参考**：

- **「金」是唯一反复失败的**，共 8 版：三柱并排→皇冠、错落塔→城垛、中央尖柱+倾斜副柱→图腾、单棱柱→瓶子、八面体宝石簇→多角叶片、单颗菱形→无记忆点、换色后单棱柱→种子/胶囊、加缺损→残缺晶柱。**结论：16×16 下"金"没有公认符号，任何匀称的竖向形体都会读作容器或种子。**
- **描边不能一刀切**：宽实体形状（岩块、晶柱）必须用 **4 邻域**描边（8 邻域会把 4–5px 宽的晶柱腐蚀到只剩 1–2px 内壁）；细长肢体形状（雪花 1px 枝干）必须用 **8 邻域**（4 邻域下描边会包住整条枝干，读作齿轮）。
- **几何必须先全部收集成区域、最后统一描边 + 上色**：边画边上色会让后画的枝干擦掉先画好的描边（雪花曾完全没有 `rim` 像素）。
- **动效一般画在形状之上**；唯一例外是"缺损"（挖掉像素），必须在描边**之后**挖，否则描边会绕过缺口把缺口变成形状的一部分。
- **亮带动画在窄形体上会冻结**：晶柱仅 6px 宽时亮带整行一起变亮，导致相邻帧字节完全相同（实测先出现"前 3 帧冻结"，改正弦后又出现 2 对重复帧）。

### 6.7 光 / 暗的画法

| 元素 | 形象 | 做法 |
|---|---|---|
| 光 | 太阳 | 圆盘（径向渐变 + 边缘变暗）+ **4 长 4 短**的八向光芒 |
| 暗 | 月亮 | 满月本体（右上受光的月牙形亮部 → 左下沉入近黑）+ **向外渐亮**的冷紫光环 |

**暗为什么要用"向外渐亮的光环"**：用户要求"发着黑光的月亮"。纯黑在物品栏里**读作什么都没有**，所以本体取最深的紫（近黑但可辨轮廓），而"黑光"这个概念交给它外围那圈**由内向外变亮**的冷光来表达——发光的是那圈，本体保持暗。这是在 16×16 下同时满足"暗"与"可见"的唯一读法。

**两处迭代（都只有渲染后才暴露）**：

1. **太阳的光芒碎成了孤立小方块**——因为射线从内径 4.6 开始、而圆盘半径 4.4，中间留了空隙，2.7px 的短射线在 16 格下被离散热成单点。改为**射线直接从圆盘边缘长出**，并区分**4 长 4 短**（八条等长会读作八角星而不是太阳）。
2. **月亮的月牙挖空挖成了黑洞/甜甜圈**——初版用第二个偏移圆去"挖"月牙，在 16px 下把中心挖掉，读作甜甜圈。改为**满月本体 + 受光侧塑形**（真实的球体明暗），这才是这个尺寸下能读出"月亮"的写法。
3. **太阳的颜色数只有 32**（其余元素 54–136）——圆盘是大片平色。提高噪声幅度并加边缘变暗后为 **64**，进入区间。

## 8. Non-Goals

- **不给物品任何效果**（用户明确"暂时为最基础的物品"）；不新增属性、不注册药水效果、不加配方。
- **不做动画贴图**：用户明确改为静态图；`.mcmeta` 不得存在。
- **不做数据驱动**：8 件是固定内容，不引入 Codec/JSON 注册表。项目现有数据驱动项（水区域/结构效果/财宝成长/石碑放置）都是"整合包作者可能想改"的内容，本项不符合该判据。
- **不加配置项**：无任何可调开关（与天灾群系映射表同理，属结构性内容）。
- **不修改 `Rarity` 枚举**：见 §2.2。
- **不改动用户手绘的五张贴图**：只做「复制 + 改名」，不做任何像素修改；尺寸不符时脚本**拒绝安装**而不是缩放。

### 9.1 已作废：动画方案下关于"断言口径"的教训

下面三条出自已作废的动画方案（V2），但作为**写像素检查项时的通用原则**仍有价值——三条都是"断言本身写错了"而不只是代码错了：

- **不要断言某像素精确等于某个调色板色**：内部色是混合出来的，整数舍入使它常常差 1 而落不到精确值。真正要保证的是"有明暗区分度"，应改为断言色调数与亮度跨度。
- **阈值必须在调色板物理可达范围内**：内部色只存在于"压暗后的暗色"与"亮色"之间，故低对比调色板的**全部可达跨度**可能远小于直觉（实测冰只有不足 50）。阈值定得比可达范围还高，等于要求图形做不到的事。
- **细长形状不该被要求有内部明暗**：1px 线条状的形体本来就没有内部。断言改为条件式：有内部就必须有跨度，没有内部则交由看图判断。
