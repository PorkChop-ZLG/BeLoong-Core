## 0. 问题与目标

### 0.1 问题

本系统的 NPC **可以移动**（区别于传统站桩 NPC）。当某个玩家的剧情让 NPC 走开后，
**其他玩家就找不到也推不动自己的剧情**了 —— 多人服务器下当前系统不可用。

### 0.2 根因（**不是**"NPC 会动"）

在代码里逐条核过之后，根因可以精确表述为：

> **剧情需要的那部分状态是"每人一份"，而承载它的实体只有一份。**

依据（这三条是本设计的地基）：

| 机制 | 事实 | 依据 |
|---|---|---|
| 对话数据查表 | **按实体类型**查 ⇒ 同类型实体共用一份数据 | `NpcDialogueHandler.java:55` `get(target.getType())` |
| 回复可见性 | **按玩家判**（读该玩家自己的原版进度）| `NpcDialogueHandler.java:81` → `NpcDialogueStage.java:68/101`（签名都收 `ServerPlayer`）|
| 路线 / 表情 / 状态 | 挂在**实体**上（每实体一份）| `NpcRouteGoal.java:106/123/138/180` 全是 `this.npc.route()/routeIndex()` |

⇒ "数据与判定"**早就是每人一份**了 ✓；唯一被共享的是**实体的空间位置**（以及跟着它的路线进度）✓
⇒ 因此解法必然是：**把那部分状态搬到一份"属于该玩家"的实体上** ✓

### 0.3 目标

1. 多人服务器上，**每个玩家都能独立走完 NPC 剧情**，互不阻塞、互不干扰；
2. **保留可移动的 NPC**（剧情需要的位移照旧）；
3. 不因"每人一份"而无限堆积实体与半途状态（**清理机制**）。

### 0.4 非目标

- **多人共同观看同一段演出**（用户明确：暂不需要）
- **跨维度剧情**（本设计按"实例跟随某一维度"处理）
- **锚点的自动重建**（锚点被删属于运维事项）
- **存档迁移**：**实体**侧不需要 —— 现有世界里的那只 `beloong:mo` 天然就是"公共锚点" ✓。
  但**玩家进度**侧需要处理（**修正**：本文档初稿把这两件事混为一谈，说成了"不需要"）：
  升级前已获得 `root` 的玩家在新规则下"锚点被隐藏、又没有分身" ⇒ 眼里什么都没有 = **软锁**，
  且旧系统里多人共用一个 mo ⇒ **每个人的剧情位置在物理上无法还原**。裁定见 **D21**（统一按"剧情重新开始"）。

## 1. 架构

### 1.1 分类规则：按**状态所有权**

> 用"这个实体承载谁的状态"分类，而不是用"它能不能动"分类。
> 前者在"公共 NPC 将来也需要移动"时依然成立；后者会被规则卡死。

| 类别 | 定义 | 位置 | 可见性 |
|---|---|---|---|
| **公共锚点** | 承载**零玩家状态**，只是"场景里那个 NPC" | **永不因任何玩家的剧情而移动** | 对"**还没有自己分身**"的玩家可见 |
| **私有分身** | 承载**恰好一个玩家**的全部剧情状态（位置 / 路线 / 表情）| 自由移动 | **只**对该玩家可见、可交互 |

### 1.2 核心不变量（可直接当验收标准）

> **任一玩家眼里，`beloong:mo` 永远恰好只有一个** ——
> 未开始 ⇒ 是公共锚点；已开始（拿到 `root`）⇒ 是他自己的私有分身。

两个分支在 `root` 达成的**同一刻互换**，因此不变量恒成立。

### 1.3 两个实现地基（都用原版机制，不自造系统）

**地基 A：可见性 = 覆写 `Entity#broadcastToPlayer(ServerPlayer)` 的纯函数**

```java
// Entity.java:3021 —— 默认 true
public boolean broadcastToPlayer(ServerPlayer player) { return true; }

// ChunkMap.java:1327-1343（TrackedEntity.updatePlayer）—— 每个追踪周期、逐玩家问它
boolean flag = 在追踪距离内 && this.entity.broadcastToPlayer(player) && 区块已加载;
if (flag) { if (seenBy.add(conn)) serverEntity.addPairing(player); }     // 发给该玩家
else      { if (seenBy.remove(conn)) serverEntity.removePairing(player); } // 从该玩家移除
```

返回 `false` ⇒ 该玩家客户端上**这个实体根本不存在**：**无渲染 ✓ 无碰撞箱 ✓ 无法右键 ✓**，
且**零自定义网络包、零客户端改动** ✓（`ServerPlayer.java:957-961` 就是官方同款覆写：让旁观者不接收自己）

⚠️ 三个约束必须尊重：
- 它每个追踪周期对范围内**所有玩家**调用 ⇒ **必须是纯函数**（只能依赖"实体 + 该玩家"，不得写字段/发通知）
- 切换在**下一个追踪周期**生效（非瞬时）。本设计下**两者位置重合**，所以即使有几 tick 重叠也**视觉无感**
- **不用** `Entity#isInvisibleTo(Player)`（`Entity.java:2420`，渲染器在 `LivingEntityRenderer.java:122/246` 用它）：
  它只是**渲染层** ⇒ 实体仍在客户端、碰撞与交互都还在 ✗

**地基 B：事实来源 = 玩家自己的原版进度**

`beloong:npc/{root,1_1,2_0,2_1}` 本来就是每人一份 ✓ ⇒ **不新增任何每玩家持久状态** ✓
（与项目既有模式一致：`learned-patterns.md`「用原版系统当状态存储：把阶段交给 advancement，自己只做只读闸门」）

### 1.4 数据驱动：新数据类型 `npc_story`

数据目录：`data/beloong/beloong/npc_story/<实体类型路径>.json`（与 `npc_route`/`npc_dialogue` 同一套约定，
即 `data/<ns>/<modid>/...` 那一级）；加载方式照 `NpcRouteLoader`（服务端 reload listener + Codec）。

**最简形态（v3 最终字段）**：

```jsonc
// data/beloong/beloong/npc_story/mo.json
{
  "start_advancement": "beloong:npc/root",        // 必需：分身"从这一刻起应当存在"
  "end_advancement":   "beloong:npc/2_1",         // 必需：终态；同时是"撤回"的起点
  "spawn": "anchor",                              // 可选：anchor（默认）| [x,y,z]（+可选 dimension）| player
  "cg": "mo_entrance",                            // 可选：分身出现时由它播放的 CG（**仅事件路径**）

  "lifetime_ticks": 72000,                        // 可选：默认 72000（1 小时）；-1 = 永久
  "clear_on_logout": false,                       // 可选：默认 false（意外断线可续）
  "required_dimension": "beloong:loong_palace",   // 可选：省略 = 不限维度（**不硬编码**）
  "dimension_grace_ticks": 1200                   // 可选：默认 1200（60 秒）宽限
}
```

**数据形状的四条约定**：

1. **文件按实体类型命名**（`mo.json` ↔ `beloong:mo`）⇒ 与对话数据同构，"哪个 NPC"不必写进文件；
   将来地黄龙接剧情只需再放一个 `dihuang_loong.json`
2. **触发条件只支持"进度"一种** ⇒ 剧情本来就完全由原版进度驱动；再加"进某区域/右键就生成"这类条件
   需要写条件求值器 + 轮询，属于 YAGNI
3. **`end_advancement` 必需**（v3 新增用途）⇒ 它同时表达"剧情已完成"与"撤回走到哪为止"
4. **`cg` 解析失败不致命**：只打 WARN，**分身照常生成** ⇒ 生成与演出解耦，坏数据不毁剧情

### 2.1 改动 / 新增清单

| # | 组件 | 性质 |
|---|---|---|
| C1 | `NpcEntity` 增加**归属**：`@Nullable UUID owner` + NBT（沿用本项目 NBT 风格）+ `broadcastToPlayer` 覆写 + 一个可覆写的可见性判定 | 基类 ✓ 全部 NPC 共用；默认"无主 ⇒ 对所有人可见" ⇒ **现有 NPC（地黄龙）行为不变** |
| C2 | **私有分身复用同一种实体类型 `beloong:mo` + owner NBT**（**不新建实体类型**）| **零新增数据文件（除 `npc_story/mo.json`）✓ 零标签改动 ✓** 对话/路线数据完全复用 |
| C3 | `npc_story` 的 Codec + Loader | 照 `NpcRouteLoader` |
| C4 | **分身管家**：`AdvancementEarnEvent`（已有先例 `MoEntranceTrigger`）+ `PlayerLoggedInEvent` + 低频巡检 | 新类，含生成器与对账器 |
| C5 | `NpcDialogueHandler` 加**交互闸门**：私有的只认主人（防改包/去同步硬闯）| +2~3 行 |

### 2.2 可见性判定（两个分支，都 O(1)）

- **锚点**：`可见 ⇔ 该玩家未获得 root`
- **分身**：`可见 ⇔ 玩家 == owner`

两者在 `root` 达成那一刻互换 ⇒ 不变量（§1.2）恒成立。

### 2.3 CG 由**私有分身**播放（v2 修订）

| 现状 | 修订后 |
|---|---|
| `MoEntranceTrigger` 监听 `AdvancementEarnEvent` ⇒ 判 `beloong:npc/root` ⇒ **在玩家 ±48 格内搜索 `MoEntity` 取最近**（`MoEntranceTrigger.java:48`、`:60-65`）⇒ 播 `mo_entrance` | 同一事件位置改成：**先幂等确保该玩家的私有分身存在** ⇒ **直接持有这个引用**去播 CG ⇒ **整个"就近搜索"被删除** |

**顺序（实现约束）**：

```
AdvancementEarnEvent(root)
 → ① 幂等确保私有分身存在（已存在则复用，不重复生成）
 → ② 在【锚点位置与朝向】把分身放好   ← CG 的相机轨迹"触发即烘成世界坐标" ⇒ 必须先生成、后播
 → ③ CgRegistry.byName("mo_entrance") 取 CG ⇒ 以【分身】为 target 播放
 → ④ 锚点对该玩家隐藏（下一追踪周期生效）
```

**三个收益**：

1. **"找不到末就不播 CG"这个失败模式彻底消失** ⇒ 演员改为**按需构造**。
   对应地，推翻 `MoEntranceTrigger` 原有的"找不到就只 WARN、不重试"裁定（原 WARN 文案：
   `no beloong:mo is within 48 blocks — the mo_entrance CG was NOT played`）
2. **不会再挑到别人的分身** ⇒ 引用是自己刚创建的，无歧义
3. **CG 主体与"玩家的那个 mo"严格同一** ⇒ 不存在"CG 演锚点、走剧情演分身"的错位

**兜底（锚点不存在时）**：在玩家**身前若干格**生成 + WARN ——
不能生成在玩家脚下 ✗：`CgContext.of` 在"观察者与锚点水平重合"时返回 `null`（方向退化）⇒ CG 会直接中止。

### 2.4 分身管家（生成 + 对账）

- **生成（事件路径）**：`AdvancementEarnEvent` 命中 `start_advancement` ⇒ 生成 + 放好 + （可选）播 CG
- **对账（声明路径）**：登录时 ✓ + 进度变化时 ✓ + 低频巡检（可配）✓ ⇒
  **"按所有 `npc_story` 声明，把该玩家世界里的私有分身补齐/清除"** ⇒ 幂等 ✓ 自愈 ✓
- **锚点的定义**：**该实体类型的"无主实例"**（`owner == null`）；
  找不到 ⇒ 按 §2.3 兜底；找到多个 ⇒ 取最近的一个 + WARN
- **效率**：对账**不得** O(玩家 × 实体)。一次遍历该维度实体建 `owner → entity` 映射（O(实体)），
  再逐个在线玩家比对（O(玩家)）；顺手检出**重复分身**

## 3. 数据流

### 3.1 一次完整旅程

```
A 进龙宫 ⇒ 获得 root（原版 location 触发，每人一份）
   └─ 同一刻发生四件事（§2.3 的顺序）：
      ① 在【锚点的当前位置与朝向】生成 A 的私有分身   ← 关键：同位置 ⇒ 切换视觉无感
      ② CG 由【分身】播放
      ③ 锚点对 A 隐藏（下一追踪周期内生效）
   ⇒ 此后 A 眼里那个 mo 就是【他自己的分身】，但位置/外观与之前完全一致，玩家无感

A 右键那个 mo（其实是分身）⇒ 对话；数据按类型查、闸门按 A 自己的进度判
A 点 reply1 ⇒ 现状那两条命令照旧执行
   └─ /beloong route beloong:mo_route_1 经 LastDialogueNpc 解析 ⇒ 指到【分身】
   ⇒ 【锚点一次都没动】

玩家 B 同时在场：B 未开始 ⇒ B 看到的是【锚点】（在自己该在的位置），
   A 的分身对 B 完全不存在（不可见、不可点、无碰撞箱）
B 进龙宫 ⇒ 同样拿到自己的分身 ⇒ 各走各的
```

### 3.2 为什么生成时机是"`root` 达成那一刻"

最初我主张"分身生成与交互无关、纯进度驱动"，但**路线指派是靠 `LastDialogueNpc`（玩家最近对话过的那个实体）解析的** ⇒
必须保证"玩家对话的那个实体就是他将来的分身" ⇒ 生成点必须**早于**第一次对话。
⇒ 因此生成时机 = `root` 达成那一刻（这也吸收了"用交互来确立剧情主角"的洞察）。
⇒ 附带好处：**"锚点可见 ⇔ 无分身"这条规则不再有软锁窗口**。

### 3.3 对账器决策表（每 N 秒 + 事件上各跑一次）

| 观察到的状态 | 动作 |
|---|---|
| 应当有 ∧ 没有（含老存档）| **按 D21 重置**：撤回整条链 + WARN（**不生成、不播 CG**）⇒ 玩家回入口重新获得 `root`；CG 只在 `AdvancementEarnEvent` 那条路播（否则重连会重播）|
| 应当有 ∧ 有 ∧ **超时**（`now − bornAt > lifetime_ticks`）| 删除 ✓ ⇒ 进行中 ⇒ **同时撤回整条链**；已完成 ⇒ 只删不撤 + INFO |
| 应当有 ∧ 有 ∧ 离线超过宽限 ∧ `clear_on_logout=true` | 删除 + 撤回 |
| 应当有 ∧ 有 ∧ 不在 `required_dimension` 超过宽限 | 删除 + 撤回 |
| 应当有 ∧ 有 ∧ 任意一项仍在宽限内 | 什么都不做（等待）|
| **已完成**（有 `end_advancement`）∧ 有 | **保留**（D6）✓ |
| 未开始 ∧ 有 | 异常 ⇒ 删除 + WARN |
| 有多个 | 保留最近生成的、其余删除 + WARN |

## 4. 清理机制（租约）

### 4.1 三轴

把私有分身看成一笔**有租约（lease）的实例**：**时间**（时长）/ **会话**（在线）/ **空间**（维度）。

### 4.2 字段与默认值

见 §1.4。三条要点：

- **`lifetime_ticks` 默认有限（1 小时）**；`-1` = 永久。
  ⚠️ 刻意**不用 `0` 表示永久**：数值上 `0` 更像"立刻过期"，容易写反
- **`required_dimension` 省略 = 不限维度**：维度是**内容**，不写进框架默认值（龙宫写在 `mo.json` 里）
- **`dimension_grace_ticks`**：离开维度/离线到清理之间的宽限。
  ⚠️ 没有它，**在龙宫死一次**（重生回主世界）就会被判失败 ⇒ 宽限 60 秒，走回来就没事

### 4.3 撤回算法（**已裁定：沿父链**）

```
adv = end_advancement
while (adv != null):
    revoke(player, adv)
    if (adv == start_advancement) break
    adv = adv.parent()          // 走不到 start ⇒ 英文 WARN（说明链被改坏了）
```

**为什么可行**（实测数据）：剧情进度是一条**严格线性的父链** ——
`root←(无)`、`1_1←root`、`2_0←1_1`、`2_1←2_0`，无兄弟。

**为什么必须整条链一起撤**：只撤 `root` 的话，`2_0` 仍在 ⇒ `reply2` 依然可选 ⇒
玩家能**跳过路线 1** 直接进第二段 ⇒ 流程被破坏。

**为什么不手写"进度组"**：那份列表要人工维护，漏一个就回到"有进度、没分身"的软锁；
沿链则由守卫钉住"链必须单线"即可。

**与原版的关系**：`/advancement revoke <targets> until <adv>` 就是同一套语义（撤销目标及其**全部祖先**）。

### 4.4 已验证的良性交互与已知代价

**"到点即清 + 撤回"在起点会瞬间重启 —— 但这是良性的**（已实测边界）：

| 事实 | 值 / 依据 |
|---|---|
| `root` 触发器 | `minecraft:location` ⇒ **每 20 tick 轮询** |
| `root` 盒子 | `beloong:loong_palace`，x −8..8，y 56..72，**z −16..0** |
| 剧情后段位置 | 路线 1 走到 z=−55；石碑 ≈−57；路线 2 到 −108 ⇒ **都在盒子之外** |
| 另三个进度 | `1_1`=`impossible`、`2_1`=`impossible`、`2_0`=右键石碑 ⇒ **撤回后不会自动重新授予** |

⇒ **只有"玩家正站在起点盒子里"时**，撤回后 ≤20 tick 会重新获得 `root` ⇒ 分身与 CG **立刻重来一次**。
这恰好等于"**站在起点超时 ⇒ 回到起点重新开始**"，是期望行为；代价是**多看一次登场 CG**。
⇒ **深剧情超时（z ≤ −20）不会自动重启**，玩家必须自己走回起点 —— 正是规则 5 想要的行为。

### 4.5 提示与可观测性

- **清理前给玩家一条可见提示**（提前量可配）：否则玩家无法理解为何被重置
- **每次清理写一条英文日志**，写明原因（超时 / 离开维度 / 离线 / 重复 / 异常）+ 玩家 + 剧情名：
  让服主能回答"我的剧情为什么被重置了"

## 5. 错误处理

| 情形 | 处理 |
|---|---|
| 分身缺失 / 被 `/kill` / 老存档（已获 `root` 但无分身）| **统一按"剧情重新开始"**（D21）：撤回整条链 + 英文 WARN ⇒ 玩家回入口重新获得 `root` 再走一遍。⚠️ **不可**改为"就地重新生成一只分身" —— 中期阶段（`1_1`/`2_0` 已获得）会变成"两条回复都不显示"，玩家对着一只不会说话的 mo 卡死 |
| 出现重复分身 | 生成前按 owner **查重（幂等）**；巡检发现多个 ⇒ 保留最近的一个、移除其余 + WARN |
| 切换时序 | 可见性在**下一个追踪周期**生效；因两者位置重合 ⇒ 视觉无感、无副作用（将来若需瞬时，补一个"从该玩家移除实体"的包即可）|
| 他人硬闯（改包交互）| 服务端在 `NpcDialogueHandler` 再判一次"私有的只认主人" ⇒ 静默忽略 |
| 锚点被删 | 新玩家无法开始 ⇒ 按 §2.3 兜底 + WARN；**自动重建不在本设计内**（运维事项）|
| `npc_story` 里 `cg` 名字写错 | 只 WARN，分身照常生成 |
| 剧情链被改坏（撤回走不到 start）| 英文 WARN + 尽可能撤回 |
| 玩家退出 / 重连 | 分身随世界持久化（owner 在 NBT 里）⇒ 重登后仍在原处、仍只对自己可见；租约计时**按游戏时间（tick）继续走** |

## 6. 验证策略

本项目**没有测试套件** ⇒ 验证 = **不变量脚本 + 实机**。

### 6.1 机械守卫（加进 `tools/YSMParser/stage_invariants.py`）

- `NpcEntity` 的 owner 字段**写进 NBT 且读写对称**
- `broadcastToPlayer` 覆写**存在**且**纯函数式**（不写字段；用文本断言 + 人工复核）
- 剧情链**线性**：每个非 root 的剧情进度**恰好一个父**，且**链上没有非剧情的子进度**
- 对账器**幂等**（生成前按 owner 查重）
- CG **只出现在事件路径**里（对账器补生成时不得调 CG）
- 租约字段（`bornAt` / `lifetime_ticks`）在 NBT 里读写对称
- `npc_story` 里的 `start_advancement`/`end_advancement` 与对话数据里的闸门**逐字一致**

### 6.2 实机验收清单

1. 双人同服：A 走完第一段 ⇒ **B 进龙宫看到的仍是入口的 mo**
2. A 的分身在 A 眼里正常走路；在 B 眼里**不存在**（看不到、点不到、无碰撞）
3. B 与 mo 对话完全不受 A 影响
4. A、B 的分身位置互不干扰（同时各走各的路线）
5. 双双重登 ⇒ 各自分身仍在原处、仍只对自己可见
6. 删掉 A 的分身再让 A 重登 ⇒ **自愈 + WARN**
7. A 在剧情中途走出龙宫维度超过宽限 ⇒ 分身被清、进度被撤 ⇒ 回龙宫需重新获得 `root` 再走一遍
8. 把 `lifetime_ticks` 临时改小 ⇒ 到点清理 + 撤回；**若 A 已完成剧情 ⇒ 只清理不撤回**
9. 站在起点盒子里等到超时 ⇒ 分身与 CG 重来一次（良性，§4.4）

## 7. 决策记录（含被否决方案与推翻记录）

### v1（架构与可见性）

| # | 决定 | 否决的方案与理由 |
|---|---|---|
| D1 | 分类按**状态所有权** | ✗"按能不能动"：公共 NPC 将来若需要移动就被规则卡死 |
| D2 | 分身用**同类型 + owner NBT** | ✗新建类型 `beloong:mo_double`：要复制一份对话数据、多一处标签登记；而闸门本就按玩家判 ⇒ 共用数据完全够用 |
| D3 | 可见性 = **覆写 `broadcastToPlayer`** | ✗`isInvisibleTo`：只是渲染层，碰撞与交互仍在；✗自建可见性系统 + 自定义包：多状态、多同步、多一类 bug |
| D4 | 事实来源 = **玩家已有的原版进度** | ✗新增每玩家持久状态：重复存储、两处可能不一致 |
| D5 | 分身生成时机 = **`root` 达成那一刻** | ✗"与锚点交互时"：会留下软锁窗口；✗"与交互完全无关"：会与 `LastDialogueNpc` 的解析对象错位（详见 §3.2）|
| D6 | 分身终态 = **保留但只对主人可见** | ✗消散：剧情结尾"末坐在那里"对主人有意义，且保留实现更简单 |
| D7 | 锚点**永不因剧情移动**（去掉"回家机制"）| ✗移动 + 回家：会把共享实体重新变成多人争用点 |

### v2（CG 与数据驱动）

| # | 决定 | 说明 |
|---|---|---|
| D8 | 数据驱动：新增 `npc_story`，按实体类型一文件 | 与 `npc_dialogue`/`npc_route` 同构 |
| D9 | **CG 由私有分身播放**；删除"就近搜索 `MoEntity`" | **推翻** `MoEntranceTrigger` 原有的"找不到就只 WARN、不重试"裁定 ⇒ 演员改为按需构造，该失败模式不存在了 |
| D10 | **存在性声明式 + 演出事件式** 分离 | ✗自己记录"CG 是否播过"：起点进度天然就是那个标记，且与项目既有"只读闸门"模式一致 |
| D11 | 锚点 = 该类型的**无主实例** | 让"公共/私有"在代码与数据两侧都可表达 |
| D12 | `cg` 解析失败只 WARN、不影响分身 | 生成与演出解耦，坏数据不毁剧情 |
| D13 | 加入 `end_advancement` | v3 里它承担"是否已完成"与"撤回起点"两个职责 |

### v3（清理机制）

| # | 决定 | 否决与理由 |
|---|---|---|
| D14 | 租约（生成时刻 + 时长）**记在实体 NBT** | ✗每次现算 / 存在玩家侧：要么 O(实体数)，要么多一份会漂移的状态。好处：**以后改数据里的时长不会追溯影响已存在的分身** |
| D15 | **清理与撤回原子**（同一刻、同一入口）| ✗先清后撤：中间态就是软锁 |
| D16 | 是否撤回由**是否已完成**决定 | ✗按清理原因决定：会把**通关玩家**判成失败（原方案规则 5 的漏洞）|
| D17 | 撤回**沿剧情链**（`end` → `parent()` → `start`）| ✗手写进度组：要人工维护、漏一个就软锁；原版 `revoke … until` 是同一语义（§4.3）|
| D18 | 维度**不硬编码**，进数据 | ✗把龙宫写进框架默认值 |
| D19 | **宽限期**（默认 60 秒）| ✗立即清：在龙宫死一次（重生回主世界）就被误判为弃坑 |
| D20 | 清理前**给玩家提示** + 每次清理写**英文审计日志** | ✗静默清理：玩家无法理解为何被重置，服主也查不出原因 |
| **D21** | `已获 root 但无分身`（**老存档** 或 **分身中途丢失**）⇒ **统一按"剧情重新开始"**：撤回整条链，玩家回龙宫入口重新获得 `root` 再走一遍 | ✗"就地补生成分身、不动进度"：只在最早阶段有效（`root` 后未对话 ✓），一旦 `1_1`/`2_0` 已获得 ⇒ `reply1` 要求 `1_1` 未完成、`reply2` 要求 `2_0` 已完成 ⇒ **两条回复都不显示** ⇒ 卡死；要做对就得写"按阶段分叉"的规则 ✗。✓一条统一规则同时覆盖两种情形，且可被守卫证明（`root ∧ 无分身 ⇒ 必然重置`）|
| D21 补充 | 因此 §2.2 的两条可见性规则**保持"只依赖进度"**（锚点 ⇔ 未获 `root`；分身 ⇔ owner 是自己）| 不需要任何"该玩家是否已有分身"的查询 ⇒ 可见性判定仍是 **O(1) 纯函数**（这一点很重要：否则 `broadcastToPlayer` 每追踪周期要做实体搜索）|

### 额外记录：一处量级修正（诚实）

原方案把清理的必要性表述为"100 个分身会带来较大性能开销"。核过之后需要修正：
**持久化实体不强制加载区块** ⇒ 离线玩家或无人区域的分身**根本不 tick** ⇒
"100 个分身每 tick 全跑"不会发生。真正的成本是：① 世界实体条数 ② 同区域聚集时一起 tick
③ 存档与状态卫生 ④ **玩家已弃坑但状态停在半途**。
⇒ **清理机制依然值得做**，但理由应写成"**卫生 + 状态一致性**"，而不是"否则卡服"。
（顺带：因为可见性只发给主人 ⇒ 客户端渲染压力天然被限制。）
